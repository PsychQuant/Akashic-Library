# #664 — Semantic Scholar 共用接口（`akashic s2`、`akashic_s2`）

Spectra change `semantic-scholar-interface`（`openspec/changes/semantic-scholar-interface/`）。使用者有 Semantic Scholar（S2）的 API 金鑰，要讓 Akashic 的使用者與 skill 都能查它。

## 交付

- **`AkashicS2`**（新 library target）：本體裡唯一可以連網、唯一可以讀 keychain 的地方。八個端點（`paper`、`match`、`batch`、`references`、`citations`、`recommend`、`author-search`、`author-papers`）加不連網的 `status`。
- **CLI `akashic s2 …`** 與 **MCP `akashic_s2`**：兩面共用 `AkashicS2`，不經 `AkashicService`、不開 store。回傳是線索，不是寫入。
- **金鑰**：keychain `semantic-scholar`／`default`，程序內非互動讀取；不收指令參數或環境變數；`x-api-key` 只附給 `https` 且 host 恰為 `api.semanticscholar.org` 的請求；連線無快取、無 cookie、不跟隨轉址。
- **全機每秒至多 1 個請求**（檔案鎖預約時段）；429 的退避由所有呼叫者共用。
- **守衛 `akashic-guards network-confinement`**（負對照 `network-confinement-mutations`）：九個網路與 keychain 字樣只准出現在 `Sources/AkashicS2/`。它是字面的封閉清單，不是證明沒有別的連網途徑。
- 規則：`web-access-via-safari-browser.md` 的〈例外〉改為兩類、新增〈Semantic Scholar 的取得順序〉；`mcp-cli-parity.md` 加 `akashic_s2`／`s2` 一列（不經服務層的封閉例外）。

## 這一輪留下的教訓（寫進規則的〈觸發過的實例〉）

- **承諾的對象是真實的網路層時，stub 驗不到。** 「金鑰不寫進任何檔案、只送 S2 主機」是設計承諾；測試全用 `URLProtocol` stub，stub 不經快取也不轉址，所以實作者自己的驗證全綠，驗證才抓到。修正後補了碰真網路層的測試（兩個 loopback 伺服器、轉址目標不得收到任何請求；CLI 測試前後比對 URLCache 的檔案），並做過變異檢查。
- **逐請求的 `cachePolicy` 只管「讀不讀快取」，不管「存不存」。** 保證要放在連線這一層。
- **取得順序的列舉要用程式真正的值域來寫。** 第一版只列結束碼 0 與 3，漏了「項目在、讀不到」與版本落差；第二版把 `present` 當成「沒有項目」，程式卻把其他 keychain 錯誤也算成 `present: false`。

## 量測

- `tools/list`：35 個工具、回應 59,137 位元組（`akashic_s2` 附在陣列最後，不改變其他工具的呈現順序）。
- 全套測試、守衛：`swift build`、`swift test`、`run-guards.sh` 都帶 `-Xswiftc -warnings-as-errors`。**一次整套測試被 `RealHomeSandboxGuard` 中止**（真實 `~/.akashic` 在測試期間被改動；三個 bundle、三條不同的路徑、中斷點與 S2 無關，同時本機有別的 session 的測試與十幾個常駐的 `akashic-mcp`）。排查結論是外部程序，**是推論不是證明**；本機安靜後整套重跑全過，守衛沒有被停用。
