# 第三輪 verify 收尾：最後兩條，以及一個「看起來像唯一讀檔點」的旁路

2026-08-25 傍晚。PR #425 的 6 個 HIGH 全部修完。前四條記在
`2026-08-25-verify-round-three-fixes.md`，本篇記最後兩條。

## 五、`entryDict` 對 work 的識別碼全盲——而守衛找到六個

`entryDict` 逐欄位組 payload，而 #394 新增的 `doi`／`pmid`／`isbn` **一個都沒進去**
——`akashic get-entry` 與 MCP 兩面同時失明。

**這與已修的 venue ISSN 是同一族、換一個 entity kind。** 修 venue 那次我加了
`VenueSurfaceTests`，但**沒有問「這一族還有誰」**——於是同一個形狀在 entry 上又存在
了一輪。本輪加 `EntrySurfaceTests` 就是那個問題的答案。

守衛找到**六個**缺口，而只有四個屬於 #394：

| 欄位 | 來源 | 處置 |
|---|---|---|
| `doi`／`pmid`／`isbn` | #394 §4 | 修 |
| `references` | #394 §5（第 15 條邊） | 修 |
| `venues` | **#304** | 開 #426，依 scope guard 不混入 |
| `thesis` | **#335** | 同上 |

### `knownGaps` ≠ `exempt`

兩個既有缺口列在 `knownGaps` 而不是 `exempt`。語意不同：**exempt 是「刻意不輸出」，
knownGaps 是「該輸出而還沒輸出」**。混為一談會讓守衛在下次有人問「為什麼看不到
venues」時給出**錯的答案**。守衛額外斷言每個 knownGap 都指向一張 issue。

### 守衛要認得 canonical accessor

payload 讀的是 `entry.canonicalDOIs`（doc 明寫「讀取請走它」——殘留與結構化值同時
在場時它才是正典），而守衛的字面比對找 `entry.doi`，於是報了假紅。

加 alias 對照之前，值得看清楚那個假紅的方向：**守衛若只認欄位名的字面，會逼呼叫端
改用較差的讀法才能過關**。一個守衛把正確實作判成違規，比漏報更糟——它會主動把
程式碼推向錯的方向。

## 六、乾跑拒跑而 `--apply` 成功

形狀升級只在 `apply == true` 寫檔，所以乾跑時裸純量還在 → load 對那些檔 quarantine
→ 守衛 throw；而 `--apply` 先升級再 load 因而**成功**。同一個 store，兩種模式相反的結果。

這違反本命令自己寫下的契約（「乾跑與 apply 得到**同一組** blockers——乾跑因此真的能
預告 apply 的結果」）與守衛自己的註解（「兩種模式都擋」，實際上只擋乾跑）。

**而錯誤訊息說了假話**：它斷言那是「本命令的形狀前置升級沒認出的寫法（它只認頂格
`issn:` ＋ 頂格 `- `）」，而實測觸發值**正是**它認得的形式。工具會自己修，只是乾跑
不准寫——於是使用者被指示去手改 39 個檔。修完之後那句話變成假的，一併更正；留著
會讓下一個人往錯的方向查。

### 裁決：乾跑模擬升級後再 load

`LibraryStore.textOverrides`（絕對路徑 → 內容）讓乾跑把升級後的文字餵給 decode 而
**磁碟一個位元組都不動**。

**這不是相容路徑。** `no-compat-fallback` 的三個封閉類別是「缺欄位推導／舊欄位別名／
舊目錄回退」——它一個都不是。它是顯式的預演注入點，`grep textOverrides` 一眼看完
（目前只有一處），空字典時行為逐位元不變。

## 一個「看起來像唯一讀檔點」的旁路

第一版我把覆寫掛在 `readUTF8` 上——它長得就像 store 的讀檔入口。測試照樣紅，而我
差點以為是 key 對不上。

真因用 `grep -n readUTF8` 一眼看出：**它只有兩個呼叫端，都在 quarantine 報告裡，
沒有一處在 `load()` 的主路徑上**。`load()` 走的是 `CanonicalLoadSource.data` closure。

值得記的不是「我掛錯地方」，是**一個函式的名字與它的實際涵蓋範圍可以差很遠**，
而確認的方法很便宜：數它的呼叫端。

## 負控的第五個變體

這一輪的負控全部通過，但過程中出現一個新變體值得記：**`EntrySurfaceTests` 的第一版
在「正確的實作」上就紅了**（因為 canonical accessor）。那不是負控失敗，是守衛本身的
判準太窄——而它的危害方向與漏報相反：**它會逼人把對的程式碼改壞**。

今天累計五種「測試沒有測到它以為在測的東西」：

1. fixture 用了形狀不合法的值（`10.1/abc`）
2. mutation 的粒度太粗（把兩個獨立修改綁成一個）
3. mutation 沒有真的改變行為（只改 `.map` 來源）
4. 因果鏈被截斷（`==` 失敗就不寫檔，於是殘留測不到）
5. **守衛的判準太窄，對正確實作報紅**

前四種讓守衛**漏**，第五種讓守衛**誤傷**。
