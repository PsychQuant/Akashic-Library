# person 的外部來源

補完一個人需要的東西通常是：識別碼（ORCID）、著作清單、任職與任期、姓名的各種寫法。

## 可信度是「對某類問題」的，不是來源的全域評級

同一個來源對不同問題可靠度完全不同。實測最清楚的例子是 ORCID：

| 問的問題 | ORCID 的可信度 |
|---|---|
| 這筆著作是不是這個人的？ | **最高**——本人維護、零消歧錯誤 |
| 這個人的著作**就是這些**嗎？ | **很低**——系統性缺近期 |

實測：某機構 41 位研究者的 ORCID 共 1291 筆著作，但對照圖書館的 WoS 匯出，**只有 36% 的已知著作出現在同一人的 ORCID 裡**，且缺的幾乎全是最近兩年的。

所以看到「ORCID 是 Tier 1」這類排序時，要問它排的是**準確性**還是**完整性**——那是兩個不同的序。

## ORCID

```
https://pub.orcid.org/v3.0/expanded-search/?q=<查詢>        # 找 iD
https://pub.orcid.org/v3.0/<iD>/works                      # 著作
https://pub.orcid.org/v3.0/<iD>/record                     # 完整記錄
```

免費、免金鑰，帶 `Accept: application/json`。

### 兩個實測踩到的陷阱

**一、`employment` 欄只列現職，永遠不回填歷史。** 一位研究者曾在 A 機構任職、現在在 B，他的 ORCID employment 通常**只有 B**。用 employment 判斷「這人是否曾屬於某機構」會系統性漏掉所有已離職者。

實測案例：某人的 ORCID employment 只列劍橋，但名冊顯示他 2004–2009 在另一機構。救回的方式不是找更權威的來源，而是**交叉佐證**——著作時間窗落在該任期內＋主題相符＋有一篇與該機構已確認成員的合著。

**二、`given-names` 常存的是英文暱稱而非拼音。** 一位中文姓名的研究者，ORCID 的 given-names 可能是 `Grace` 而不是 `Shwu-Rong`。用拼音去比對會查無此人。找人時姓氏比名字可靠。

## 個人網站與機構名冊

對「這個人在哪、任期多久」這類問題，機構自己的頁面通常比任何聚合服務準確——但格式各異，需要逐個處理。

**實測有用的模式**：

- **退休／歷任頁**常帶完整任期（起訖年月），現職頁反而只有現況、沒有到職日
- **舊版微站**（週年紀念站之類）常保留已離職者的頁面，是找歷史成員的好來源。檔名規則通常有跡可循，摸出來之後可以批次取得
- 舊頁面可能是 **Big5 之類的非 UTF-8 編碼**，抓下來先確認編碼
- 已離職者的個人頁**存活率很高**——不要預設「人走了頁面就沒了」

**抓取禮儀（實測踩過）**：短時間內對同一網域發數十個請求會觸發 nginx 403，而且**被擋之後看起來像是頁面不存在**——會讓你錯誤地記錄「該站已失效」。請求之間留延遲，被擋了要能區分「擋」與「無」。

## 姓名比對

中文姓名的羅馬拼音有多種系統（威妥瑪、漢語拼音、以及個人慣用寫法），同一人在不同來源可能是 `Jine-Phone Chou` 與 `Jin-Phone Chou`。

**判定同一人靠佐證，不靠拼音相似度**：學位授予機構與年份、任職起訖、與已確認成員的合著關係。實測三次來源不一致，兩次靠佐證解決、一次根本不是衝突（兩來源時間互補），**零次靠「誰比較權威」的排序解決**。

含意：大多數時候來源是互補的，不是競爭的。先建佐證鏈，不要先建優先序表。

## 著作清單的其他來源

| 來源 | 用途 | 注意 |
|---|---|---|
| 機構圖書館的 WoS／Scopus 匯出 | 當期著作最完整 | 常缺 DOI 與機構欄，要另外補 |
| 個人網站的著作列表 | 涵蓋 ORCID 缺的近期 | 格式非標準，多數要逐篇人工對照 |
| 期刊的紀念專輯（已故者） | 有時附完整著作目錄 | **不要預設有**——實測某位的紀念專輯只有 Highlights 與 Editorial，沒有著作目錄 |
| 學位論文庫 | 早期著作、指導關係 | — |

## 建立 person 實體的門檻

從裸字串作者建人物實體時，出現次數是一個可用的門檻。實測一份 100 篇論文的作者分佈：

| 出現次數 | 不同名字數 |
|---:|---:|
| ≥3 次 | 79 |
| ≥2 次 | 181 |
| 全部 | 746 |

出現 1 次的佔 76%。要不要建取決於用途：做合作網絡分析時骨幹是 ≥3 次的那些；要讓每個作者槽都有實體則全建。

**建立時只會有一個名字**——bootstrap 出來的實體只帶當時那個字串。其他寫法要之後補進 `names`。
