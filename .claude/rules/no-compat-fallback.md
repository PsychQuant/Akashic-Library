# 不留相容 fallback：要改格式就一次改完全部

使用者 2026-08-12（+08:00）定調：「不要 fallback，要改就一次改全部」。

適用於**為了讀舊資料而保留的相容路徑**。以下是**封閉列舉，只有三類，不得依性質
相似類推第四類**：

1. **缺欄位的推導或預設值**——舊記錄沒有某欄位，程式在讀取時推一個出來。
   實例（2026-08-12 全庫掃描，**目前就這兩處**）：
   - `Models.swift:295` — `self.id = id ?? DeterministicUUID.forPerson(key: key)`
   - `Organization.swift:98` — `self.id = id ?? DeterministicUUID.forOrganization(key: key)`
2. **舊欄位名的別名**——同一個語意讀兩個鍵，因為某個版本改過名字。
   **本 repo 目前沒有實例**（掃過 `YAML.swift`）。列在這裡是為了在它出現時就擋掉，
   不是在描述現況。
3. **舊目錄佈局的回退搜尋**——新位置找不到就去舊位置找。
   **本 repo 目前沒有實例。** 見下方「不算的近似案例」——`usesEntitiesLayout` 看起來
   像這一類，但不是。

## 不適用（同樣是封閉列舉，只有四類）

這四類**不是**本規則所稱的 fallback，寫進來是因為「fallback」這個詞太大，
不明寫就會把它們一起吃掉：

1. **錯誤處理與重試**——網路失敗重試、逾時退避。
2. **明說的功能降級**——外部依賴不在時走替代路徑，**且對使用者說了**。
3. **缺席即語意的可選欄位**——`orcid` 沒有就是沒有。那不是回退，那是 `nil` 的意思。
4. **安全側的保守預設**——判不準時選比較嚴的那邊（fail-closed）。

### 不算的近似案例：佈局模式切換

`LibraryStore.swift:411` 的

```swift
let dest = usesEntitiesLayout ? entityURL(id: entry.id) : entryURL(citekey: entry.citekey)
```

**不受本規則管**。它是**每個 store 判定一次的模式**，不是「先試新的、失敗再試舊的」。
兩者的差別在**是否存在雙重讀法**：模式切換下，任一個 store 只有一種佈局，行為單一；
回退搜尋則是同一個 store 同時可能命中兩處，那才是本規則要防的分岔。

寫下這個近似案例，是因為它長得夠像，不明說就會有人（包括未來的我）拿本規則去砍它。

## 規則

**不新增第一段所列的相容路徑。** 要改格式，就在同一個變更裡把**全部既有資料**
改完，然後只留新路徑。

一次改不完時（資料在別人手上、跨機器未協調、遷移需要人判斷），相容路徑可以存在，
但必須同時滿足三條：

1. **不得住在 default 位置。** 要顯式呼叫，讓「誰還在走它」grep 得出來。
   `id ?? derive(key)` 是反例：每個沒帶 id 的呼叫端都**默默**走了相容路徑。
   正例是分成 `Person(key:names:id:)`（要求顯式 id）與一個具名的
   `Person.backfillingLegacyID(key:names:)`。
2. **寫下退場條件，以及量它的方法。** 不是「之後再刪」，是「當 `<這個量測>` 回 0
   就刪」。量測要具體到能貼進終端機跑。
3. **退場後刪掉，不留著當保險。** 留著的相容路徑不會保護任何東西，它只是在等
   一個新的呼叫端誤入。

## 為什麼：不對稱

| 選擇 | 代價 |
|---|---|
| 一次改完 | 一次痛。改的當下要寫 migration、要驗數量歸零。可逆——改壞了 revert |
| 留 fallback | 兩條路各自演化。**而且分岔是安靜的**：兩條路都「能跑」，只是在某些輸入上答案不同 |

一次改完的成本是**當下且有界**的；留 fallback 的成本是**未來且無界**的——它按
「之後有多少人碰到這段程式」計費，而那個數字你現在不知道。

## 為什麼：相容路徑會活得比它的用途久，而且沒有人會發現

2026-08-12 的實測（#241）：

```
person 記錄            869
磁碟上已有 id: 欄位     869
仍需 v5 補值            0
```

`id ?? DeterministicUUID.forPerson(key: key)` 這行**當初是對的**——舊的
`people/<key>.yaml` 沒有 `id:` 欄位，而兩台從沒協調過的機器必須推出**相同**的值，
否則同一個人在不同 clone 得到不同 id，index 主鍵分岔、entry 的作者引用斷掉。
用 v5（由 key 決定）而不是 v4（隨機）正是為此。

遷移做完之後，那條路的**正當用途歸零**，但它還在 default 位置上。於是現在唯一
還走得到它的是「新建記錄」——也就是它會**傷害**的那個情況：新人的身分變成他名字
的函數，兩個同名的人在合併 library 時會安靜熔成一筆。

**它變壞不是因為有人改錯，是因為世界變了而程式碼沒跟著退場。**

這種缺陷讀程式碼發現不了——那行沒有任何地方看起來可疑。要抓到它只能問「這條路
現在還有誰在走」，而那是**量測問題不是閱讀問題**。所以規則的第 2 條要求把量測
寫下來：沒寫下來，就沒有人會去量。

## 為什麼：同一個性質在兩種情況下價值相反

v5 的決定性（同輸入必得同輸出）在兩個場景是相反的：

| 場景 | 決定性的意義 | 判定 |
|---|---|---|
| 補值 | 各機器算出同一個答案 | **特性**——否則身分分岔 |
| 新建 | 同名者算出同一個答案 | **缺陷**——身分熔合，不可逆 |

所以「該不該用推導」沒有單一答案。要先問：**推導是為了補一個缺的值（migration），
還是為了決定一個新的值（identity）？** 共用一個 default 必然在其中一邊出錯。

這是本規則第 1 條（不得住 default 位置）的全部理由——**位置決定了誰會走它**，
而 default 位置的意思就是「所有沒特別說的人都走這條」。

## 與其他規則的關係

- **全域 `common-spec-prose-enumeration.md`**：本規則刻意用兩個封閉列舉，而不是
  「凡是為了相容而存在的路徑」這種總括判準。後者會在錯誤處理、可選欄位這些邊界上
  長出我沒同意的答案。
- **`lossless-intake.md`**：那條管「進來的資料不得丟」，本條管「格式改變時不留兩條
  讀法」。兩者都在防**安靜的分岔**——前者是資訊與記錄分岔，後者是行為與行為分岔。
- **`replace-endnote-and-zotero.md`**：完全取代 Zotero 意味著將來會匯入別人的
  library。兩條讀法在單機上只是技術債，在合併時會變成**資料毀損**。

## 觸發過的實例

**2026-08-12 · [#241](https://github.com/PsychQuant/Akashic-Library/issues/241)**
（同名者的最終區辨）：`id ?? forPerson(key:)` 的遷移用途已歸零（869/869 都有 id），
但它仍在 default 位置，於是每個新建的 person 都拿到 `v5(name-derived key)` 當身分。
本規則直接裁掉「保留 fallback 順便支援舊格式」這個選項——要改就把 default 換成
直接產生，legacy 補值若還需要，就搬到具名入口並附退場量測。

寫這條規則時**順手掃出第二處**：`Organization.swift:98` 有一模一樣的形狀
（2 筆 org，皆已有 id，遷移用途同樣歸零）。#241 原本只講 person——**同型缺陷成對
出現，而 issue 只記了先被看見的那一個**。這是規則第 2 條要求「寫下量測方法」的
附帶好處：為了量「還有誰在走」而寫的那條 grep，會把同型的其他處一起撈出來。

把實例留著，是因為只留結論的話，日後維護者會覺得「這條寫得囉嗦、我幫它精簡」而把
裁決力刪掉（見全域 `common-spec-prose-enumeration.md` 的第 3 條執行細節）。
