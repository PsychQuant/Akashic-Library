# 一句話變成一支守衛：#407 的 169 個 commit，以及它在自己身上找到的東西

2026-08-22 至 08-24。使用者的指令只有一句：「**不斷做直到所有問題都修完為止**」。

起點是 #407 ——「交付物裡的斷言沒有東西要求它先被量測過」。它不是某個功能壞了，是
**一整類壞法**：寫下一句可能是錯的話，然後沒有任何機制會發現它錯。這份記錄的重點不在
169 這個數字，而在**這條規則反覆在它自己的執行過程中被觸發**。

## 主線：規則長成守衛，守衛長出負控，負控長出後設檢查

`plugin/rules/assertions-must-be-measured.md` 要求「寫下一句可能是錯的話之前先回答四個
問題」。散文規則的問題是它**管不到自己**——所以這一輪的主要產出不是那份散文，是圍著它
長出來的可執行層：

| 層 | 東西 | 它問什麼 |
|---|---|---|
| 守衛 | `plugin/tests/` 的 20 支 | 交付物裡有沒有沒被量過的斷言 |
| 負控 | `audit-guards-mutations.py` 的 53 個 case | **那些守衛真的會紅嗎** |
| 後設 | 該 harness 的 2 個自檢 ＋ `oracle-precondition-control.py` | **那些負控自己有沒有壞** |

最後一層是被逼出來的。R67h 那次，一個負控**挑中了唯一測不到目標路徑的守衛**去下毒——
它跑了、印了 ✓、什麼也沒驗到。修法不是換一支守衛，是讓它**自己算該挑哪支**
（`max(counts, key=…)`）。

### 一個貫穿全程的發現：跑過的控制不等於會失敗的控制

這句話在這一輪被實測**四次**：

- **R67b**：兩個 parity case 的輸出逐字相同，於是它們互相不可區分——把守衛改壞，兩個
  一起變綠。修法是加一個**跨 case 的不變量**（`PAIRED_IDENTICAL`），不是改字串。
- **R67j**：兩個 ROBUST case 的注入打在**錯的表**上。回退修正後它們仍然綠——也就是說
  它們從來沒測到任何東西。
- **#413**：新加的不變量第一版**空轉**——兩個 case 都指向「有表的標題」，於是
  `_rows_after` 回 `int` 而 `borrowed` 分桶只收 `tuple`。回退守衛仍綠才發現。
- **#414 R1**（本批最後一輪）：一個負控 case 因為規則檔多長出一張表，從「錨不存在」
  **悄悄改走「錨在別節」**。兩條路各有 case，所以**測試計數沒變、覆蓋卻少了一格**。

唯一有效的驗證方式**只有一個**：把修正退回去，看它會不會紅。

## 第二條線：手數不準，機械謂詞才問得到 recall

#409（`wikipediaEntry` → `referenceWorkEntry`）本身是機械改名，但它的**假陳述清單**
不是。我先手數說「3 個地方寫錯」，最後是 **12 個**：

    3 個  手數
    +4    R1 跨模型審查
    +4    一個帶錨點的謂詞（issue 編號共現）
    +1    一個**不帶**錨點的謂詞

最後那個 +1 是 R2 的 DA 席逼出來的：**「重掃找到 1 個偽陽性」量的是 precision，不是
recall**。帶錨點的謂詞只找得到「提到 #409 附近」的句子，而過期的句子不一定提到它。

同型的事在 #415 又發生一次：issue 指名 `INREFERENCE` 一個缺口，實測是 **6 個**
（`AUDIO`／`DATASET`／`IMAGE`／`INREFERENCE`／`SOFTWARE`／`VIDEO`）。那是兩個 switch
的差集，相隔一百行、各自都讀得通順——**靠人比對發現不了**。修法因此不只是補五行 case，
而是把不變量寫成宣告式（`testEveryForwardBiblatexTypeSurvivesTheRoundTrip` 加一份顯式的
`deliberatelyLossy`），讓「哪些是刻意有損」變成**宣告**而非推論。

## 第三條線：#339 的兩個觸發條件成立了，而重做裁決的結果是「維持不動」

`entity-backlink-completeness` 為「work → work 的被收錄於」記了一個暫緩裁決，附兩個
可執行的觸發條件。這一輪它們都成立了（6 → 31 筆、最大共用 ×3 → ×10），於是回頭重做。

拆解那 31 筆之後，兩個門檻**幾乎完全由「參考工具書」那一群造成**——維基百科 14 筆
（zh/en 兩個變體）＋ SEP 3 筆，而真正的編著章節 14 筆是 14 個容器、每個 ×1。

使用者裁定：參考工具書的容器走 **venue**，不走新的 ref 邊。理由是 #324 自己的判準
（§11：「它決定了哪些欄位存在」）——#324 關掉的是**編著**那條路（索取
`BOOKTITLE + EDITOR + PUBLISHER`，venue 持不住），而參考工具書是持續出版的線上工具，
索取的欄位組接近 `website`／`database`。**把兩者混為一談，正是「依性質相似類推」。**

**而那個觸發條件本身量錯了東西**：它數「帶 `booktitle` 的記錄」，而 `lossless-intake`
規定來源欄位不刪——所以容器改由 venue 承載之後，那個數字**完全不會下降**（實測仍是
31）。要數的是「仍只有純量字串、沒有任何 ref 承載容器」的記錄。條件已改寫。

## 這一輪在自己身上找到的東西

按時序，全部是「我寫下一句話 → 量測否掉它」：

| 事 | 我寫的 | 量測 |
|---|---|---|
| pre-push 耗時 | 「59 秒」 | 那只涵蓋守衛。`swift test` 一支就佔 72%，端到端 **595 秒** |
| 移出那支慢守衛的效益 | 「59 → 7 秒（−88%）」 | 實測 **263 → 205 秒（−22%）**；它不是 pre-push 慢的原因 |
| #414 的納入理由 | 「沒有逐卷編者**與同義的出版社**」 | 後半為假——`VenueType` 本身就有 `.publisher`，全庫 82 筆 |
| #414 守衛的訊息 | 一律說「venue 持不住編者」 | 37 筆 `conference-session` **零筆帶 booktitle**，那個推導對整個成員沒發生 |
| `zero-instance-guards` 第 7 列 | 「前六列在前件內都**完備**」 | 對第 5、6 列為假——它們由**有限抽樣**建立，兩次跑相同證不到決定性 |
| 改名的假陳述數 | 「3 個」 | **12 個** |
| `#415` 的缺口 | issue 說 1 個 | **6 個** |

**最後一列是 issue 的斷言（#415 說 1 個），前六列是我自己寫下的。**

第 6 列容易被讀成別人的——它是我**手數**的「3 個」，而不是誰告訴我的。這一列與第 7 列的差別正是本批第二條線在講的事：手數與 issue 的敘述都會低估，而兩者都要靠機械謂詞才問得到 recall。

## 三次「守衛釘住實作位置而非性質」

同一個形狀在這一批出現三次，值得單獨記：

1. `EntityShapeLabelTests` 釘住 `migrate-work-types` 這個**已於 #325 階段二刪除**的
   命令名——於是它擋住了對那句訊息的修正（#410）。
2. `VenueTests` 斷言訊息含小寫 `venue`，而訊息分兩支之後其中一支只有大寫 `` `Venue` ``
   ——測試在一個**與它要測的性質無關**的字上紅。
3. `AuthorizedNameTests` 釘住「CLI 的 `Validate` 內文要出現 `load.organizations`」，
   而 #416 把那個走訪搬進 `StoreHealth` 之後守衛紅了——它釘的是位置，不是「機構真的
   被驗證」這個性質。

三次的修法相同：**改成斷言性質**。第三次順帶讓不變式變強（三個面都拿得到，先前只有 CLI）。

## #416：查「新守衛真的會被走到嗎」時掉出來的

#414 加完守衛之後問了一句「它會被呼叫嗎」——守衛存在 ≠ 守衛被呼叫。量測：

```
$ grep -rn "validate()" Sources/ | grep -iE "entry|entries" | grep -v '///'
Sources/akashic/Commands.swift:186:            let issues = entry.validate()
```

**全樹只有一個呼叫點**。`doctor()` 與 App 面各 0。而 `mcp-cli-parity` 對 `validate` 是
CLI-only 的裁決，理由寫著「讀取檢查由 `akashic_doctor` 覆蓋（**功能重疊**）」——那句話
被這個量測否掉：doctor 覆蓋的是**跨記錄**檢查，per-entry 一條都不做。落差裡有一條是
**error** 級（citekey 不符 pattern），而 App 是取代 Zotero 的主要 UI。

修法沿用 #263 建立的形狀：per-record 驗證是唯讀的，抽進 `StoreHealth.perRecordIssues`，
三個面各自渲染。CLI 那五個展開的迴圈因此收斂成一個——而**第一版只搬了三族**
（漏掉 organizations 與 divergences），是照著 CLI 的迴圈數才數出五族。

## 最後一件事：「這需要 X，而 X 有風險」——我驗了 X 的風險，沒驗「需要 X」

#414 的方向 1（讓 `booktitleCarrierTypes` 的成員資格由欄位契約**推導**）被我列為
「需要使用者裁決」，理由是它會製造第三張必要欄位表，而 `apa7-is-the-work-floor`
記過三張表會各自分岔。

**動手量之前先驗那個前提，它不成立。** 既有的 `requiredFields(for:)` ＋
`recommendedFields(for:)` 就能區辨——`INCOLLECTION` 的 recommended 含
`EDITOR,PUBLISHER`，兩個成員都不含。判準因此有了程式層對應物，**16/17 相符**，
不需要新表。

這是本批最後一個、也是形狀最乾淨的一次：**我引用的風險是真的，但那個風險綁在
一個我沒驗過的必要性上。** 上面那張表的六列是「**寫下的話**被量測否掉」，這一次是「**不做的理由**被量測否掉」——同一條規則的另一個方向，而它更難發現：一句沒做的事不會出現在任何交付物裡，所以沒有守衛掃得到它。

唯一的不合是有訊息的：`.conferenceSession` 的契約（`PRESENTATION`）**完全沒有
`BOOKTITLE`**，容器是 `EVENTTITLE`；與資料層互相印證（37 筆零筆帶 booktitle）。
APA7 §10.5 把「會議發表」與「論文集中的論文」併在同一節而 `WorkType` 只給一個格子
——第一筆論文集論文進來時，容器會進庫、會歸 venue，但**印不出來**。已開 #417。

## 尾聲：「零實例所以不急」被推回來做完，而其中一次做錯了

收尾時我把三件事列為「零實例、不急」。stop hook 不接受，於是逐一回去做——**結果是
兩件做完、一件做錯後還原**，而做錯的那次最有教育意義。

| | 結果 |
|---|---|
| #417 方向 2（論文集名印不出來）| ✅ 做完。`biblatexEntryType(fields:)`，實測 `.bib` **逐字相同**（37 筆無一帶 booktitle）|
| #418（venue 歸錯戶沒有退路）| ✅ 做完。`resolve-venues --repoint`，兩面同時、兩側都寫 verdict |
| #417 方向 4（把 `.conferenceSession` 移出載體表）| ❌ **做錯，兩條既有測試立刻抓到，已還原** |

**做錯那次的根因是判準裡一個看不見的錯子句。** 判準原本是
`BOOKTITLE ∧ ¬EDITOR ∧ ¬PUBLISHER`，而 `¬PUBLISHER` 與**我自己兩輪前的量測**矛盾
——出版社不是 venue 持不住的東西，它自己就是一個 venue。

它能存活兩輪，不是因為看起來對，是因為**拿掉它預測完全不變**：只有兩個型別的契約含
`BOOKTITLE`，而 `INCOLLECTION` 同時含兩個欄位，任一子句單獨都排得掉它。所以沒有任何
資料或測試碰得到它。我甚至替它編了一個理由（「PUBLISHER 排的是論文集」），而那個
「真案例」正是它會弄錯的那個。

R70 跨模型審查的診斷比我準：它**錯置**而非冗餘——`literals(for:)` 的 publisher 分支
**從不受**那個集合閘控，所以那個子句用「契約有沒有 PUBLISHER」去決定一個與 publisher
輸出無關的閘。

**一句沒被量測反駁過的話，不等於一句對的話。** 已寫成守衛
（`testEveryClauseInThePredicateIsLoadBearing`：逐一拿掉每個子句，預測都必須改變），
negative control 驗過。
