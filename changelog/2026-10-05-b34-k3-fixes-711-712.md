## #711：R3 仍在列舉「什麼算」（評審第 0、2、4 列，MEDIUM）

R3 把辨識補寬，但補法是列舉——評審在列舉之外又找到：

| 寫法 | 誰找到 | R3 |
|---|---|---|
| `akashic validate \|`、空白行（或只有 `#` 的行）、`grep -c x` | 第 0 列 | 遇到空白行就停止接續，兩半各缺一半 |
| 多行 inline code 的第二行以 `\|` 開頭（段落、清單、引用區塊裡） | 第 2 列 | 每一個以 `\|` 開頭的行都被當成表格列、切段 |
| `"${AKASHIC_BIN-akashic}"`（不帶冒號的預設值） | 第 4、20 列 | binary 的 lookbehind 與 `che-akashic` 一起排除 |
| `ggrep`／`zgrep`／`pcregrep`／`ugrep -c` | 第 4、7、12、20 列 | 計數命令只認 `[ef]?grep` |
| `rg --count-matches` | 第 4 列 | `--cou(?:nt?)?` 後面接 `-` 就失敗 |
| `\| awk 'END{print NR}'`、`\| nl \| tail -1`、`\| sed -n '$='`、`\| grep -n \| tail -n 1` | 第 12、20 列 | 不經已知的計數命令 |
| `~/bin/Akashic validate …`（macOS 不分大小寫，跑得起來） | 第 20 列 | 辨識分大小寫 |
| `` `…validate 2>&1` \| `grep -c x` ``（兩段 inline code 之間夾一個 `\|`） | 第 20 列 | 只接「只隔空白」的兩段 |

### 反過來寫：認不出時偏向「是量測」與「同一個單位」

- **計數**：binary 的輸出經管線送進**任何**命令都算計數，除了一張封閉的「已知不計數」清單（`selfProofDisplayFilters`：`head`，以及不帶計數選項的
  grep 家族）。名字以 `grep` 結尾的命令都是 grep 家族；以 `--cou` 開頭的長選項都是計數選項。不經管線的計數（`<( … )`、`;` 串接）照舊靠計數命令
  與 `wc`、`jq … length` 的辨識。
- **binary**：不分大小寫；參數展開的運算子是字邊界（`${X-akashic}` 算、`che-akashic` 不算）。
- **單位**：接續運算子之後的空白行與純註解行照接；以 `|` 開頭的行只有在 GFM 表格裡（前一行是同一層的表格列、或下一行是分隔列）才是表格列；
  兩段 inline code 之間只隔一個接續運算子時接成一個；段落最後一段 inline code 以接續運算子結尾、下一段落以 inline code 開頭時接成一個。
- **同一組判斷的其他路徑一起改**（K3b）：散文（縮排區塊、`<pre>`）跨空白行時同一把——上一個段落最後一個邏輯行與下一個段落第一個邏輯行以接續運算子
  相連就接；引用層數**變淺**不再切段（CommonMark 的 lazy continuation：引用區塊裡沒收尾的 inline code 接到下一行沒有 `>` 的那一行），加深才切。
- 誤認的方向是多紅一行（具名），漏認的方向是放行。規則檔與 doc 原本寫「認不出的寫法封閉三類」，R4 改成開放的清單（評審第 20 列）：以別名、
  複本或名字不含 akashic 的變數執行、binary 的輸出先存進變數或檔案、散文裡 binary 與計數不在同一個邏輯行、兩段 inline code 之間隔著文字。

## #711：`${STORE:?…}` 寫在管線裡停不下來（評審第 1、3、5 列 MEDIUM，第 14、15 列 LOW）→ 第 90 列

R3 把第 18、46、49、73、77 列寫成 `--library "${STORE:?…}"`，說「沒設時 shell 停下」。bash 與 zsh 實測：參數展開的錯誤只結束管線**那一段**的
子 shell，訊息走 stderr（還沒套 `2>&1`），右邊的 `grep -c`／`wc -l` 對空輸入照印 `0`——第 46、73、77 列的期望值就是 0。STORE 打錯成一個不是 store
的目錄時，`validate` 報錯而計數一樣印 0，`doctor` 還在那裡建出一個 store、改它的 `.gitignore`（評審第 15 列）。

- 模板加前置條件：`: "${V:?訊息}" && [test -f "$V/store.yaml" && ]LC_ALL=C grep -a -q … && <BIN> <參數> 2>&1 | grep -c …`。`<參數>` 用到的變數都要列在
  最前面的 `: "${V:?…}"` 裡，`--library "$V"` 另要 `test -f "$V/store.yaml"`。
- fence 與 inline code 裡的**任何**單位（不只量測——第 73 列的 `find … | wc -l` 不提 binary）把 `${V:?…}` 寫在管線裡即紅。沒有管線的簡單指令
  （`python3 - "${STORE:?…}" <<'PY'`）真的停得下來，不報。
- 五列改寫。真 binary、scratch store 實測（bash 與 zsh 各一次）：

  | STORE | 第 41、46、49、73、77 列的七條 | 第 18 列 |
  |---|---|---|
  | 沒設 | stdout 空，stderr 一句 | stdout 空 |
  | 設成一個不是 store 的目錄 | stdout 空，那個目錄沒多出任何檔 | — |
  | 設成 store | 印量測值（0／`orphaned:` 兩行） | 印 1 |

- 散文改成實話（第 19 列量測段、第 18、46、49、73 列）；`changelog/2026-10-04-b32-f7-fixes-711-712.md` 的 LOW 17 列加一句更正指向這裡。
- 第 90 列：擋它的寫法**看起來已經擋住了**，所以不能只改散文；理由與第 13 列的差別寫在該列。

## #712：「同一個拼法」比位元組（使用者 2026-10-05 裁決；評審第 10 列）

`resolve-venues` 列表的 `suppressed` 原本以 Swift `String ==`（canonical equivalence）判「壓住它的否決是不是同一個拼法」，只差 NFC／NFD 的邊被當成
「逐字被否決」，在 `candidates` 與 `suppressed` 兩邊都不出現。使用者裁決比位元組（與 `confirmedLiteral`、`byteExactKey` 一致）：

- `VenueResolver` 的被否決拼法以 UTF-8 位元組為鍵；只差 NFC／NFD 的候選列在 `suppressed`，壓住它的兩種拼法各列一次（字串相等時依位元組排序）。
- `ResolutionLedger.rejectedPairings(venues:)` 回陣列、不經 `Set<ResolutionPairing>`——`Set` 的相等也是 canonical，會把只差 NFC／NFD 的兩筆否決收成一筆。
- `VenueResolver.apply` 改寫邊之前比位元組。
- 兩面同一條路徑（`AkashicService.resolveVenues`）；CLI 的 `--help`、`akashic-verify-venue` SKILL 的第三種可能、`mcp-cli-parity` 那一格同步。MCP 描述沒改
  （「逐字相等的否決是普通已否決、不列」的「逐字」本來就讀成位元組），`tools/list` 0 位元組變動。
- 測試：resolver 單元（兩個方向、兩種拼法都被否決、ledger 不經 Set、apply）、CLI 與 MCP 真 store 各一。負控三個（`suppressed` 改回 `String ==`、
  ledger 改回經 `Set`、apply 改回 `String ==`），各自讓對應的測試變紅，反向編輯還原。
- 同一判斷的其他路徑：MCP 組合腿的 `skippedBecauseRejected` 以 id 與正規化配對判，不是「同一個拼法」的判斷；`confirmedLiteral` 本來就比位元組；
  App 沒有 venue 的解析面。person／organization 的列表沒有 `suppressed`（#721），它們的否決以正規化鍵比，不在本輪。
