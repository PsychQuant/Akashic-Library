## #584：複合運算式一律要每個運算元具名，拆不開的形狀不豁免

### 根因

`DisplaySafeExemption.names` 只取運算式的**第一個識別字**。這對單一運算元是對的，對複合運算式是洞：`idx + entry.title`、`cond ? unsafe.title : ""`、`count ?? entry.title`、`fmt(entry.title)`、`xs.map { $0.title }` 只要註記講第一個名字就整條放行；以字串字面開頭、後面接成員呼叫的運算式（`"x".appending(raw)`）更糟——尾段沒有插值也不被 `+` 切開，`allSatisfy` 對空集合為 true，**連具名都不需要**；整字比對的 lookbehind 沒排除 `.`，註記講 `entry.title` 就讓另一個值 `title` 免檢；註記標記出現在字串字面裡也被當註記。這正是 issue 的原情境（「真的未消毒的運算式與安全的運算式並排、註記只講後者」）在**單一運算式內部**的版本，首版只在「同一行的兩個運算式」層級修好。

### 改了什麼

- `Tests/AkashicKitTests/DisplaySafeExemption.swift`：`names` 重寫成**遞迴拆解**，原則是 fail-closed——認得的形狀每個帶資料的運算元各自要被具名，拆不開的一律不豁免（型別 doc 有封閉的拆解規則）。拆解的形狀：開頭關鍵字與前綴 `!`／`-`；頂層二元運算子（`??`、三元 `? :`、`+ - * / %`、比較、`&& ||`、範圍；兩側要有空白）把運算式切成運算元，`as`／`is` 的右邊是型別；括號包住的運算式與 tuple；字串字面（字面後面接尾段＝拆不開）；常量（數字、`true`／`false`／`nil`、`[]`／`[:]`、key path 字面）；鏈 `頭.成員(…)[…] { … }`（頭要具名，呼叫引數、有標籤的下標引數、尾隨閉包 body 各自是運算元；無標籤的下標引數是查找鍵、不流進結果；前導點與 `displaySafeClipOnly` 的函式名不要求具名，要具名的是載體）。整字比對的 lookbehind 加上 `.`。`notes(in:)` 只認**註解裡**的標記（用 `strippingLineComments` 的引號感知判定註解起點）。

### 誠實邊界

- 粒度仍是**運算元的頭識別字**，不是成員路徑：同一行（或同一個運算元裡）的 `entry.citekey` 與 `entry.title` 共用 `entry`。`testKnownBoundaryMembersOfTheSameObjectShareAnExemption` 仍釘著這個邊界。
- **無標籤的下標引數視為查找鍵、不要求具名**（`counts[lib.key]`）。對標準的字典／陣列下標這是對的；一個自訂的 `subscript` 若把引數原樣回傳，這個邊界看不到。有標籤的（`default:`）會檢查。
- 運算子要有空白；`a+b` 不認得、一律不豁免（191 條裡沒有依賴它的）。閉包的 `params in` 只用一條正規表達式拆，認不得的形狀整段當 body（fail-closed：多出來的識別字要具名）。
- 同族的另外幾個守衛仍是行級（`testErrorToTextEntriesGoThroughTheSingleEntryPoint`、`testSanitizedCarrierSinksOnlyClip`、`InvisibleEscapeCoverageTests`），只認 `contains("display-safe-exempt:")`，字串字面裡的標記在那三處仍算數；首版 changelog 已載明，本輪沒動。
- 這條規則是**文字啟發式**，對資料流仍是盲的：註記說「已消毒」，守衛只確認註記具名了那個運算式，不確認它真的已消毒。那 191 條註記的斷言沒有機械檢查（其中 22 條這輪逐條看過，其餘依形狀分桶加抽查）。
