## 1. #700 MEDIUM：「區塊已在」要與 git 的判讀一致

**問題**：`hasRuleLine` 先把一行前後的空白、tab 與任意個 CR 剝掉再比對 `sourcesRuleLines`。git 不剝行首的空白與 tab（`  sources/` 對 git 是「以兩個空白
開頭的名字」），行尾只去一個 CR（緊接換行或檔尾）與空格、不去 tab。這種 `.gitignore` 被判成「區塊已在」：`doctor` 不出聲、`file add` 照常成功、兩個匯入
不警告，而 `sources/` 沒被排除。同一個問題的另一個形狀（b36 verify devils-advocate 第 22 列）：`.gitignore` 是 symlink、指向的檔有區塊時同樣判成已在，而 git
2.32 起不讀工作樹裡 symlink 的 `.gitignore`。

**實測**（git 2.55，2026-10-09，`git check-ignore -q sources/x`）：`sources/`、`sources/ `、`sources/  `、`sources/\r`、`sources/ \r`、`/sources/**  ` 排除；
`  sources/`、`\tsources/`、`sources/\t`、`sources/\r `、`sources/\r\r`、`sources/\ ` 不排除；symlink 的 `.gitignore` 印 `warning: unable to access
'.gitignore': Too many levels of symbolic links`、不排除。

**修正**：

- `hasRuleLine` 照 git 的切法：行尾一個 CR 先去，再去行尾的空格；行首不動、tab 不動。git 不去反斜線跳脫的行尾空格，這裡一律去——差別只在含反斜線的行，
  而 `sourcesRuleLines` 沒有一個含反斜線，判讀相同（寫在 doc）。
- `inspectSourcesIgnoreOnce`：`.gitignore` 是 symlink（指向一般檔）時一律 `.symlink`，不論指向的內容有沒有區塊。`.symlink` 的原因與處置改寫：git 不讀它，
  處置是把 symlink 換成一般檔（先前叫人「在它指向的檔加上這段」——加了也不生效）。`brokenSymlink` 的處置同樣拿掉「修好它指向的檔」。
- warning 與 `file add` 拒絕的首句改成「沒有**生效的** sources 排除區塊」：symlink、大到 git 不讀的檔裡可能有區塊，只是不生效（LOW 13 一併）。
- `markerWithoutRule` 的原因說出 git 不認行首帶空白或 tab、行尾帶 tab 的 `sources/`，處置叫人補「頂格的」那一行。
- `store-source` 的拒絕訊息（`assertSourcesExcluded`）：補「頂格」、symlink 的 `.gitignore` git 不讀、規則行帶行首空白時 doctor 不改。

**同一個判斷的其他路徑**（逐一查過）：`judgeSourcesIgnore` 只有 `hasRuleLine` 一份比對，先看（`inspectSourcesIgnoreOnce`）與鎖內重看（`appendSourcesIgnoreUnderLock`）
共用它；鎖內重看以 `O_NOFOLLOW` 開檔，symlink 走 `ELOOP` → 重看 → `.symlink`。`file add`（`.refuse`）、`doctor`、CLI `import-zotero`、MCP 兩個匯入（`.report`）
都經 `ensureLayout`；CLI `import-wos` 開既有 store、不經它（有記錄的差異不變）。量測文件第 87 列的 Python 腳本是同一個判斷的第二份——改成同一個切法（`cut`），
說明改成 symlink 不論有沒有區塊都會被拒／報。live store 重量：`main 913 file utf8 block writable`（不變）。

**測試**：

- `GitignorePreservationCLITests.testRuleLinesAreCutTheWayGitCutsThem`（單元）：上面兩組形狀加檔尾沒有換行的一行。
- `GitignorePreservationCLITests.testThePresentJudgementAgreesWithGitCheckIgnore`：13 種規則行（含 `!sources/`）加 symlink 指向有區塊的檔、硬連結，每一種在暫存的
  git repo 裡以 `git check-ignore` 對照，要求 `inspectSourcesIgnore() == .present` 若且唯若 git 排除。git 的環境剝掉 `GIT_*`、`GIT_CONFIG_NOSYSTEM=1`、
  `GIT_CONFIG_GLOBAL=/dev/null`、`HOME` 指暫存目錄（使用者的全域 excludes 會讓 `sources/` 被別的規則排除）。
- `testAMarkerWithoutTheRuleIsNotTreatedAsPresent`：先前列為「已在」的 `"  sources  \n"` 翻轉；`"\tsources/"`、`"sources/\t"`、`"sources/\r "` 同為不在——
  `file add` 拒絕、`doctor` 報；`sources  `、`sources/ \r\n` 仍算已在。
- `testUTF8GitignoreGetsTheBlockAppendedAfterItsOwnBytes` 的後半：symlink 指向有區塊的檔，`file add` 改為拒絕（訊息說 git 不讀、不再叫人加在指向的檔）、`doctor` 報；
  symlink 與它指向的檔不動。

**負控**（反向編輯還原）：`hasRuleLine` 改回剝前後空白、tab 與 CR → 上面三支紅（3 支、23 則）。symlink 那一格與 WebRead 的 LOW 一起做（見第 3 節的合併負控）。

## 2. #692 MEDIUM：〈開始前〉的 CLI 探測分不出 b35 之前的 binary

**問題**（Codex 與 logic 兩席）：探測只呼叫 `web-read origin` 與 `url`（b34 加的），b34 的 binary 全部通過，而它的 `check` 照 b35 之前的契約——停在已知驗證服務上、
文字沒有訊號的讀取印 `READ-OK`、以 0 結束並寫出文字。讀取區塊之後沒有別的文字檢查，會把驗證服務的頁面當內容讀、照常導航到下一頁。

**修正**：web-access.md〈開始前〉第 4 點多一條真呼叫——before／after 都是 `https://challenges.cloudflare.com`、`--landing -`、raw JSON 是一段沒有訊號的文字，
要求 `web-read check` 以 2 結束而且沒有寫出文字檔；不符合就停、說 CLI 太舊。說明那一段寫出為什麼（b34 的 binary 過得了前面幾條）。verify-venue SKILL 沒有自己的
一份探測（它引用 web-access.md），`plugins/akashic-discovery` 沒有 `web-read`。

**測試**（`WebAccessReadContractTests`，從文件抽出區塊實跑）：`testTheStartProbePassesWithTheCurrentCLI`（真 binary 過得了整個探測）；
`testTheStartProbeStopsACLIWithTheOldCheckContract`（替身 `akashic`：`web-read check` 照舊契約寫出文字、印 `READ-OK`、以 0 結束，其餘轉給真 binary——探測以 1 停下、
說出原因）。區塊抽取改成認得清單項目裡縮排的圍欄（〈開始前〉的區塊縮排三格）。

**負控**：探測的判定改成 `true ||` → `testTheStartProbeStopsACLIWithTheOldCheckContract` 紅；還原後與 b37 修正前的文件逐位元組相同（`cmp`）。
