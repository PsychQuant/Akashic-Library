# 為什麼一個 700 bytes 的檔案能把程式卡住 43 秒

> 這份文件是**解釋**，不是規格。規格在 [`../store-format.md`](../store-format.md) §5。
> 追蹤紀錄在 [#36](https://github.com/PsychQuant/Akashic-Library/issues/36) /
> [#27](https://github.com/PsychQuant/Akashic-Library/issues/27) /
> [#52](https://github.com/PsychQuant/Akashic-Library/issues/52)。

## 一分鐘版

一張紙寫食譜：

```
配方A：9 顆餅乾
配方B：做 9 份「配方A」        → 81 顆
配方C：做 9 份「配方B」        → 729 顆
…寫 8 行…
配方H：                        → 4300 萬顆
```

**紙只有 8 行。讀完 = 0.001 秒。**

但如果有人問「這總共幾顆？」—— 得**真的一顆一顆數** = **43 秒**。

YAML 有這個「取名 + 引用」的語法（`&名字` 定義、`*名字` 引用），所以上面那張紙是
一個合法的 YAML 檔，700 bytes。

## 程式什麼時候會去數？

**只有當這東西被拿來當「標籤」的時候。**

YAML 規定同一份資料裡標籤不能重複。所以程式看到一個標籤就得問「這個跟前面那個一樣
嗎？」—— 要回答，就得把整個 4300 萬顆看過一遍。

當它只是「內容」，程式從不去數，放著就好。

```yaml
zz: *配方H      # 當內容 → 0.001 秒
*配方H: 1       # 當標籤 → 43 秒
```

**43,000 倍。同一張紙，只差它在冒號的左邊還是右邊。**

## 技術版

<details>
<summary>展開</summary>

`Yams.compose` 建完一個 mapping 之後檢查重複鍵：

```swift
// Yams/Parser.swift:398
let duplicates = Dictionary(grouping: mappingKeys) { $0 }.filter { $1.count > 1 }
```

`Dictionary(grouping:)` 要把每個 key 放進雜湊桶 → 必須算 `hashValue`。而
`enum Node: Hashable` 的合成 `hash(into:)` 是**結構性的**：走訪每一個葉節點。

**COW 讓「複製」免費，但 hash 不能取巧** —— 兩棵結構相同的樹必須算出相同的 hash，
而判斷相同就得看過全部內容。9 個 `*a7` 在記憶體裡是同一份 storage，但 hash 無從知道。

value 位置的節點從來不需要 hash，因為 mapping 只對 key 做重複檢查。

</details>

## 我會遇到嗎？

**幾乎不會。** 實測的威脅模型：

| | |
|---|---|
| store 位置 | `~/.akashic`（**不在** Dropbox / iCloud 同步樹）|
| remote | private，協作者 **1 人** |
| 真實 536 個檔案 | **0 個 anchor、0 個 alias**（用真 parser 掃過）|
| 寫入端 | 只有 Yams emitter，**從不產生** anchor/alias |

所有實際入口（`import-zotero`、`import-wos`、App、MCP）都經過 emitter。剩下兩條路：

1. 自己手寫一個放進 `entities/` —— 自傷
2. 從別台機器 pull 到被污染的 commit —— 但 remote 是 private、只有你能推

## 那為什麼還是修了

三個理由，只有第三個是強的：

1. 它是 **pre-existing** 的。發現了就得決定「修」或「**明確地**不修」，不能知道了還放著。
2. 成本是零：`validate` 536 筆 0.32 秒，加守衛前後沒有可測差異。
3. **第 6 版擋掉的是 SIGSEGV，不只是慢。** 那個失敗**不可 quarantine** —— Swift 的
   `catch` 抓不到，一個檔案會讓三個 consumer 每次載入都直接死。嚴重度與發生機率無關。

## 修了七次，每次錯在哪

| 輪次 | 我測的量 | 危險的量 |
|---|---|---|
| R5 / R6 | 行尾字元 | block scalar 的內容 |
| R10 / R11 | `? ` 的**位置** | compose 內部的展開 |
| PR #42 | anchor 數 × alias 數 | 實際放大量 |
| PR #49 | **語法**巢狀深度 | **alias 展開**深度 |
| PR #51 v1 | 展開深度（對）| 子樹大小漏算一層 → 84 倍低估 |

**共同形態：測的量 ≠ 危險的量。** 像是檢查行李重不重，卻只量長寬高。

R11 的直覺其實是**對的**（位置確實是關鍵，見上面），但用**文字**去判位置必然失敗
—— `*a: 1` / `{? *a : 1}` / `{*a: 1}` 是同一件事的三種寫法。

PR #49 的失敗最值得記：那個攻擊**語法上完全是平的**，每行都是深度 1，深度是靠引用
一層層堆出來的：

```yaml
root: &a0 x
k1: &a1 [*a0]
k2: &a2 [*a1]
…8000 層…
? *a8000
: 1
```

180 KB、語法深度 **2** → 守衛完全放行 → `akashic validate` 直接 **SIGSEGV**。

## 現在怎麼防的

**在 parser 的 event 層估計展開成本。** `yaml_parser_parse` **不展開 alias**（每個
alias 就是一個 event），所以掃描成本與**輸入大小**成正比。

關鍵是：**這裡不需要重現任何 YAML 詞法** —— 那正是前五次失敗的來源（引號跨行、
flow collection、CRLF、註解起始條件，每個細節都是一個獨立破口）。

四個獨立的軸，任一超過即拒收：

| 軸 | 上限 | 擋的是什麼 |
|---|---|---|
| 展開後**節點數**（僅在有 alias 時）| 200,000（寫入 2×）| 指數放大 |
| 展開後 **bytes** | 64 MB | **重量** —— 19,000 次引用一個 5 KB scalar 只算 38,003 節點，展開後卻是 95 MB |
| 展開後**樹深** | 512 | 語法看不到的那一種（見 PR #49）|
| 輸入 bytes | 8 MB | 單一超大節點 |

**守衛不需要知道 alias 在哪裡** —— 它擋的是「展開量大」，而那是 key 位置爆炸的
**必要條件**。擋掉必要條件就夠了。

## 我可以改門檻嗎

可以，但先看實測的成本對應（約線性）：

| 展開節點 | `Yams.compose` |
|---|---|
| 11 萬 | 0.01 s |
| 480 萬 | 4.8 s |
| 4300 萬 | 43 s |

200,000 ≈ compose **0.2 秒**上限。

誤殺面（離門檻兩個數量級以上）：

| | 深度 | 節點 |
|---|---|---|
| 一般 entry | 5 | 34 |
| 45 位作者 + 40 大欄位 | — | 230 |
| 真實 corpus 最大檔 | 3 | 180 |
| #20 的 temporal person（1400 段）| 6 | 15,857 |

**改門檻前先跑 `testDocumentedMeasurementsMatchReality`** —— 它把上面這些數字釘成
斷言，文件改了而實測沒跟上就會失敗。

## 一個仍然開著的判斷

「幾乎不會遇到」（威脅模型）與「SIGSEGV 不可恢復」（嚴重度）指向相反方向。這是
**真實的張力**，這份文件刻意不下結論。

若日後決定不再維護這道守衛，正確做法是把 `store-format.md` §5 改回「已知未防護」並
附上上面的威脅模型 —— **明確的不修**，不是含糊帶過。
