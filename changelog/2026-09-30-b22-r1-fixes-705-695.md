# 2026-09-30 #705、#695 的 R1 verify 修正

R1 verify 六席（requirements、logic、security、regression、devil's advocate、Codex）對 #705 與 #695 的合併清單共 44 列。本檔記兩個 issue 的處置、每一個負控與量測。列號是那份合併清單的列號。兩個 issue 各自的 changelog 末尾有一節〈R1 verify 之後〉，只摘要，細節在這裡。

## #695：enrich 的來源欄位與 references 的形狀

### 改了什麼

- **定界符改在 Unicode scalar 上找（第 6、10 列，security、DA，MEDIUM）。** `RetrievalWriteShape.urlIssue` 用 Swift 的 `Character` 切 authority、找 `@`，而 `Character` 是 grapheme cluster：`@` 後面緊跟組合符號（U+0301）、ZWJ（U+200D）或 VS16（U+FE0F）時兩者合成一個 `Character`，`contains("@")` 為 false。DA 席以真 binary 跑 `akashic enrich --apply`，`https://user:pw@\u{0301}example.org/x` 通過檢查、帳密寫進了 store。這個函式是三個入口共用的（person、venue 的 references 與 enrich 的來源欄位），所以三個面同時失效。現在 authority 從 `unicodeScalars` 切，`@` 在 scalar 上找。帳密的檢查排在字元檢查之前，所以 ZWJ（Cf）那一格說的也是帳密，而不是「格式字元」。
- **反斜線。** `\` 刻意不當定界符：WHATWG 對 http／https 把它當成 `/`，RFC 3986 不認它。不當定界符時，第一個 `/`、`?`、`#` 之前的任何 `@` 都算帳密，是兩種解析的聯集。主機部分出現 `\` 直接拒絕，不讓 store 留一個兩種解析器讀出不同主機的網址。
- **控制字元、格式字元、空白（第 19 列，security，LOW）。** url 整串拒絕危險 scalar 與任何空白（RFC 3986 不收空白，要編成 `%20`）。media type 拒絕危險 scalar 與前後空白，內部空白照收（`text/html; charset=utf-8`）。「危險 scalar」用輸出閘的同一份性質 `UnsafeToEmitScalar.contains`（Cc、Cf、Zl、Zp、非 U+0020 的 Zs、Default_Ignorable、私用區、渲染成空白的碼位），不另寫清單。retrieved 的文法本來就逐位元組比到結尾，NUL、換行、空白都過不了，這一輪只加測試釘住。`firstIssue` 多一個 `mediaType` 參數，`Names` 多一個 `mediaType` 名稱，兩個呼叫點同批改。拒絕訊息不回顯原值。
- **retrieved 的訊息（第 28 列，只改訊息）。** `+0800` 先前就被拒，訊息只寫 `±HH:MM`。現在直接說「偏移要帶冒號：+08:00，不收 +0800」。
- **enrich 的離線出路（第 18 列）。** 補救句連 `sourceMediaType` 一起點名：digest 加 media type 的提案會被要求 status。
- **文件（第 38 列，以及「一份契約」的措辭）。** `plugin/CHANGELOG.md` 的 #674 一節那句「enrich 沒有跟著收緊（#695，待裁決）」原句不改，後面加上日期與指向 #695 一節的說明；#695 一節補上這一輪多拒的輸入。`mcp-cli-parity` 三列的 #695 註記補上兩件事：共用的是一個形狀函式，「擷取不齊」的判定兩面刻意不同；venue 列那句「被拒的輸入不變」在這一輪之後不成立。`docs/store-format.md` 兩處補上字元規則。MCP 工具描述沒有加字：tools/list 離預算只剩三百位元組左右，拒絕訊息自己說出是哪一種字元。

### 「一份寫入契約」的實況（第 9、14、25、34 列，沒有改行為）

共用的是**形狀**：status 範圍、url、retrieved、media type 的字元與文法，兩面呼叫同一個函式、說同一句話。「這筆算不算擷取型、要不要 status」由兩個面各自判定，**刻意不同**：

| 形狀 | references（person／venue） | enrich 的來源欄位 |
|---|---|---|
| 給了 status，缺 url 或 retrieved | 拒絕（平面 init 要四欄） | 值照補、reference 不寫、理由進 `provenanceSkipped`（#542 R2） |
| 只給內容 digest | `content` 單獨出現也要 status | `sourceDigest` 單獨給是回顯，不觸發 status（#517） |
| media type 加 digest | 要 status | 要 status（第 18、32 列：比裁決點名的三個鍵多一個；與 references 對齊，是實作的選擇，待使用者確認） |
| status 超出 100–599，沒有 url／retrieved | 拒絕 | 拒絕（範圍檢查在「要不要 status」之前；第 34 列指出裁決描述的「值照補」對這一格不成立） |

理由是兩面的輸入不同：enrich 的來源欄位是補值的附帶資訊，摘要提案只帶 digest；references 的每一筆就是那份記錄本身。兩份判準住在兩個呼叫端，是日後最可能再分岔的地方。要合成一份得先裁「enrich 對不齊的來源也拒絕」，那會拿掉 `provenanceSkipped` 這個出口，不在這一輪。

### 誠實邊界（#695，這一輪新增）

- **不驗日曆（第 28 列）。** `2026-02-31`、`2099-12-31`、`0000-01-01` 都通過：`ISO8601Prefix` 刻意不驗日曆（它也管出版日期，歷史資料裡有這種寫法），retrieved 沿用同一個。擷取時刻一定是真實的近期時刻，理論上可以更嚴；`ISO8601Prefix` 這一輪沒有動。
- **錯誤的先後與回顯（第 26 列）。** 來源形狀的檢查在 citekey／doi 之前，兩種錯同時在時先報來源形狀。`sourceRetrieved` 的原字串（至多 80 個 scalar）進 `InputError` 的理由，靠消費端在擲出站點逃一次；目前三個消費端（service、CLI、MCP）都逃。`AddOnlyEnrichment.plan` 是 public API，日後不逃的消費端會把控制字元帶到終端。
- **不相容的收緊（第 9、27 列）。** enrich 缺 status 整批拒絕、person 的 `references: []` 從 no-op 改成拒絕，都是使用者的裁決，`plugin/CHANGELOG.md` 已列。本 repo 內沒有會被拒的既有呼叫端；repo 外的呼叫端與舊版 skill 文字看不到。
- **IDN 主機裡的 ZWJ／ZWNJ。** IDNA2008 在少數文字的標籤裡允許它們；url 整串拒絕 Cf 會擋下這種主機。上一輪的唯讀量測說 live store 的 33 筆擷取型 url 全是 https、沒有帳密；這一輪沒有重讀 live store，新的字元規則對既有記錄的影響沒有量。
- **只在寫入面。** 載入既有記錄仍走 `ProvenanceReference.init`，不驗這些字元規則，收緊寫入不會讓既有記錄讀不進來。

## #705：寫了、legacy 拷貝沒刪掉的那一筆

### 改了什麼

- **rename、rename-person 刪舊鍵 legacy 檔那一步走同一個搬移刪除（第 4、11 列，logic、DA，MEDIUM）。** 兩個函式寫完新鍵那一份之後，自己用 `FileManager.default.removeItem` 刪舊鍵的 legacy 檔（`LibraryStore.swift` 的 `renameEntry` 與 `renamePerson`），沒有經過 `removeMovedLegacy`。DA 席在唯讀目錄上實跑：兩個命令都只印 Foundation 的 `couldn’t be removed`、rc=1、沒有 `writtenWithLegacyCopy`；磁碟上新鍵已寫進 `entities/`、舊鍵 legacy 檔還在，引用它的 work、verdict、歧異記錄、library 規則都沒改寫。#705 的寫入者表與 `mcp-cli-parity` 的 #705 段都說這兩個命令「由進入點的範圍涵蓋」，那句話對它們是假的。現在那一步呼叫 `removeMovedLegacy`：範圍內記下、繼續改寫其餘引用，改名做完；已經不在的算成功；範圍外（App 的改名）擲「已寫入……」的 `legacyCopyNotRemoved`，不再是原始錯誤——App 仍會在那裡中止，但訊息說出它寫了。報告具名的是這筆記錄**現在**的鍵，legacy 檔是舊鍵那一份。work 的附記分兩種：一般的寫入兩份共用 citekey（原句不變）；改名時 legacy 那份是舊 citekey，附記改說「兩份共用同一個 id——legacy 那份是改名前的 citekey」（index 的 entries 表以 uuid 為主鍵，同樣撞重複）。兩份文件同批更正。
- **`akashic_import_zotero` 的 rebuild 失敗時，報告不再被錯誤出口截掉（第 1 列，Codex，MEDIUM）。** importer 自己的範圍收下、放進 `ImportReport`；之後 index rebuild 失敗，服務把整份 payload 嵌進錯誤訊息，而 MCP 的錯誤出口有 200 行／96 KB 的上限。pretty JSON 裡每筆佔七行，三十筆左右就開始被截。分派的範圍什麼都沒收到，補不回來。現在服務在丟錯之前以新的 `LegacyCopyLedger.handToEnclosingScope` 把那幾筆交給外層範圍，並從嵌進去的 payload 拿掉；分派在格式化錯誤之後把人可讀報告放在回應最前面、不截。成功時照舊只在 JSON 的鍵裡，不報兩次。沒有外層範圍的直接呼叫端沒有人可交，照舊帶在 payload 裡。
- **錯誤回應把報告放在最前面（第 5 列，logic，MEDIUM，部分）。** `reportingWrittenWithLegacyCopy` 對錯誤回應改成「報告、空一行、原本的錯誤」。先前附在末尾：收到 isError 的呼叫端先讀到 `UNIQUE constraint failed`，很可能重試，而兩份並存時重試會被 #631 拒絕。13 個工具共用的說明句 `legacyCopyNote` 從「錯誤時附在訊息末」改成「錯誤時列在訊息前」，字數相同。CLI 本來就把報告印在錯誤之前（stdout 先、stderr 後），不動。**沒有做的一半**：讓 index 容忍兩份並存、work 的寫入因此回成功，是另一個設計問題，由 orchestrator 另開 issue。
- **成功回應已帶這個鍵時併進同一個陣列（第 15 列，logic，LOW）。** 先前條件是「鍵不存在才加」，鍵已在（`akashic_import_zotero` 的 payload）時落到「附文字」那一格，合法的 JSON 變成 JSON 加一段文字。現在併進既有陣列、依 (kind, key) 重排，回應仍是一份 JSON。同名鍵卻不是陣列（不是這個函式寫的形狀）時不覆寫它，照舊附文字。今天不可達（importer 在 run 之外不寫 entry），是防禦性的。
- **沒有外層範圍時，失敗不帶走收到的那幾筆（第 17、22、30、36 列）。** `collecting` 在沒有外層、body 擲錯時把收到的原樣回傳，而 `ZoteroImporter.run` 與 CLI 的 `LegacyCopyReport.payload` 都寫 `try result.get()`，失敗時直接擲出、收到的就丟了。現在兩處改呼叫新的 `LegacyCopyLedger.get(_:written:)`：成功回結果；失敗時收到的若已轉交外層（`written` 是空的）原樣擲原本的錯誤，否則擲 `LegacyCopyLeftBeforeFailure`——`underlying` 是原本的錯誤，描述先列報告、再列錯誤。CLI 進入點與 MCP 分派是最外層，自己處理 `written`，錯誤型別與結束碼不變；分派那個「只為型別完整」的 `.failure` 分支也把收到的帶上。`collecting` 的 doc 改寫成實況。新的 struct 進 `SanitizationBoundaryTests` 的 conformer 封閉清單，理由寫在那一列。

- **第 12、16 列（「同一趟稍早已寫入這一筆」只有 importer 會說）**：其他多階段寫入者對同一筆的第二次寫入仍給泛用的「兩份並存」拒絕。DA 實測 resolve_people 的 reject＋apply 同呼叫時 apply 腿被既有的 unlocatable 閘具名拒絕，回應帶頂層 `writtenWithLegacyCopy`，不是新的錯亂。
- **第 13 列（13 個工具的說明句名單是手寫的）**：沒有加推導式的測試。程式裡沒有「會寫既有 work／person 的 MCP 工具」這個分類：`WriteGateRulings` 是 CLI 葉命令的閘裁決，「寫 store」的集合比這個分類大（`add_venue`、`update_venue`、`record_divergence`、`dismiss_divergence`、`store_source`、`add_person`、`create_entry`、`add_organization` 都寫 store，卻不寫既有的 work／person 或只建新記錄），MCP 工具與 CLI 命令的對應只寫在 `mcp-cli-parity` 的表裡。推導出來的名單要嘛要求在說錯話的工具上加這句，要嘛需要一份手寫的排除清單——那就是把同一份手寫名單換個地方。changelog 那句「新的寫入工具不必記得接它」只對行為成立，對說明句不成立：新的寫入工具要記得加 `legacyCopyNote` 並加進 `testWriterToolDescriptionsNameWrittenWithLegacyCopy` 的名單。
