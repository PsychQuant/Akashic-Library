# 2026-10-09 名字分類修正輪四：報告裡的 attested 有上限、update-person 對同 key 兩筆拒絕、MCP 屬性說明改成實話、合併的結論不取決於 key 拼法（#564）

`changelog/2026-10-05-b34-k1-fixes-564.md`（修正輪三）之後的 verify（b36 Y1，六席：requirements、logic、security、regression、devils-advocate、Codex）找到 4 個 MEDIUM、12 個 LOW、8 個 INFO（devils-advocate 席把其中兩則 MEDIUM 校正為 LOW）。使用者 2026-10-05（05:18Z）對修正輪三留下的三項已經裁了（對外形整個離開 names 拒絕——維持現狀；organization `remove_names` 的 `segments` 少列——不加回應鍵；`--edit-name-segment`——維持一條腿、裁決表註明只閘 remove），這一輪照裁決收尾。依 findings 檔的 0 起算列號引用。

## MEDIUM

### 報告裡一段名字的 attested 沒有上限（第 0、1 列；LOW 第 13 列同源）

b34 把 organization `remove_names` 報告的 `segments` 截在 20 段，零實例表第 96 列也寫「段數與每段的 attested 項數都不封頂」——修好的只有前一半。`nameSegmentFieldsDict` 照樣把每段的 attested 整列迴送；logic 席用真 binary 造了一段 20,000 個觀測點，一次 `update-organization --remove-name` 回 460,506 位元組（DA 席 60,000 個回 1,380,503）。同一個函式也被 venue `edit_name_segment` 的 before／after 與讀取面 `akashic_venue` 用。

處置：

- **報告截、讀取面全列**：`nameSegmentFieldsDict` 多一個 `attestedCap`。報告（organization `remove_names` 的 `segments`、venue `edit_name_segment` 的 before／after）傳 `nameSegmentAttestedListedCap`（20，同 `segmentsListedCap`），超過時陣列最後一項是「…另 N 個觀測點未列出（共 M 個）」——**不新增回應鍵**（`cappedCitekeys` 的同形；使用者 2026-10-05 對 `segments` 少列裁「不加」，同一個取捨）。讀取面傳 nil、全列：它呈現的是記錄本身，`match.attested` 要逐項相同，列不全就拼不出 match；person 讀取面的隸屬段也是全列。被刪或被改的段的完整內容在 git 的上一版，報告只是索引。
- organization 的段改成 lazy：只為列出的那幾段建報告（Codex 席的次要一點）。
- 真 binary 同一個形（一段 20,000 個觀測點、`update-organization --remove-name`）：**1,095 位元組**（b36 那一席在 b089dc73 量的是 460,506）。
- 零實例表第 96 列補記、量測腳本改成兩軸都量（organization 與 venue 的名字段；2026-10-09 唯讀量測 live store：organization 13、venue 485、同一個名字最多 1 段、一段最多 0 個觀測點）。

### `update-person --fields` 對同 key 兩筆的 person 寫進先載入的那一筆（第 2 列；LOW 第 14 列同源）

`updatePerson` 的 `fields` 路徑直接 `load.people.first(where:)`，沒查 `unlocatablePersonKeys`；同一個命令的 `--remove-name`、organization、venue 的寫入面都查了。security 席真 binary：手造兩筆 key 都是 `dup` 的 person，`--remove-name` 被拒，`--fields` 的 names 附 `--judgement` 寫了 `judgementsRecorded: 1`、落在任意一份；`--fields '{"note":"x"}'` 也一樣。DA 席校正：不是名字分類專屬、也不是 b34 引入，是 `fields` 路徑整體缺這一道。

處置：在讀 store 之後、找記錄之前補上一道：兩筆**不同**的 person（id 不同）共用這個 key 就拒絕——在乾跑與實跑分岔之前，所以乾跑同樣拒絕。CLI 與 MCP 都走 `updatePerson`，一處修好兩面。

**為什麼不照 `remove_names` 問涵蓋更廣的 `unlocatablePersonKeys`、也不問 `duplicatedPersonKeys`**：第一版照抄了前者，全套測試抓到 `WrittenWithLegacyCopyR2Tests.testASecondWriterInTheSameScopeSaysTheEarlierStepWrote` 變紅——那個集合另收「load 判定那筆的檔寫入時會被拒」（#641），而 #705 刻意讓同一個操作裡的第二次 `update_person` 走到寫入當下的 #631 前置：那一道拒絕說出「同一個操作稍早已寫入這一筆」，並把稍早那一筆標成之後的寫入沒套用（`laterWriteRefused`）。load 時的那一道是給多檔寫入者在第一次寫入之前擋撕裂的（`unlocatablePersonKeys` 的 doc 寫的就是多檔寫入者）；這裡只寫一個檔，寫入當下的拒絕同樣零寫入、訊息更準。第二版改問 `duplicatedPersonKeys`，同一支測試照樣紅：同一筆記錄的 legacy 拷貝與 entities/ 那份在 load 裡是兩筆同 key、同 id 的記錄，也算重複——`crossRecordIssues` 對它報 warning 不報 error，正是因為那是同一筆。兩筆不同的記錄共用 key（id 不同）則寫入當下擋不到（兩筆各有自己的檔），所以只有這一類要在 load 之後問，判準與 `crossRecordIssues` 的 error 那一支相同。`remove_names` 仍問整個集合（b34 的契約，這一輪不動）；兩條腿的差別記在這裡。

### MCP `akashic_update_person` 的 `judgement` 屬性說明與裁決 2 矛盾（第 3 列）

b34 改了工具描述（「只替進出的名字寫指定／撤回」），inputSchema 的 `judgement` 屬性仍寫「動到 authorized 時必填；仍是對外形的寫確認」。只讀屬性說明的 LLM 呼叫端會以為附理由能替沒動的名字留確認，實際上那種呼叫被拒。

處置：改成「fields.names 的理由（名字進出 authorized 時必填，否則拒收）」——同時把第 4 列那個比裁決嚴的拒絕寫進 MCP 面。新增 `NameClassificationSchemaTextTests`：走**真 binary** 的 `tools/list`，釘住 `judgement` 要說出「進出、必填、拒收」，`judgement` 與工具描述都不得宣稱會寫「確認」。
