## 1. 第三條放置路整條拿掉（finding 0 HIGH、1／3／4／5／6 MEDIUM、12／14 LOW）

**成立，而且是同一個根因。** R2 的第三條（exFAT、FAT32 上唯一能走的路：以 `O_CREAT | O_EXCL` 建立目的檔、逐塊複製、同步、讀回驗證）靠
`fstat` 在建立**當下**取的 `(device, inode)` 認「自己的檔」。本輪在真的 exFAT 磁碟映像（macOS 27，FSKit 掛載）上量：

| | exFAT | APFS（對照） |
|---|---|---|
| 新建空檔的 inode | 18446744073709551612 | 957824580 |
| 寫入一個位元組之後 | **9** | 957824580 |
| `VOL_CAP_FMT_HARDLINKS` ／ `VOL_CAP_INT_RENAME_EXCL`（`getattrlist`） | 兩者都是**有效旗標、值為 0** | 兩者皆 1 |
| `renamex_np(RENAME_EXCL)`、`link(2)` | 都回 `ENOTSUP`（errno 45） | 成功 |

inode 一變，`removeOurs`、完成之後的 `lstat` 比對、`InFlightSourceFiles` 的訊號清理全部比不上：失敗（ENOSPC、讀回驗證不符、同步失敗）與 SIGINT／SIGTERM
都留下半截檔在內容位址上，之後的 `store-source` 以大小不符拒絕、doctor 只說「孤兒 blob」；讀回驗證抓到的壞檔還會讓下一次存檔把它當成「已經在了」並記 index；
而每一次成功的存檔都被報成 `bytesWritten:false`（finding 12、14）。第三條還讓未完成的檔在最終檔名下看得到，同時進來的存檔會把大小相同的半截檔當成「已經在了」
並寫 index，之後原作者的清理把它收回（finding 1）；它也把 exFAT 上要的剩餘空間加倍（暫存檔加目的檔，finding 6）。

**修法**（`SourcePlacement.swift`、`SourceStore.swift`）：

- `placeTemporaryBlob` 只剩兩條，都是**原子、排他**的動作：`renamex_np(RENAME_EXCL)`，檔案系統不支援時 `link(2)`＋刪暫存名。兩個都不支援就是
  `unsupportedVolumeError`——具名拒絕：「sources/ 所在的檔案系統做不到不覆寫的原子放置（…；exFAT、FAT32 即此類）——沒有存任何東西。把 store 放在 APFS 或 HFS+ 的磁碟區上」。
  `createExclusive`、`writeChunk`、`unlinkIfSameFile`、`BlobPlacement` 的對應接縫與第三條整段刪除。
- **在建立任何檔案之前就拒絕**：`LibraryStore.volumeSupportsExclusivePlacement(at:)` 讀磁碟區的能力旗標（`getattrlist`、`ATTR_VOL_CAPABILITIES`）：兩個旗標都有效而都為 0 才回 `false`
  （`RENAME_EXCL` 或 hard link 任一個有就是 `true`；旗標無效或查不到是 `nil`，不擋）。`storeSource` 的第一步與 `preflightStoreSource`（批次前置檢查）都問它，
  所以分片目錄、暫存檔、blob、index 一個都不建；位址上已經有同一份內容也一樣拒絕（「每一次存檔」，不因為「已經在了」而放行）。~~磁碟區沒有回報能力旗標（`nil`）時，
  走到放置那一步才發現兩個呼叫都回「不支援」——暫存檔由 `defer` 以名字刪掉、同一句拒絕。~~（b29 V5 MEDIUM 0：旗標讀不到時，位址上已有同一份內容的存檔不走放置，
  那一支回成功、缺條目時還補 index——「每一次」在那裡不成立。現在寫入之前、任何分支之前實際放一次，見 `2026-10-02-b29-h5-fixes-703-700.md`。）
- **「大小相同就算已經在了」不會讀到進行中的檔**（finding 1）：位址上的名字只經上面兩個原子動作出現，那一刻內容已經寫完、同步過；失敗與訊號的清理刪的只有暫存名，
  從不刪位址上的檔。所以窗口在構造上就不存在。證據是測試而不是論證：`testTheAddressOnlyAppearsInOneAtomicStepWithTheCompleteContent`（放置之前位址上沒有東西、暫存檔已是完整大小）、
  `testAConcurrentStoreThatPlacedFirstKeepsItsBlob`（B 在 A 的放置之前先放好同一份：A 以 `EEXIST` 當成已經在了，位址上的檔一個位元組沒動）、
  `testPollingTheAddressNeverSeesAPartialFile`（存 12 MiB 的檔時另一個執行緒不停地 `lstat` 位址：看過的大小只有完整大小）。負控：存檔寫出暫存檔之後、放置之前先在位址上建一個空檔（第三條的形狀）→ 前兩支紅。
- finding 6（空間加倍）：第三條沒了，兩份的需求隨它消失；`RENAME_EXCL`／`link` 路只要一份。

**真的 exFAT 映像上跑真 binary**（2026-10-02，scratch 的 `AKASHIC_HOME`）：`store-source` 一個 3 MB 的檔到 exFAT 上的 store →
`Error: sources/ 存檔 無效：sources/ 所在的檔案系統做不到不覆寫的原子放置（磁碟區回報不支援 RENAME_EXCL 與 hard link；exFAT、FAT32 即此類）——沒有存任何東西。把 store 放在 APFS 或 HFS+ 的磁碟區上`，
`sources/` 底下沒有任何檔；同一個檔存到 APFS 上的 store：「✓ 已存入位元組」「✓ 已建立 index 條目」，位址與 index 正常。live store 在 APFS 上，不受影響。

**`InFlightSourceFiles` 的 inode 比對還需要嗎？不需要，改成以名字認**（使用者要求檢查）。inode 比對本來是為第三條路的目的檔設計的（位址上的名字會被別人搶先放上，所以要確認
「刪的是自己建立的那個」）；第三條拿掉之後，登記的只剩**暫存檔**，名字帶這一次呼叫自己的 UUID、以 `O_EXCL` 建立——名字本身就是身分，沒有別人會放同名的檔。在支援的磁碟區上 inode 比對仍然成立，
但它在任何 inode 會漂移的檔案系統上失效（正是這次的根因），而能力閘只擋得住有回報旗標的磁碟區。所以改成：登記路徑、刪之前 `lstat` 確認仍是**普通檔**（名字上被換成目錄或 symlink 就不動）、不比 inode。
在任何檔案系統上都一樣成立。測試 `testRegisteredTemporaryFilesAreRemovedByNameWhateverTheirInode`（`rename` 蓋掉同名檔、inode 真的變了，仍要被刪）與
`testARegisteredNameThatIsNoLongerARegularFileIsLeftAlone`；負控：登記時多取 inode、刪之前比對（R2 的寫法）→ 前者紅；拿掉普通檔檢查 → 後者紅。

## 2. `syncFile` 不再讓真的 `F_FULLFSYNC` 錯誤被 `fsync` 的成功蓋掉（finding 2，MEDIUM）

**成立。** 先前 `F_FULLFSYNC` 失敗就一律試 `fsync`、成功就回 0；`fsync` 在 macOS 不清裝置的寫入快取，補不了失敗的 `F_FULLFSYNC`（R2 verify 第 21 則要的耐久性因此破洞）。
現在 `syncFile(_:fullFsync:plainFsync:)` 先存 errno：**只有 `F_FULLFSYNC` 回「不支援」（~~`ENOTSUP`／`EOPNOTSUPP`／`EINVAL`~~——b29 V5 起是封閉的六個，加上 `ENOTTY`、`ENODEV`、`ENOSYS`，見 `2026-10-02-b29-h5-fixes-703-700.md`）才退到 `fsync`**；`EIO`、`ENOSPC` 等直接回傳，存檔被拒
（不放上位址、不留暫存、不寫 index）。`fsync` 自己的真錯誤照樣回；`fsync` 也回「不支援」時當成盡力而為（回 0——那個檔案系統沒有可用的同步手段，不是 I/O 錯誤；這一條沒有改）。
**`EINTR` 的政策：每個呼叫重試至多 8 次**，用完仍 `EINTR` 當成錯誤回傳（訊號被我們忽略或由 dispatch 接手，實際上不會發生，仍以有界迴圈寫明）。
兩個系統呼叫是參數（預設是真的）。測試：`testARealFullFsyncErrorIsNotHiddenByASuccessfulFsync`（`F_FULLFSYNC` 回 `EIO`、`fsync` 成功 → 回 `EIO` 且沒去試 `fsync`）、
`testFsyncIsOnlyTheFallbackForAnUnsupportedFullFsync`、`testSyncRetriesInterruptsAFixedNumberOfTimes`、整合的 `testAStoreIsRefusedWhenFullFsyncFailsEvenIfFsyncWouldSucceed`。
`F_FULLFSYNC` 與 `fsync` 的成本取捨（使用者決定項）沒有動。

## 3. 訊號來源：事件送到時重新讀處置（finding 13、18、27，LOW／INFO）

**成立，而且 finding 18 在 XCTest 裡重現過。** 長駐的 `DispatchSourceSignal`（建立後不取消）加上「最近一次接管時是預設處置」的旗標：主機在第一次存檔**之後**才裝自己的 handler
時，kqueue 的 `EVFILT_SIGNAL` 在行程自己裝了 handler 時也會記錄訊號，長駐的來源照旗標做 `SIG_DFL` ＋ `raise`，把主機的優雅關閉殺掉。
- **(a)** `handle` 改成讀當下的處置（`shouldTerminate`）：我們正在忽略它且處置仍是忽略 → 是（那一下 Ctrl-C）；處置是預設 → 是（還原之後才送到的事件，否則 Ctrl-C 被吞掉）；
  處置是別人的 handler、或不是我們忽略的 `SIG_IGN`（主機自己的）→ 不管。`defaultAtLastTake` 旗標整個拿掉。測試：真的訊號（`kill(getpid(), sig)`——`raise` 只對呼叫的執行緒送，kqueue 看不到，我第一版就這樣測成了空測試）
  `testALingeringSourceDoesNotKillAHostThatInstalledItsOwnHandlerLater`；真值表 `testTheSignalSourceOnlyTerminatesWhenTheDispositionIsOursOrDefault`。負控：`.custom` 也回 true → 真的訊號那支讓整個測試行程被那個訊號結束，真值表紅。
- **(b)** 「登記期間沒有 spawn 子行程所以忽略不被繼承」的註解只對呼叫的執行緒成立：`SIG_IGN` 是整個行程的，`exec` 會繼承。現在寫成誠實邊界（`InFlightSourceFiles` 的 doc 與 `docs/store-format.md`）：內嵌 `AkashicStoreIO` 的主機要自己避開；CLI 與序列化的 MCP actor 目前不會這樣。**沒有改行為。**
- **(c)** `releaseSignals` 只還原**處置仍是我們設的忽略**的訊號（先前無條件 `SIG_DFL`）。測試 `testReleasingTheSignalsDoesNotOverwriteAHandlerInstalledMeanwhile`；負控：無條件還原 → 紅。
