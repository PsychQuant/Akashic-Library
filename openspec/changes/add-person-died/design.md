## Context

Store 目前把三件互相獨立的事壓成一個由隸屬時間軸推導出來的 `status`：隸屬是否結束（可表達）、是否仍活躍（不可表達）、是否在世（不可表達）。`Organization` 有 `founded` 與 `dissolved`，`Person` 卻沒有任何生平欄位——同一個 store 裡機構有生命週期而人沒有。

約束條件：

- store 格式是**有版本、normative、被三個獨立 binary（CLI / akashic-mcp / App）共讀**的已發布格式，另有外部消費者（storyline 專案的 DuckDB 重建流程）。
- 既有的 tolerant-preserve 機制會原樣保留未知欄位並在寫回時重新產生。
- 既有的日期精度慣例是 **ISO 8601 前綴字串**而非日期型別，理由寫在日期區間型別的文件註解裡：來源資料常是月精度，轉成日期型別得補一個不存在的「日」，之後就再也分不出「1 月」與「1 月 1 日」。

相關但不在本變更內的 issue：63（無界區間的表達）、66（provenance 機制）、64（CV 補完）、83（39 位退休研究人員的著作缺口）。

## Goals / Non-Goals

**Goals:**

- 讓「是否在世」成為可記錄的事實，且不損失來源的日期精度。
- 明確區隔三件事的處置方式，並讓這個區隔在**衍生層也看得見**（目前只在原始碼註解）。
- 不 bump store format、不需要遷移工具。
- 讓「已故卻仍有開放隸屬」這種資料矛盾能被發現。

**Non-Goals:**

- 出生日期欄位。
- 帶 provenance 的結構化逝世記錄。
- 無界區間（「知道已故、完全不知何時」）的表達——見決策 4。
- 隸屬狀態欄位的改名。
- 活躍度的記錄或推導函式。
- 實際逝世日期的資料填補。

## Decisions

### 決策 1：範圍取「只記逝世」，不加出生

三個候選是「生卒都加」「純推導活躍度」「只加逝世」。

**純推導不能單獨成立**：已故者的著作清單是**封閉**的、在世者是**開放**的，而 issue 64 的 CV 補完需要的正是這個終止條件。從「最後發表年」推導給不出它——一位 2019 年後沉寂的在世學者，與一位 2019 年過世的學者，推導結果完全相同。純推導可以是補充，不能是替代。

**出生日期延後**：對在世者是個資，而本專案用途不明。因為新增欄位是 additive，日後要加仍是 additive，**延後的成本為零**。這是可逆決定，沒有理由現在就付。

### 決策 2：平的字串欄位，不是複合值——方向決定可逆性

候選是 `died: String?`（平欄位）對上形如「日期＋來源＋註記」的複合值。複合值直接回應了「平欄位掛不上 provenance」這個反對，該反對本身是對的。但兩個方向的**可逆性不對稱**：

| 選擇 | 日後 provenance 機制（issue 66）落地時 | 格式影響 |
|---|---|---|
| 平欄位 | 在旁邊**新增**一套機制 | additive → 不 bump |
| 複合值 | issue 66 若設計出別的形狀，**改既有欄位的形狀** | 欄位形狀變更 → 必須 bump format |

為一個**尚未設計**的機制先蓋一個 bespoke 版本，等於把「未來可能要 bump」買進來。取平欄位。

過渡期的來源保全見決策 8。

### 決策 3：不 bump store format

依 store 格式文件的 bump 準則表：additive（新增欄位）**MUST NOT** bump，non-additive（欄位語意變更、刪除、結構重排）**MUST** bump。兩者不重疊且邊界是硬的。

新增 `died` 是純粹 additive：舊 binary 靠 tolerant-preserve 原樣保留該欄位，**不會按舊語意誤讀新格式**（那才是 refuse-if-newer 要擋的情境）。

這一點必須**寫進格式文件**，否則下一個人會以為漏了 bump。本變更與 authorized names 那次（issue 81）的差別要講清楚：那次改的是既有欄位的語意——舊 binary 會在一次 read-modify-write 裡重排該欄位而不自知——所以必須 bump 並寫遷移。本變更沒有任何一項。

### 決策 4：`died` 的缺席是**右設限**，不是表達力缺口

這是本設計最容易被誤解的一點，必須寫清楚。

`died` 是存活分析中「事件指示 δ 與事件時間 T」的緊湊編碼：

| 寫法 | 統計意義 | 對 T 的資訊 |
|---|---|---|
| `died: "2004-11-18"` | 精確觀測（δ=1）| T 已知到日 |
| `died: "2004-11"` | **區間設限**（δ=1）| T 落在該月 |
| `died: "2004"` | **區間設限**（δ=1）| T 落在該年 |
| 缺席 | **右設限**（δ=0）| T 大於觀察窗，上界不存在 |

**ISO 前綴慣例本來就在做區間設限**——精度就是區間寬度。這不是本變更發明的，是既有慣例的正確描述。

缺席同時涵蓋「真的還活著」與「已故但未觀察到」。**從資料的角度這兩者就是同一件事**：右設限的定義就是「在觀察窗內沒觀察到事件」。這不是缺陷，是設限的本質，任何 schema 都消不掉它。

**死亡是必然事件，所以缺席永遠不是「不適用」。** 每個人都會死，只是我們尚未觀察到——`died` 因此不是「一個可能不存在的事件的選填資料」，而是一個**部分觀察到的普遍屬性**。這個區別有實質後果：δ=0 是一個**完整且明確**的狀態，不是資訊缺漏。

**同樣的話對機構也成立。** 曾有一版設計主張「機構的解散不是必然事件，所以那裡的缺席另有『永不解散』的讀法」——該主張**已撤回**：舉不出任何被證明不會結束的組織，最老的持續營運者（金剛組 578–2006、慶雲館 705 至今）只是尚未結束，那正是右設限。用存活分析的話說，那一版等於假設了一個 cure model（存在「免疫」個體、生存函數在無窮遠處不為零），而該假設沒有證據。**兩者都是 proper distribution，δ=0 在兩邊都是設限。**

真正的不對稱不在「事件會不會發生」，在**事件本身的定義是否銳利**：

| | 人的死亡 | 機構的解散 |
|---|---|---|
| 事件必然發生 | 是 | 是 |
| 有機制保證且壽命有上界 | 是（約 120 年）| 否 |
| **事件邊界清晰** | **是** | **否** |

人的死亡是銳利事件：不會半死，也不會被另一個人吸收。機構會合併、分割、被併購、改名、重建——金剛組 2006 年被吸收，那算不算解散？**那不是設限問題，是同一性問題。** 所以機構欄位的缺席除了「未觀察到」之外，還可能藏著一個未裁決的同一性問題；而本 store 對那種東西已有專屬機制（issue 71 / 77 的歧異記錄：未決的同一性問題是一級事物），不該用設限的修法去蓋。

對本變更的結論不變：`died` 的缺席是純粹的右設限，無其他讀法。

而且**設限時間在本 store 是可推導的**：最後一筆著作的日期給出「至少活到那時」的下界。標準存活資料存的是觀測時間與事件指示的配對，其中觀測時間對設限者而言是**設限時間**而非死亡時間；本 schema 在 δ=0 時不存任何值，靠設限時間可從發表資料還原來補。**這個編碼之所以不失真，正是因為設限時間可還原**——與決策 5 的立場自洽。

**唯一真正缺的一格**是「δ=1 但區間無界」（知道已故、完全不知何時）：ISO 前綴最粗只到年，沒有「某個時候」這種寫法。δ=0 完整、δ=1 有界完整、只缺 δ=1 無界。這一格屬於 issue 63，本變更不處理。升級條件很具體：issue 83 的檢索若真的撞上這種案例，就是把 issue 63 一起解的時機。

### 決策 5：活躍度什麼都不加——刪除測試

不加欄位、不加推導函式、不加匯出欄。

匯出的 publication 表已含日期，「最後發表年」是一句依研究者分組取日期最大值的 SQL。**假設今天真的加了一個活躍度欄位，把它刪掉會壞掉什麼？什麼都不會壞**——所有消費者都能從 publication 重算。一個刪掉不會壞事的抽象層不該存在。

更根本的理由：「活躍」沒有非任意的門檻（近五年？近十年？）。記下來等於把一個規約當成事實存進 store。

### 決策 6：隸屬狀態欄位不改名，改為新增逝世欄並把語意寫進匯出 schema

候選是「把 `status` 改名為 `affiliation_status`」對上「不改名」。

改名讓「它描述隸屬」寫在欄位名上，但那是對**衍生層**的 breaking change，跨到 storyline 專案。取第三條路：

- 隸屬狀態的推導邏輯與欄位名**逐字不動**。
- 匯出的 researcher 表**新增 `died` 欄**——衍生層的 additive，既有按欄名取值的 reader 不受影響。
- 把「隸屬狀態描述的是**隸屬**，不是活躍或在世」從原始碼註解移到**匯出的 schema 說明**。

理由：改名是讓消費者「不被誤導」，新增欄位是讓消費者「拿到他真正要的東西」。**先給資料再談改名**——有了逝世欄之後，隸屬狀態被誤讀的實際損害會小很多，改名的急迫性可能自己消失。

### 決策 7：逝世不參與隸屬狀態推導；矛盾只報告不自動修

隸屬狀態的推導邏輯**逐字不動**。逝世是關於人的事實，隸屬狀態是關於隸屬的事實，兩者正交。魏慶榮的案例：`died` 為 2004-11-18、隸屬結束於 2004-11 → 隸屬狀態仍是 retired，**這是對的**（隸屬確實結束了）。

另新增一條驗證：**有 `died` 卻仍有開放的 affiliation 段** → 出現在報告中，**不自動關閉**。

不自動關的理由：把隸屬的結束時間設成逝世日是**推論**，而該推論可能錯（人可能離職多年後才過世，開放的段只是漏記）。紀律與時間軸重疊檢查的既有註解一致：「回報而非拒絕，判斷屬於使用端」。

### 決策 8：provenance 機制落地前，逝世來源一律寫進既有的 person note 欄位

醜——單一自由文字欄、不參與計算。但**「醜且留著」勝過「乾淨且弄丟」**：issue 83 檢索時來源就在手上（紀念文集），蒸發掉之後重找的成本等於第一次找。provenance 機制落地時這些字串是可遷移的；沒記下來的來源不是。

這是硬要求，不是建議。

### 決策 9：概念用 deceased，欄位名用 `died`

issue 的用詞澄清已把「過世」的 canonical 定為 **deceased**（一個人的生命結束，與隸屬結束正交）。欄位名取 `died`，因為它持有的是**該事件的日期**，與 `Organization` 的 `dissolved` 對稱（同為過去分詞當日期欄位）。

規約：spec 與文件散文用 "deceased"，欄位名與程式識別字用 `died`。本 repo 無共用詞彙檔，不另立詞條。

## Implementation Contract

### Behavior

- 一筆 person 記錄可以帶一個 optional 的逝世日期。寫入什麼精度就讀回什麼精度——年、年月、年月日三種寫法都原樣保留，**不得**被補齊成完整日期。
- 逝世日期的存在**不改變**任何既有推導：隸屬狀態、時間軸、顯示名、authorized 名字的行為逐字不變。
- 匯出的 researcher 表多一欄逝世日期；未記錄者為 NULL。
- 診斷指令會報告「有逝世日期但仍有開放隸屬段」的記錄，且**不修改**它們。

### Interface / data shape

- `Person` 新增 `died` 屬性，型別為 optional 字串，語意為 ISO 8601 前綴。位置緊接既有的識別碼類欄位之後、`profile` 之前（與 YAML 輸出順序一致）。
- YAML 表示法：person 記錄的頂層新增 `died` 鍵，值為字串。缺席即欄位不存在（**不得**輸出空字串或 null 佔位）。
- `died` **必須**登記進 person 的 known-keys 集合。
- 診斷報告新增一項查詢，回傳「有逝世日期且至少一段隸屬仍開放」的記錄 key 清單（依字典序）。
- 匯出的 researcher 表欄位清單新增一欄，欄名 `died`，位置在既有欄位之後。

### Failure modes

- `died` 的值若不是純量（例如寫成 list 或 map）→ 沿用既有的形狀檢查機制拒絕，錯誤訊息點名欄位名。
- `died` 缺席**不是**錯誤，也**不得**被推導或猜測。
- 「有逝世日期但仍有開放隸屬」**不是**錯誤，不進 quarantine、不阻擋載入——僅出現在診斷報告中（刻意可見但不阻塞）。
- 本變更**不得**觸發任何 format 版本檢查行為的改變。

### Acceptance criteria

- 三種精度（年 / 年月 / 年月日）的 round-trip 測試通過，且斷言精度未被補齊。
- 一個回歸測試證明 `died` 未登記進 known-keys 時會被偵測到（欄位不得同時被結構欄位與未知欄位機制持有而重複輸出）。
- 一個契約測試以魏慶榮為案例：`died` 為 2004-11-18、隸屬結束於 2004-11 → 隸屬狀態仍為 retired。
- 一個測試證明「有逝世日期＋開放隸屬」出現在診斷報告中，且該記錄在跑完診斷後**內容未變**。
- 匯出的 researcher 表欄位清單含 `died`，且該欄對未記錄者為 NULL。
- store 支援的 format 版本常數**未變**。
- 既有測試全數通過。

### Scope boundaries

**In scope**：person 的 `died` 欄位（模型、codec、known-keys）、診斷報告的新查詢、匯出 researcher 表的新欄位、格式文件與 README 的說明、上述測試。

**Out of scope**：出生欄位、provenance 機制、無界區間表達、隸屬狀態欄位改名、format bump 與遷移工具、活躍度的任何記錄或推導、實際逝世日期的資料填補。

## Risks / Trade-offs

- **最大的風險是把它做大。** 本變更是 additive、不需 bump；若在同一個 change 裡順手解 issue 63 或 issue 66，會變成需要遷移的 schema 重構。scope 邊界已在上方寫死。
- **known-keys 漏登記** → 欄位重複輸出。這是本 repo codec 的既知陷阱，必須有回歸測試釘住，不能只靠記得。
- **精度回歸**：任何把逝世日期轉成日期型別的中間層都會把「年」補成「年月日」，而且**不會報錯**。測試必須直接斷言字串原樣。
- **來源流失**：provenance 機制落地前靠 note 欄位承載，不參與計算。決策 8 已把它定為硬要求，但仍依賴人執行。
- **匯出新增欄位**對以位置取值（而非欄名）的下游消費者是破壞性的。已知消費者按欄名取值，但這個假設未經全面查證。
