## MEDIUM

### #709 `resolve-divergence --dry-run` 預測成功、實跑被拒（第 3、4 則）

兩席在真 binary 上各自重現：work A、B 是攣生候選，第三筆 C 引用 B、自己有 leftover（`entities/<id>.yaml` 與 `entries/<citekey>.yaml`，同一個 id）。
`--dry-run --survivor a…` 以 0 結束並印「參照將改寫：C, C」；拿掉 `--dry-run` 才被 #631 以 `legacyCopyPresent` 拒絕（零寫入、git 乾淨）。

成因：第二個 #709 commit 把這一對從共用的 `assertNoCrossRecordErrors` 拿掉，改由 `candidateLegacyCopies` 只看**候選**；「被改指的 entry 自己有 leftover」
那一格的拒絕只剩 `commitResolution` 的 `entryWritePlan` 預檢，而 preview 不經過它。`validateResolvePreconditions` 的 doc 自己寫著 dry-run 與實跑必須擲一樣的錯（#139 F1）。

修法：`DivergenceResolve.assertRewriteTargetsWritable`——對 `entriesTouchedByMerge`（preview 的 `rewritten` 與 D86 的閘早就用同一份）的每一筆跑 `entryWritePlan`，
住在 `validateResolvePreconditions` 的尾端（版控閘之後）。work／person／venue 三種合併共用。`commitResolution` 裡那一道留著當最後一道防線。
person 側以 person 為 holder 的 verdict 遷移早就由 `assertHoldersWritable` 跑 `personWritePlan`，不重複。

**「同一筆列兩次」**（第 3 則末句）：pair 在被改指的名單裡就會被拒絕，所以成功的報告裡不會有兩份；一份在 `entities/`、另一份是改名前舊 citekey 的拷貝**不引用**候選時，
只有被引用的那一份在名單裡、也只列一次。測試的對照組（`testWorkMergeWithoutALeftoverStillPreviewsAndRuns`）釘住「只列一次」。

測試：`ResolveDivergencePreviewLegacyCopyTests`（新，六支）把 preview 與實跑逐一配對——work 合併（leftover 同 citekey、改名留下的拷貝）、person 合併、venue 合併，
斷言兩邊擲同一個錯、訊息指名檔案、磁碟位元組逐位不變；對照組兩支（沒有 leftover、被引用者只有 legacy 一份）斷言 preview 與實跑都成功且 `rewritten` 一致。
負控：註解掉 `assertRewriteTargetsWritable` 那一行 → 四支紅（對照組仍綠）；還原後全綠。

### #709 `akashic_doctor` 的前 20 則可能全是 warning（第 5 則）

`crossRecordIssues()` 依產生順序吐，每對 leftover 先造出兩則 warning；MCP 取前 20 則，而 `indexRebuilt: false` 的 note 指向的 error 可能排在第 25 位（真 binary：12 對 ＋ 兩筆共用 citekey 的不同記錄，
`first` 20 則全是 warning）。修法：`StoreHealth.errorsFirst` 的 `ValidationIssue` 版（穩定分割，同 `perRecordIssues` 的作法），套在 `health(from:)`——CLI、MCP、App 讀同一份順序，不各自分割。
`count` 仍是完整則數。測試：`DoctorCrossRecordErrorsFirstTests`（健康清單 error 先且 warning 之間保持原順序；`first` 的第一則是那個 error）。負控：拿掉分割 → 兩支紅。

### #705 截斷成功清單會遺失「後續寫入未套用」（第 1 則）

`laterWriteRefused` 標在 ledger 的那一筆上，MCP 成功回應只留前 20 列，`…Total`／`…Truncated` 只說拷貝總量。25 份拷貝裡只有排序第 25 的那筆被拒時，可見的 20 列都沒有 `laterWriteNotApplied`，
使用者只知道有拷貝要清、不知道有更新沒落地；`akashic validate` 重建得出兩份並存、重建不出「這一趟打算套用什麼」。

修法：另給 `writtenWithLegacyCopyNotApplied`（完整的沒套用筆數，在截斷之外；大於 0 才出現，沒有這個鍵＝零，所以既有回應的位元組不變）。import 的 payload、併進已帶這個鍵的回應（兩邊相加）都處理；
錯誤回應的人可讀報告在「另有 N 筆未列出」那一行補說其中幾筆沒套用。十三份工具說明共用的 `legacyCopyNote` 點名這個鍵（#672 的立場）。
測試：`WrittenWithLegacyCopyR2Tests` 加三支（25 筆只有第 25 筆有標記、對照組無標記時鍵不出現、CLI 全列、併進已截的回應；錯誤文字；import payload）。負控：count 條件改成不可能 → 三支紅。

### #707 執行紀錄的 end／rc 只檢查 harness（第 2 則）

`migrated-guard-control` 在逐 run 處理時，`if invokes.isEmpty && declared.isEmpty { continue }` 排在 end 檢查**之前**，所以一般守衛（沒有 invoke、沒有宣告）的 end 從來沒被查過：
runner 把一般守衛改成 `… || true`（它回非零）或它留下 start 就被殺，只要它的 harness 仍提供負控證據，讀者就回報「無缺口」；runner 的文字檢查攔不住，因為那一行確實有 start。

修法：除了讀者自己（它在迴圈外），**每一個**被 runner 啟動的行程都要有 `end`、rc=0；harness 的訊息原樣保留（它說「它的 N 次執行都不算數」），一般守衛另有一句。
`migrated-guard-control-mutations` 加三格：兩格改壞的紀錄（一般守衛 rc=1、一般守衛留下 start 沒有 end），一格真的迷你 runner（`decision-matrix-drift` 對不存在的檔跑、回 rc=1、被 `|| true` 遮掉，
它的 harness 照常提供證據；斷言讀者回 1 並指名、輸出沒有「無缺口」）。負控：把新分支關掉（`&& false`）→ 這三格全紅（27/30）；還原後 30/30。
