## MEDIUM

### person 的對外形不在替換裡消失（第 0、2、3、8、11、13 列；LOW 第 18、19、23 列同源）

修正輪二讓「沒有分類記錄的對外形」在 `fields.names` 整份替換裡一步離開 names（附理由、回 `authorizedRemovedWithoutRecord`）。五席從不同面指出同一條路的缺口：

- 理由沒有地方落：沒有名字進入或留下時 `judgementsRecorded: 0`，理由既不入庫也不在回應（第 0、8、13 列）；有名字留下時，理由被寫成那個名字的「確認」——刪「Latin Name」的理由出現在王小明的確認記錄上（第 3 列）。
- 這條路不寫記錄，format 22 的寫入閘因此沒觸發：live store 是 format 18，真 binary 在 format 18 的 store 上刪掉了對外形、`doctor` 隨後印 `no authorized name: 1 person`，要補回對外形又被閘擋下（第 2、11、13、18 列）。也沒有移除面一族的 git 閘（第 8、23 列）。
- `{"authorized":[],"variant":[]}` 能把 person 清到沒有名字（第 11、19 列）。

處置（裁決 1、2）：

- **對外形不得在替換裡整個離開 names，有沒有記錄都一樣**：移出 authorized 要寫一筆「撤回：理由」，而記錄錨定 names——所以名字要留在 variant。替換讓對外形整個離開 names 一律整批拒絕、零寫入，訊息說出口（放在 variant、附 `--judgement`；之後要刪再用 `--remove-name`），store format < 22 時另起一行說寫入閘與升級路徑。改正拼寫因此仍是一次呼叫（舊拼法移到 variant 寫撤回、新拼法寫指定），兩筆記錄都入庫。`authorizedRemovedWithoutRecord` 退場。
- **只替進出的名字寫記錄**：進入的寫指定、移到 variant 的寫撤回，仍在 authorized 的不寫確認。附了理由而沒有名字進出 authorized 整批拒絕——沒有要記的判定，理由不靜默丟掉（先前寫一筆確認到每個對外形上）。
- **替換不把 person 刪到沒有名字**（原本就沒有名字的不擋）。`zero-instance-guards` 第 86 列的「唯一入口」改成兩個入口都擋。
- format < 22 時 person 的 authorized 每一種改法都要寫記錄，都被寫入閘擋下——這是裁決 1 要的；修正輪二 changelog「交給使用者」第 4 點那句「行為不放寬」在 R2 為假，現在為真。

**實作的讀法，~~交給使用者~~ → 使用者 2026-10-05（05:18Z）裁：維持現狀**：裁決 1 的「替被移出的名字寫一筆撤回」實作成「拒絕對外形整個離開、出口是留在 variant」。另一種讀法是程式自動把它留在 variant——那會讓結果與呼叫端送的整份替換不同（「提及的欄位整個換」的契約），所以沒有採用。

### 合併搬記錄以原始倖存者為基準、相同歷史不重搬、線性（第 1、4、9、10 列；LOW 第 21 列同源）

修正輪二把合併搬名字分類記錄改成「逐筆接、只比最後一筆」，修好了「指定 R → 撤回 S → 指定 R」被吃掉的那一格，卻帶出三個問題：

- **相同歷史翻倍**（第 4、10 列，真 binary）：兩筆攣生各有「指定 R → 確認 S」，合併後倖存者四筆，`validate` 報兩則重複；修正輪二之前同一個合併搬 0 筆。倖存者「指定 R → 確認 R2」併入「指定 R」，較早那筆「指定 R」被重新接成最後一筆。
- **尾端矛盾的基準隨順序漂**（第 1、21 列）：每接一筆被併者就拿「此刻的倖存者」當基準並累加差集——被併者 A 暫時修掉倖存者原有的矛盾、B 又帶回來，B 的矛盾被當成新的；一筆造出的矛盾被下一筆修好也照擋。結論隨被併者的給定順序翻轉。
- **平方成長**（第 9 列，真 binary）：每接一筆都倒著掃整份 references、做 parse 與 canonical；兩個 person 各 4,000 個互異名字、各一筆撤回時乾跑 89 秒（debug）。

處置：

- **搬法**（`NameClassificationRecord.carryCollecting`）：被併者依 key 排序，各自的記錄依自己的順序接，兩種情形不接——(1) 與那個名字那個分割此刻的最後一筆位元組相同；(2) 倖存者那個名字那個分割的歷史裡已有位元組相同的一筆，**而且**此刻的最後一筆與名字合併後的分類一致。第 (2) 條讓相同歷史不再翻倍；「此刻一致」保住修正輪二要的那一格（「撤回 S」接上之後尾端不一致，第三筆「指定 R」照接）。
- **尾端矛盾**：以原始倖存者的狀態為基準，全部接完之後算一次差集（`classificationTailDelta`）；被併者依 key 排序，結果與給定順序無關。矛盾逐條說出是哪一筆被併者帶來的，或是倖存者自己的記錄（這次合併改了它的分類）。
- **線性**：每個（分割, 名字）的最後一筆與歷史位元組一次建好索引、逐筆更新；`appendCollecting`（寫入面）同一個索引。
- 真 binary 重跑：兩個 person 各走過「指定 R → 撤回 S → 指定 R」再合併，搬 0 筆、`validate` 零則重複。

### #582 的重複 reference 掃描不誤報合法歷史（第 5、12 列）

`duplicateReferenceIssues` 把名字分類記錄當集合分組，「指定 R → 撤回 S → 指定 R」（store-format §3.5 定為合法、修正輪二的合併刻意造出）被報成「同一個動作做了兩次」，處置「留一筆」照做會讓最後一筆與分類矛盾。現在名字分類記錄另算：只報同一個名字同一個分割裡**相鄰**而彼此相等的（寫入面只比最後一筆，寫不出它；手改或舊 binary 才有），處置寫「刪掉相鄰多餘的那一筆不改變最後一筆」，並明說不相鄰的同一句是合法歷史。`zero-instance-guards` 第 35 列補記並改量測腳本（2026-10-05 live store：名字分類記錄相鄰相等 0）。

### 出口說出交換與它的代價、variant 欄位另給出口（第 6、7 列；LOW 第 14、25、31、32 列同源）

- person「不在 authorized 卻以指定結尾」的出口「先放進 authorized、再移回 variant」在同書寫系統已有對外形時走不通（authorized 放不下兩個）。刪名字的拒絕與合併的拒絕都改成說出要與那個對外形交換，以及它的歷史會多一對撤回／指定。
- 合併拒絕的出口一句涵蓋全部，variant 分割「不在 variant 卻以指定結尾」那一格給的是 authorized 的做法（`--authorize` 再 `--unauthorize` 只寫 authorized 的記錄），照做之後同一則拒絕原樣回來。出口改成依實體、分割與矛盾的方向各一句（`tailConflictExits`），只列這次出現的那幾種；variant 那一格是「要它是異寫就 `--add-variant`；要它不是，`--add-variant`、`--authorize`、`--unauthorize`，再 `--authorize` 補回原本的對外形」。真 binary 照新出口做完，合併通過。
