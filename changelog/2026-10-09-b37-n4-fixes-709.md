## MEDIUM 1、3：`bootstrap-people` 不把 person 拷貝算進計畫

`BootstrapPlanSource.people` 的種類只有 work，理由寫在註解、上一輪的 changelog、零實例第 91 列與 mcp-cli-parity：person 拷貝只進 `existing` 與否決／確認史，
「只會讓候選少一個（保守側）」。這句沒量過。verify 以真 binary 重現三條反例：

- 拷貝帶 entities/ 那份沒有的否決記錄：`Doe, A.` 本該「與既有 person 寬鬆共鍵、先消歧」，否決把它放行成建檔候選，`--apply` 建了 `doe-a`。
- 拷貝多一個名字：`Roe, B.` 被當成已存在，既不是候選也不在 pending，沒有任何提示。
- 內容相同的改名拷貝：舊 key `doe-a` 留在已用的 key 裡，新候選的 key 變成 `doe-a-2`；拷貝刪掉之後那個後綴改不回來。

修法（裁決 1）：`BootstrapPlanSource.people` 的種類加 person。附註依計畫與拷貝的種類分句說實話（work 拷貝：literal 多算一次出現；person 拷貝在 people 計畫：
key、名字與否決／確認記錄也算數，可能讓候選變多、變少或 key 多後綴；person 拷貝在 organizations 計畫：隸屬 literal 多算一次出現）。註解、上一輪 changelog
（劃線加更正）、零實例第 91 列與 mcp-cli-parity 的那句前提拿掉、改成實話。`bootstrap-venues` 不讀 person，照舊不擋（對照組）。

測試：`BootstrapPlanBlockersCLITests` 的三支反例（真 binary；每支先跑沒有拷貝的對照、再加拷貝，斷言反例成立，再斷言乾跑點名、`--apply` 以 1 拒絕、零寫入）、
`testAPersonCopyDoesNotBlockBootstrapVenues`；`ShadowedLegacyCopyReadersCLITests.testAPersonOnlyCopyIsInThePeoplePlanButNotTheVenuesPlan`（上一輪的
`…IsNotInThePeopleOrVenuesPlan` 改寫）。負控：種類改回只有 work，五支紅（21 則斷言失敗）；反向編輯還原。

## MEDIUM 4：拒絕只認 load 的拷貝標記

`legacyCopiesInPlan` 只數 `fileSituation.shadowedLegacyFile`，而標記要求 entities/ 有同一種、同一個 id 的那份。兩個 legacy 檔共用 id、或 entities/ 與 legacy 同
citekey 而 id 不同，計數同樣加倍，乾跑沒有附註，`--apply` 先寫 person 再以 index 的 UNIQUE 失敗收場。

修法（裁決 2）：判準搬到 `LibraryLoad.planBlockers(_:)`——計畫讀到的種類裡 load 標出的拷貝 ∪ 無法唯一定位的記錄（works 問 `unlocatableCitekeys`、people 問
`unlocatablePersonKeys`；各自的封閉類別寫在 `DuplicateCitekeys.swift`，這裡不另寫一份）。同一對拷貝的兩份本來就無法唯一定位，只在拷貝那一段列一次。
附註（`planBlockersNote`）與拒絕（`refuseApplyWithPlanBlockers`）都由它算；舊名 `legacyCopiesInPlan`／`legacyCopiesInPlanNote`／
`refuseApplyWithLegacyCopiesInPlan` 一起換掉，因為它們不再只說拷貝。`bootstrap-people --json` 的 `legacyCopiesInPlan` 照舊是拷貝數（自此含 person 拷貝），另帶
`unlocatableInPlan`（兩者處置不同：刪拷貝 vs. 先修好）。

**誠實邊界**（裁決的字面，交使用者知道）：「無法唯一定位」的第 3 類——load 判定檔案寫入時會被拒，例如一份不受 git 追蹤的 legacy 單檔——不讓計數加倍，也照樣擋。
store 不在 git 裡時，計畫讀到的那一種只要有一份 legacy 殘留，`--apply` 就拒絕（2026-10-09 真 binary 實測，`testASingleUncommittedLegacyFileAlsoBlocks` 釘住）。
venue／organization 的重複 key（#669）不在條件裡，裁決沒有列它們。live store：legacy 殘留 `entries/` 0、`people/` 0，重複的 citekey 0、重複的 person key 0。

測試：`BootstrapPlanBlockersCLITests`（store 是 git 工作樹、檔案已 commit，所以單份 legacy 檔不算無法唯一定位——`testASingleCommittedLegacyFileDoesNotBlock` 釘住）：
兩個 legacy 檔共用 id、同 citekey 不同 id，三個 bootstrap 都在乾跑點名、`--apply` 拒絕、零寫入；同 key 不同 id 的 person，people／organizations 擋、venues 不擋。
負控：`found` 清空，三支紅（29 則失敗；失敗訊息裡看得到修正前的行為——乾跑沒有附註、`--apply` 寫了檔之後才 `UNIQUE constraint failed: entries.uuid`）；反向編輯還原。
零實例表新增第 102 列（本分支編號）。

## MEDIUM 2、5：`enrich` 的 DOI 歧義理由在同 citekey 的拷貝加真孿生時說錯

`AddOnlyEnrichment.plan` 以 `working[e.citekey] = e` 建表，同 citekey 後者勝；load 先讀 entities/ 再讀 legacy，所以同 citekey 的 legacy 拷貝把 entities/ 那份擠掉。
命中只剩拷貝，理由說 entities/ 那份「它不帶這個 DOI」（假）、叫人刪拷貝「再跑」（刪了仍與真孿生歧義），#459 的指路不見。同一個根因的副作用（verify 的 t8）：
entities/ 帶 DOI、同 citekey 的舊拷貝沒有時回 notFound，而同一個 store 的 `create-entry --dry-run` 說「DOI 已在」。

修法：`working` 改成完整的陣列，citekey → 位置另建一張表。DOI 命中由完整的陣列篩出，歧義看命中的**筆數**（`matches` 同一個 citekey 只列一次）；
定位到之後就地更新那一筆的位置（後面的提案照舊看得到前面補的鍵）。citekey 路徑本來就先問 `unlocatableCitekeys`，不受影響。

同判斷的其他路徑（逐一看過）：`AkashicService.enrich` 的 `byCitekey` 只用在 `added` 的 item（citekey 不在 `unlocatable` 裡、恰好一筆）；
`ZoteroEnrichment.plan` 的 `byCitekey` 在用到記錄之前先問 `unlocatable`；`import-wos` 的 `byDOI` 先到先得（entities/ 先讀），寫入前也問 `unlocatable`。
這三條沒有同樣的錯。

測試：`ShadowedPairReadersTests.testEnrichKeepsTheTwinPointerWhenASameCitekeyCopyAndAnotherRecordShareTheDOI`、
`testEnrichFindsTheDOIOnTheEntitiesCopyWhenTheSameCitekeyLegacyCopyLacksIt`。負控：命中改回以 citekey 去重，兩支紅；反向編輯還原。

## MEDIUM 0（Codex）與 LOW 9、13、15：理由的處置排在明細之後，被出口截掉

唯一出口 `AkashicService.enrich` 對整句 `displaySafe(max: 512)`。先前逐份明細在前，四份以上拷貝（或 citekey 較長、entities/ 那份不在命中裡）時

## LOW 6、8、12、14：`--apply` 的拒絕把逐份清單塞進單行錯誤

`StoreIOError.invalidInput` 走 CLI 的單行出口：換行被逃成字面 `\u{000A}`、整行在 400 處截斷，12 份拷貝時只點名得到兩份，「至多 20 份」「…另 N 份」到不了使用者。

修法：拒絕訊息只說筆數、處置與去哪裡看（「乾跑（不帶 --apply）逐份列出，akashic validate 逐筆說出原因」），不帶清單；清單只在乾跑的附註（stdout，照常分行，
各至多 20、其餘一行概括）。測試斷言拒絕訊息不含 `\u{000A}` 與「（已截斷）」；`testManyCopiesAreListedInTheDryRunAndTheRefusalStaysOneLine` 用 22 份拷貝。
`ShadowedLegacyCopyReadersCLITests`／`ShadowedPairCensusCLITests` 先前斷言拒絕訊息含檔名，改成斷言乾跑含檔名、拒絕含筆數。

## LOW 10、16、17：`laterWriteRefusedNote` 與 `rerunAdvice` 仍說無前提的刪除與「即可」

`LegacyCopyLeft.laterWriteRefusedNote` 是「刪掉 legacy 那份之後重跑即可補上」，它出現在 CLI 逐筆的列、MCP 每一列的 `laterWriteNotApplied`、App 列的 detail，
App 標題在有 `laterWriteRefused` 時也整句接上；上一輪只修了沒有被拒的那一支。

修法：拆成 `laterWriteRefusedFact`（事實）與 `laterWriteRefusedNote`（事實＋「確認 entities/ 那份是新的之後刪掉 legacy 那份，再重跑才補得上」——MCP 那一列沒有標題可依，
要自己帶前提）。App 標題接事實加「拷貝處理掉之後要重跑才補得上」，前半的「照上一句處理拷貝」也改成直接寫「拷貝處理掉之後」（INFO：位置指涉）。
`LegacyCopyReport.rerunAdvice` 改成「那幾筆在拷貝處理掉之後要重跑才補得上」，兩條 stderr 訊息在它之前都說帶前提的刪除。同一族的
`StoreIOError.legacyCopyLeftEarlierInThisOperation` 也拿掉「即可」。

測試：`LegacyCopyStderrTextTests.testEveryDeletionInstructionCarriesThePremise`（這一族九句，每一處「刪掉 legacy 那份」都緊接在「確認 entities/ 那份是新的之後」後面、
沒有「即可」）；`AppLegacyCopyNoticeTests` 的被拒那一支加同樣的斷言。

## LOW 11、18(b)：零實例第 91 列的觸發條件比行為寬

先前寫「legacy 殘留數 > 0 時三個 bootstrap 的 `--apply` 以結束碼 1 拒絕」：殘留數不蘊含拷貝（拷貝要有 entities/ 那份），也不蘊含每個 bootstrap 都讀到它。
