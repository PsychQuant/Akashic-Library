## #709

### MEDIUM 0、2、4 與 LOW 9、12、16：`enrich` 的 DOI 歧義理由以 id 相等當「拷貝」的代理

`AddOnlyEnrichment.ambiguousDOIReason` 以 `Dictionary(grouping:by: \.id)` 找共用 id 的命中，一律說「是同一筆記錄（同一個 id）的 entities/ 與 legacy 拷貝，
不是兩篇作品：刪掉 legacy 那份」。兩個 legacy 檔共用 UUID、entities/ 沒有那個 id 時（手動複製一個檔忘了換 id）validate 判成兩筆不同記錄的 error，
這則理由卻叫人刪掉其中一份（security、devils-advocate、logic、regression 四席，三席以真 binary 重現）。拷貝加一筆 id 不同的真孿生共用 DOI 時，
它說「刪掉 legacy 那份之後再跑」而刪完仍歧義，#459 的指路不見了（requirements、devils-advocate）。

修法：哪一筆是拷貝**只問 load 的標記**（`fileSituation.shadowedLegacyFile`，判準只有 `markLegacyCopiesShadowedByEntities` 一份），三種情形分開說——

- 被標成拷貝的：點名它的 legacy 檔與 entities/ 那份是誰（不在命中裡時說 `entities/<id>.yaml`、它不帶這個 DOI），帶「確認 entities/ 那份是新的之後刪掉 legacy 那份」
  （#705 第三次 verify 對 `LegacyCopyLeft.explanation` 加的同一個前提）；拿掉拷貝之後只剩一筆時才說「再跑」。
- 同 id 而沒被標的：「共用同一個 id，卻不是 load 認得的 legacy 拷貝：UUID 重複是 error（akashic validate 列出），先修好」——不下「是不是同一篇」的結論、不叫人刪檔。
- 拿掉拷貝之後仍有兩筆以上：「拿掉拷貝之後仍有 N 筆記錄帶這個 DOI——不判定哪一筆才對（#459）」。沒有拷貝也沒有同 id 時，訊息與先前逐字相同。

回應的鍵、`ambiguous` 類別、零寫入都不變；兩面同一個 core plan。citekey 與 legacy 檔名在理由裡是原始值，唯一出口 `AkashicService.enrich` 對整句
`displaySafe(max: 512)`（同 `matches`），所以 core 不先逃（`displaySafe` 不冪等）。

測試（`ShadowedPairReadersTests`，走真的 load——先前的版本用兩筆 id 相同的裸 `Entry`，只靠 id 相等也綠）：
`testEnrichNamesARenameLeftoverInsteadOfPointingAtTheTwinPipeline`（改名一對：點名 legacy 檔與 entities/ 那份、帶前提、不提 #459；對照組兩筆不同記錄只提 #459）、
`testEnrichDoesNotCallTwoLegacyFilesSharingAnIDACopy`（兩份都是 legacy：前提是 load 不標、validate 判 error；理由不說拷貝、不說刪；service payload 同一句）、
`testEnrichKeepsTheTwinPointerWhenACopyAndAnotherRecordShareTheDOI`（拷貝加真孿生：保留 #459、不說「再跑」）。

**負控**（反向編輯）：把函式換回舊版，三支全紅（8 則斷言）；還原後全綠。
