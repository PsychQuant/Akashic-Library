# 在真的 Safari 上的量測（2026-11-20 的 M0–M8，與之後一次一列的 P 表）

`SKILL.md` 第 3 步關於「按了之後 Safari 怎麼開分頁、對話框讀起來是什麼」的每一條規則，都指到這張表的某一列（寫成 M1、M2e 這樣的編號），或寫明沒有量過。這是**一次、一台機器**的量測，不是永久事實；Safari 改版、偏好設定不同都可能不一樣，用之前先看下面〈沒有量過的〉。最後一節〈P 表：M 表以外的量測〉一次量測一列，編號另起、接著 P 往下，列裡寫日期，不併進 M 表；到 2026-11-22 為止是 P1（2026-11-20，在出版商網站上取全文時讀到的對話框探測）與 P2（2026-11-21，同一個視窗裡的唯讀量測，沒有對出版商送請求）。之後在本機測試頁上的一整組量測，像 M 表那樣另開一節、自己編號，那一節的標題寫日期。（這一句原本寫「最後一節〈之後在出版商網站上的觀察〉記的是 M 表以外、在真的出版商網站上讀到的對話框探測（2026-11-20、2026-11-21），編號另起（P1、P2）」：P2 沒有連出版商網站，plugin 規則第 3 條也讓之後的 P 列不限於出版商網站；2026-11-22 更正，#831 第 9 列。）

來源：PsychQuant/Akashic-Library#820 的 2026-11-20 留言（issuecomment-7027590817）。#781 verify 第 2 到第 4 輪各有一條規則建立在沒有人量過的 Safari 行為上，三次都被找出錯；維護者 2026-11-20 08:42 決定先量再修（#781 的 issuecomment-7026678467）。

## 環境

- macOS 27.3（26C5047e）、Safari 27.3、safari-browser v2.9.0。
- 維護者自己的 profile 的一個視窗，由他開、起初只有一個分頁；同一個 profile 另外開著三個視窗。
- 測試頁由本機臨時起的伺服器提供（`http://127.0.0.1:47231`）；沒有連任何出版商網站，沒有動每日嘗試帳本。
- 每一個命令都帶 `--profile` 與 `--window-id`；每一次 `documents --json` 都在同一個呼叫裡篩到測試視窗。
- 維護者在場，三個手動步驟（⌘T、儲存面板、關掉 alert）是他做的。
- Safari 的分頁與下載偏好設定從命令列讀不到；對它們的了解只有這次量測顯示出來的。

## 量到的

| 編號 | 做了什麼 | Safari 怎麼反應 |
|---|---|---|
| M0 | 在一般頁面上跑 `documents --json` | `blocking_dialog.state` 是 `clear`：對話框的探測在這台機器上能用 |
| M1 | `open --new-tab --window-id W <網址>#akashic-<記號>`（`fetch` 送的命令），視窗原本一個分頁 | 新分頁是視窗 W 的最後一個分頁，也是目前分頁 |
| M2 | 對 `<a target="_blank">` 送 `safari-browser click`，被按的分頁是最後一個、也是目前分頁 | 開出新分頁（沒有被當成彈出視窗擋下），它是目前分頁；按的命令回來之後的第一次讀取就顯示連結的目標 |
| M2b | 同一種按法，被按的分頁在 3 個裡的第 2 個、不是目前分頁 | 新分頁在第 4 個：最後面 |
| M2c | 同一種按法，被按的分頁在 4 個裡的第 2 個，目前分頁是第 3 個 | 新分頁在第 5 個：最後面，不在被按的分頁右邊，也不在目前分頁右邊 |
| M2d | 同一種按法，被按的分頁在 5 個裡的第 2 個、是目前分頁 | 新分頁在第 6 個：最後面 |
| M2e | 按一個 `target="_blank"` 的連結，伺服器回 302 | `get attr … href` 印的是屬性的原文（`/redirect`，沒有解析過）。按了之後的第一次讀取顯示的已經是轉址之後的目標，不是 href |
| M3 | 維護者按兩次 ⌘T，文章分頁在 9 個裡的第 2 個 | 兩個新分頁都在最後面（第 10、11 個），網址是 `favorites://` |
| M4a | 按一個呼叫 `window.open(url)` 的按鈕 | 新分頁在最後面，是目前分頁 |
| M4b | 按一個呼叫 `window.open(url, '_blank', 'width=600,height=400')` 的按鈕 | 開出一個新**視窗**。它的 id 列在同一個 `--profile` 底下；視窗 W 的分頁清單沒有變 |
| M5 | 按 `<a href="#" onclick="window.open(…)">` | 被按的分頁的網址從 `…#akashic-<記號>` 變成 `…#`（記號不見了），同時最後面多一個新分頁 |
| M6 | 按一個回應帶 `Content-Disposition: attachment` 的連結 | 沒有出現「要允許在…上下載嗎」的提示（維護者回報）。Safari 顯示儲存面板。面板開著時，視窗 W 的每一個分頁的 `blocking_dialog` 都是 `{"state":"unknown","reason":"incomplete","messages":[]}`，`dialog list` 以 1 結束、說它沒辦法在時限內看完每一個 Safari 視窗。按「取消」之後又是 `clear` |
| M7 | 同一個下載連結加上 `target="_blank"` | 一個一閃就關的分頁。按了之後的第一次 `documents --json` 失敗（結束碼 1，AppleScript -1719：取不到視窗的第 12 個分頁）；之後的讀取沒有新分頁，看到的是儲存面板的 `unknown` |
| M8 | 按一個呼叫 `alert(…)` 的按鈕 | 按的命令 8 秒內沒有回來。視窗 W 的每一個分頁都是 `state: present`，`messages` 是「來自「http://127.0.0.1:47231」： 」加上頁面給的字；`dialog list` 印同一句與按鈕「關閉」。zh-TW 介面的 Safari 在頁面的字前面加上 來自「origin」： |

## 另外看到的

- 幾次一般的 `click` 與 `tab focus`，畫面上沒有對話框，stderr 仍印了一行 `⚠ dialog probe could not inspect window id … completely`。
- 量測當中，測試視窗的最後面出現過兩個分頁，不是量測開的、也不是 ⌘T 開的，之後又不見了。來源不明，沒有對它們送任何命令。批次用的視窗可能從別處多出分頁。

## 沒有量過的

- Safari 自己的下載權限提示：這個來源上它沒有出現，所以它在 `documents --json` 裡是什麼樣子仍然不知道。
- 人按的一下（量到的都是 `safari-browser click`）。
- `confirm()`。
- 別的 Safari 版本與偏好設定。
- 比本機 302 慢的轉址。
- 出版商網站：這次沒有連任何一個。`fetch` 在出版商網站上跑一次仍是 #772 Strategy 第 7 項，還沒有做。
- 測試頁是 `http://127.0.0.1`：`akashic fulltext same-target` 只收 https 與乾淨的主機名稱，所以它對這些測試頁一律印 `unresolvable`；「新分頁的網址與解析過的 href 逐字相同」在真的 https 網站上成不成立，沒有量過。

## 這次量測定下來的事

1. 位置說不出一個分頁是誰開的。連結開的分頁、`window.open` 的分頁、⌘T 的分頁都落在視窗的最後面（M1–M4a）。
2. 新分頁可以和按之前讀到的連結比，而且要在按的同一個呼叫裡讀（M2）。href 要先解析；轉址過的連結對不上（M2e）。
3. 按一下可能開出新視窗，比較這個 profile 的視窗 id 在按之前與之後的集合看得出來（M4b）。
4. 按一下可能同時改掉被按的分頁的片段、又開一個分頁（M5）。
5. 頁面的對話框是 `present`，帶著頁面管不到的來源前綴；儲存面板是 `unknown`／`incomplete`、沒有文字（M6、M8）。下載權限提示仍然認不出來。
6. 分頁自己關掉時，`documents --json` 的一次讀取可能失敗（M7）。

## P 表：M 表以外的量測（一次一列，列裡寫日期）

（這一節的標題原本是「之後在出版商網站上的觀察（2026-11-20、2026-11-21）」，檔頭的標題原本寫「與之後在出版商網站上的觀察」；兩處都在 2026-11-22 改，#831 第 9 列，理由見檔頭那一段。）Safari 本身的行為，照 plugin 的規則 `site-knowledge-goes-back-into-the-plugin` 第 3 條寫在這裡；各站的結果在 [publishers.md](publishers.md) 的同日一節。P1、P2 兩次都是 safari-browser v2.9.0、使用者自己的 profile、`fetch` 鎖定的同一個固定視窗；之後的列各自寫自己的環境（這一句原本寫「兩次都是…」，那時這一節只有這兩列；2026-11-22 補，#831 第 1 輪第 6 列）。

| 編號 | 日期與做了什麼 | 讀到的 |
|---|---|---|
| P1 | 2026-11-20，一批九篇的取全文。來源：#822 的兩則 2026-11-20 留言、PsychQuant/safari-browser#345 的 2026-11-20 留言 | 視窗裡都是 HTML 分頁時（#345 記的是 17:31–17:38），`documents --json` 的 `blocking_dialog` 多數是 `clear`，偶爾一次 `unknown`／`incomplete`，等一次再讀又是 `clear`。視窗裡出現顯示 PDF 的分頁（Taylor & Francis 那一篇，17:39）之後，那一段時間裡的每一次讀取，整個視窗的每一個分頁都是 `unknown`／`incomplete`、沒有訊息。批次到第 7 篇前後連續四次讀到 `unknown`（其中一次在跑過節奏工具之後），照 SKILL 停下來請使用者看那個視窗；他 17:48 回答畫面上什麼都沒有，之後第 8、9 篇照樣是 `unknown`。從時間看那一次停下多半在 17:39 之後，逐次的先後沒有記錄。機器當時負載很高（load average 60–100），這一點有沒有關係沒有查。當時的讀數沒有逐次記下作用中的分頁；事後對得上的只有存下的分頁清單（見 P2） |
| P2 | 2026-11-21，只讀 `documents --json`、不對任何出版商送請求；視窗有 22 個分頁，其中 6 個是前兩批留下、顯示 PDF 的分頁。來源：#828 的〈量測（2026-11-21）〉 | 作用中分頁不顯示 PDF：`clear`（4 次）。以 `tab focus` 切到一個顯示 PDF 的分頁：整個視窗 `unknown`／`incomplete`、沒有訊息（連讀 2 次）。切到一個 HTML 分頁：`clear`（1 次）。切回原本的分頁：`clear`（1 次）。另外對照先前存下的分頁清單：2026-11-20 與 2026-11-21 讀成 `unknown` 的九份，作用中分頁都是當時 `pdf-shown` 的那一個；2026-11-20 讀成 `clear` 的一份，作用中分頁是 HTML 分頁 |

**P2 更正了 P1 當時的讀法。** 2026-11-20 寫的是「視窗裡一出現顯示 PDF 的分頁，之後每一次讀取都是 `unknown`」，並由此推出「同一個視窗後面需要按的每一篇都會停」。P2 在那一個視窗的八次讀取裡量到的是狀態跟著**作用中的分頁**走：作用中分頁顯示 PDF 時讀成 `unknown`，不顯示 PDF 時是 `clear`。那個視窗一直留著 6 個顯示 PDF 的分頁；視窗裡沒有 PDF 分頁時讀起來是什麼，P2 沒有量（這一句先前寫「不論視窗裡有沒有別的 PDF 分頁」，#822 verify 第 2 輪）。P1 的讀數與這個說法相容（逐次的讀數沒有記作用中分頁，但存下的清單對得上），「後面每一篇都會停」是沒有量過的推論，P2 指向相反的方向；出版商網站上、PDF 分頁出現之後還要按的一篇，仍然沒有量過。P1 裡視窗還都是 HTML 分頁時偶爾讀到的 `unknown` 是什麼造成的，P2 沒有解釋；第 7 篇前後那四次讀取各自的作用中分頁，也沒有逐次記錄。

**沒有量的**（來自 #828）：有對話框或儲存面板開著、同時作用中分頁顯示 PDF 時讀起來是什麼；別的 Safari 版本；作用中分頁顯示 PDF、而要按的是同一個視窗裡另一個 HTML 分頁的情形。
