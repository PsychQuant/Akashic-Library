# 2026-09-29 C2c（#654）與 #578 的 R1 驗證修正

兩組驗證的狀況：
- 各 5 席回報，沒有 HIGH。
- devil's advocate 那一席兩組都沒跑完：撞上 Opus 的週用量上限。之後改用 sonnet 補跑，結果另記在驗證報告。

這一輪修掉兩個 MEDIUM、兩個 LOW、一個 INFO。

## #654

- **MCP 面的 `update_person` 仍先讀 store 才驗欄位參數**（Codex，MEDIUM）。
  - #654 讓只看參數的檢查在讀 store 之前跑，CLI 在 `validate()` 呼叫 `checkUpdatePersonFields`。服務方法 `updatePerson` 本身卻沒有呼叫它。
  - 結果：MCP 呼叫端帶一個不認得的欄位加一個不存在的 person 時，先拿到「找不到 person」，參數錯誤被蓋掉。
  - 改成在 `store.load()` 之前呼叫同一個函式。
- **org 腿的形狀檢查排在長度上限之前**（logic，LOW）。
  - `parseOrgIDSpecs` 逐筆先跑形狀檢查、再擋長度，超長的輸入要先被掃一遍才被拒。
  - 改回先長度後形狀。整批的形狀檢查在讀 store 之前已經跑過，這裡的順序只影響成本，拒絕的集合不變。

## #578

- **測試的讀行 helper 是阻塞讀**（Codex，MEDIUM）。
  - `FileHandle.availableData` 對 pipe 是阻塞呼叫。子行程開著 stdout 卻不輸出時，它會一直等，迴圈的 10 秒期限永遠輪不到檢查。那支位元組預算測試本該最先失敗，卻會掛到 CI 自己的逾時。
  - 改成以 `fcntl` 設 `O_NONBLOCK`、用 `read(2)` 輪詢。
- **兩份讀取迴圈**（logic，LOW）：`readResponse` 與 `readRawLine` 各有一份，而且都會丟掉同一次讀到的第二行。
  - 讀行只剩 `readLine` 一份，`readResponse` 呼叫它再解析。
  - 讀到的第二行留在 `pending`，給下一次用。
- **issue 要的是「源碼掃描守衛」，交付的是真 binary 量測**（requirements，MEDIUM）。
  - 這是刻意的替代：呼叫端付的是 server 實際送出的那一行。源碼字串字面的加總量不到 input schema 的結構與 JSON 編碼，也會把不在那一行裡的字串算進去。
  - 先前沒有寫出來，現在寫進 `mcp-cli-parity` 那一段。
- **doctor 描述裡「CLI 同，只是不另截 20 則」容易讀反**（logic，INFO）。改成「CLI validate 每筆一樣至多 20 則，只是不把總則數截成 20」。

## devil's advocate 補跑之後（兩組都 6/6 席）

DA 那一席改用 sonnet 補跑完成，兩組各多出幾項，這一輪一併修掉。

**#654**
- **`update-person` 的 references 在參數階段與 `--dry-run` 都收下空 digest（以及形狀錯的 digest）**（MEDIUM）。
  - `appendReferences` 用不驗證的 init 組 reference，digest 只在寫入閘的 canary 驗。結果是乾跑說「會改」，真跑以 exit 1 被擋，乾跑成了謊言。
  - 改走 `ProvenanceReference` 的平面 init，也就是 YAML decode 的同一個驗證入口。CLI 因此回 64，MCP 在讀 store 之前就拒絕，乾跑也說實話。
- **第 1 項（Reference* 歸類）沒做，延後只寫在散文**（MEDIUM）。另開 #671，在它的 `### Blocking` 寫明等 #617 釋出那三個檔；`RuntimeFailure` 的 doc 改指 #671，不再寫「另一個 session」這種會過期的事。
- **MCP schema 與 CLI help 只說 digest 是 sha256:64hex**（LOW）。13 處描述補上「0 byte 內容的 digest 拒收」：MCP 7 處、CLI 6 處。
- **收緊載入謂詞沒有自己的 format bump**（LOW）。`zero-instance-guards` 第 41 列補一段部署視窗：
  - 舊 binary 仍收空內容 digest，它寫進共用 store 的記錄會被新 binary 隔離。
  - format 21 的 marker 升上去之後，舊 binary 整個拒開 store，視窗隨之關閉。

**#578**
- **`resolve_people` 的描述把「其他腿該筆略過」寫成通則**（MEDIUM）。split_author／un_split／drop_author／attribute_org 實際是整批拒絕，改成逐腿點名。「無法唯一定位」的三類原因也寫出來：key 重複、與另一筆共用 id、檔案寫入時一定會被拒。
- **`resolve_venues` 的 undecided 漏了 venue key 重複也會略過**（#670）。補上。
- **預算的推導對不上出貨樹**（MEDIUM）。
  - 39,164 是補上 #670 兩個旗標的描述之前量的；`ee29fe47` 出貨時實測 39,285。照裁決的公式，39,285 會得 50,000，超過單一 MCP 輸出的 48 KiB。
  - 預算維持 49,000（較嚴、且在 48 KiB 之下），規則與測試註解照實寫出兩個數字，待使用者確認。
  - 2026-09-29 的樹（33 個工具）實測 43,021 bytes。
- **被移到 CLI help 的細節，有幾處 MCP 呼叫端讀不到**（LOW）。
  - judge 補回 #648 的拒絕類別：寫入前整個寫入集合先驗，寫出後超過 8 MiB 即整批零寫入。
  - `add_names` 的四個回應鍵各寫一句意思。
  - 描述與 payload 鍵的守衛只涵蓋 `resolve_people`，這一格記為後續，不在這一輪擴。

## 測試與負控

- `ServiceArgvBeforeStoreTests` 加兩格：`updatePerson` 帶不認得的欄位、帶不合法的 ORCID，沒有 store 時要拿到參數錯誤。修之前兩格都紅，拿到的是「找不到 person」。
- `StdioE2ETests` 加兩支：
  - `testLineReaderTimesOutWhenThePeerStaysSilent`：`/bin/sleep 30` 開著 stdout 不輸出，期限 0.5 秒，要在 5 秒內以逾時結束。
  - `testLineReaderKeepsTheSecondLineOfOneRead`：一次到達兩行，兩行都拿得到。
- 負控兩組（反向編輯、還原後 `cmp` 相同）：
  - 讀取改回阻塞：逾時那支失敗。子行程 30 秒後結束時以 EOF 收場，而不是逾時。測試關掉父行程的寫端，所以不會永遠掛住。
  - 丟掉第二行：兩行那支失敗。
- `ServiceArgvBeforeStoreTests` 再加三格：retrieval 帶空 digest、帶形狀錯的 digest、judgement 的 rests_on 帶空 digest，沒有 store 時都要拿到參數錯誤。修之前三格都紅（紅測試跑出 3 個失敗）。負控：retrieval 改回不驗證的 init，兩格轉紅，還原後 `cmp` 相同。
- `StdioE2ETests` 17 支、`ServiceArgvBeforeStoreTests`、`ServiceArgvExitCodeTests`、org 未決與判定、消毒兩支守衛，共 112 支全綠。
