# 最弱的那一列補掉一格——動手的理由是「只差一個參數」，不是「等到了實例」

2026-08-28，#394。`update-venue` 與 `akashic_update_venue` 兩面同時新增 ISSN 寫入。

## 這一格為什麼是「最弱的」

#394 把識別碼升格為一等公民，但**只給了遷移路徑**——`migrate-identifiers` 從 `fields`
殘留搬值。查到一個**新的** ISSN（不在任何殘留裡）時，沒有任何面寫得進去，唯一的路是
手改 YAML。該 issue 自己寫著這是 `replace-endnote-and-zotero` 第 4 條要防的形狀：

> 而且它是**安靜的**失敗，因為每次個別繞過都看起來很合理。

同一天稍早，手改 YAML 的嘗試差點弄丟 `dweck1975role` 的 DOI（錨點靜默不匹配而移除
已執行，`git checkout` 救回）。那不是「小心一點就好」——手改沒有型別檢查、沒有
round-trip 驗證、沒有原子性。

## 動手的理由與 issue 寫的觸發條件**不同**，這要說出來

issue 寫的是「出現第一個查到識別碼但寫不進去的實例時」重新裁決。**本次不是那個實例**
——沒有人今天查到一個新 ISSN。

動手的理由是相反的：`Venue.issn` 的欄位、型別（`ISSN`）、正規化都**已經存在**，
而只差一個參數。把它留著等一個實例，等於讓那件事在下次真的發生時才被修，而它的失敗
方式是安靜的。

其餘三格（`add_venue`／`add_organization`／`create_entry`）維持原觸發條件——它們要的
不只是參數，還有形狀裁決（`person.orcid` 走 generic `fields` object，而那三個沒有對應
通道）。

## 三個刻意的選擇

| | 選擇 | 理由 |
|---|---|---|
| **語意** | append，不是替換 | ISSN 本來就是清單——print 與 electronic 是兩個真的號。整組替換會讓「補一個」變成「先讀再全寫」，而那是 #306 對 `add_names` 已經裁決過不提供的形狀 |
| **相等** | 看正規形 | `0003-066x` 與 `0003-066X` 是同一個號。與 `IdentifierMigration.normalizedUnique` 同一條規則——兩面若用不同的相等，對「這本刊有幾個 ISSN」會給出不同答案 |
| **不合法** | 整批拒絕，零寫入 | 與同函式既有的 `type` 值域檢查同型。識別碼尤其如此——它**終結指涉**，一個壞掉的號寫進去之後，用它做的每一次配對都建立在假的身分宣稱上 |

## 三個測試，其中一個是負向的

- `testUpdateVenueAppendsISSN` — 那條路存在
- `testUpdateVenueDeduplicatesISSNByNormalisedForm` — 大小寫異寫法不是新號
- `testUpdateVenueRejectsMalformedISSN` — **拒絕必須零寫入**（不是「收下來再說」）

`mcp-cli-parity` 的兩處已更新：MCP 表那一列記錄新參數，「識別碼寫入面的裁決」那一節
把 `update_venue` 從缺席清單劃掉並寫明剩下三格的條件不變。

## 同日稍晚：那一列關閉了

四格全部補齊——`update_venue.add_issn`、`add_venue.issn`、`add_organization.ror`、
`create_entry` 的 `doi`／`pmid`／`isbn`。

**四格用同一個理由**：欄位、型別、正規化都已存在，只差一個參數。而建檔時本來就知道
刊物的 ISSN、機構的 ROR、論文的 DOI；少了它得「先建再更新」——一次操作變兩次，中間有
一個識別碼不在的狀態。

### 形狀刻意不一致，因為被建模的東西不一樣

| | 形狀 | 理由 |
|---|---|---|
| `issn` | 清單 | print 與 electronic 是**兩個真的號** |
| `ror` | **純量** | 一個機構只有一個 ROR ID |
| `doi`／`pmid`／`isbn` | 清單 | 一筆作品可以有多個 DOI（實測 37 組同題同年不同 DOI）|

### 建檔面的拒絕比更新面更強

若守衛只擋識別碼而讓記錄建了出來，結果是一筆「呼叫端以為帶識別碼、實際沒有」的記錄
——比明確失敗更糟。三個負向測試釘住這一點，其中兩個斷言「**連記錄本身都不該存在**」。

### `.bib` 匯入路徑刻意不帶

`.bib` 的 `DOI = {...}` 進 `fields`，走**殘留路徑**由 `migrate-identifiers` 升格。
在匯入端順手升格會製造第二條升格路徑，而它對「解不了的 token」的處置與遷移端不同
（遷移把它留在殘留並報出來）——**那正是同日稍早修掉的那個 bug 的形狀**：一個 `return`
綁兩個決定。

### 一個測試假設被實測推翻

我寫 `isbn: ["978-0-13-441969-5", "0-13-441969-3"]` 並斷言 count == 2，理由取自
`IdentifierMigration.absorbsMultipleValues` 的 doc：「ISBN 的多值是真的：
978-0-13-441969-5 與 0-13-441969-3 是同一本書的 ISBN-13 與 ISBN-10」。

**實測收斂成 1 個**，而那是對的——ISBN-10 與 ISBN-13 是同一本書的兩種**編碼**，
正規化後相同。那句 doc 的「多值是真的」指的是**精裝／平裝／電子版**的不同號，
不是這一對。測試改成斷言 1 並把這個區分寫進註解。
