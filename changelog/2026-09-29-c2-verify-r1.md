## 改了什麼

- **#641：兩筆都還是 legacy 的 person 共用同一個 id**（Codex，HIGH）。目的檔 `entities/<id>.yaml` 此刻不存在，load 對每一筆的 #631 檢查各自通過；第一筆搬進去之後，第二筆才在寫入當下撞上它，preflight-then-write 就在中途撕裂。load 現在另外跨記錄比 legacy 那一段的 id，把兩筆都標成寫入時會被拒（`fileSituation.unwritableReason`），理由點名另一筆與那個 UUID。
  - 這仍是 `unlocatablePersonKeys` 的第 2 類，不新增類別。它的 doc 原本論證「共用 id 必然有一筆在 `entities/`」，對兩筆都在 legacy 的情形不成立，這一條已補上。
  - 住在 `entities/` 的一筆與 legacy 共用 id 時，目的檔已存在，既有檢查照舊擋下 legacy 那一筆。
- **import-wos 的寫入迴圈沒有 preflight**（DA，HIGH）。先前逐列寫入、沒有收容：第 N 列在寫入當下被拒（#648 的讀取上限，或任何寫入閘）時，前 N−1 列已經落盤，報告也隨 throw 丟掉，和 #641 是同一個撕裂形。現在先收集整個寫入集合，逐筆 `preflightWrite` 全部通過才寫；任一筆不過即擲出、零寫入，錯誤訊息具名那一筆。
- **authorize-names 同樣缺 preflight**（DA，MEDIUM）。#641 只擋了無法唯一定位那一類；一筆指定之後超過讀取上限的 person，仍會在中途被拒，而前面的指定已落盤、marker 沒 bump。寫入前先對整個寫入集合 `preflightWrite`。
- **#575 repair-venue-names 的寫入前置是手寫的子集**（Codex、regression、DA，HIGH）。它只做了 `assertVenueWritable` 與不帶 `replacing:` 的 encode，少了 #631 的目的檔檢查。改成直接呼叫 `store.preflightWrite(v)`：這就是 `writeVenue` 在寫入當下跑的全部前置，同一件事只有一份描述。
  - **誠實邊界**：已載入的 venue，目的檔就是它自己，所以這兩條路徑只在「載入之後、寫入之前」檔案被換掉的競態下才會分岔。這一格沒有辦法用行為測試重現，修的是一致性。
- **#581 的 `truncated` 不反映單則被截**（Codex，MEDIUM）。先前只有整則被 48 KiB 預算省略時才設 true；一則超過 1,000 字元的訊息被截短，呼叫端卻以為拿到了全部。截短抽成 `AkashicService.detailMessage`，回傳訊息與「有沒有截」，有截就設 `truncated`。今天各族的訊息在產生端就已截過（實測 268／368 字元），這一格守的是未來的訊息。

`zero-instance-guards` 第 39、40 列同步寫明這兩件事：
- 三個漏掉的多檔寫入者現在都先 preflight，先前的誠實邊界沒有列它們，是漏看、不是裁決。
- 兩筆 legacy 共用 id 的處置。

## 記錄、不改

- **`plannedWrite` 四種型別的檢查順序不一致**（logic、DA，LOW）。Entry 先查 #631 目的檔再 encode；其他三種先 encode 再查目的檔。兩道檢查互相獨立，任一道擲出都是零寫入，差別只在「同時違反兩者時先報哪一個」。
- **驗證用的 diff 含了不屬於本 cluster 的 hunk**（regression，INFO）。這是產生 diff 時把整段 batch10 範圍一起包進去的產物，不是實作的 scope creep。
