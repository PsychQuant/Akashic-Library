## Context

`attachments` 目前有兩個種類：`zotero`（相對 Zotero 資料目錄）與 `pool`（相對某個 attachment pool root）。實測全庫 1808 筆記錄中，51 筆帶 `zotero` 附件、**`pool` 為 0 筆**；程式面只有列舉成員、YAML 鍵域驗證、以及 Zotero 匯入時的保留邏輯，**沒有任何 pool root 解析、沒有開檔、沒有完整性檢查**。

`pool` 的設計意圖是「指向外部既有檔案而不複製」。該意圖已被推翻：位元組要複製一份進 store，且檔案要住在 Akashic 裡而非指向別人的儲存。

另一側，`references` 是**欄位層級**的 provenance（規範上「可附著於具名欄位」），目前掛在 person 與 organization 記錄。work 記錄沒有任何欄位能指向 `sources/` 的已儲存內容。

## Goals / Non-Goals

**Goals:**

- 讓 work 記錄能以 digest 指向「是本作品副本」的已儲存內容。
- 把「可 ingest 的內容一律以 digest 引用、不以路徑引用」寫成規範，使 `pool` 這類路徑引用不會再長回來。
- 移除 `pool`，並以 format 提升誠實反映其 breaking 性質。

**Non-Goals:**

- **不**提供把檔案存進 `sources/` 的使用者入口（CLI 或 MCP）。本變更交付的是**連結契約**，不是擷取工具；擷取入口與 `sources/index.jsonl` 的寫入路徑另案處理。
- **不**遷移既有 51 筆 `zotero` 附件。`zotero` 種類在本變更後仍然合法，其日落屬另案。
- **不**改變 `references` 的欄位層級語意，也不把兩者合併。
- **不**為引用加上角色分類（全文／補充材料）。

## Decisions

### 記錄層級的 source 引用不重用欄位層級的 references

`references` 回答「這個欄位的值以那份內容為據」。一份論文 PDF 不是任何單一欄位的證據，它是整筆記錄所描述之作品的呈現物。兩者的關係項不同：前者是「值 ← 證據」，後者是「作品 ← 副本」。

考慮過的替代方案：擴充 `references`，用一個全稱的欄位名（例如代表整筆記錄）表示記錄層級。否決，因為那會把欄位層級契約的判準弄糊——一旦允許「欄位名可以不是欄位」，該契約就失去可機械檢查的邊界。

### 引用存在記錄側，反向現算

連結存在 work 記錄上（記錄指向 digest），而非存在內容側的索引上（索引指向 citekey）。反向查詢「這份內容屬於哪些記錄」由掃描記錄現算，不另存第二份。

理由是資訊抵達的次序：內容先被取得、記錄後被建立。內容抵達當下沒有 citekey 可填；建立記錄時 digest 已經存在。只有記錄側能在對方尚未存在時誠實記下。

考慮過的替代方案：把清單放在內容側的索引檔。否決，理由如上；且兩側都記會製造兩份可能分岔的真相。

### 移除 pool 而非改造成機器本地對照表

考慮過保留 `pool`、但把 pool root 移到機器本地設定，使其成為「這台機器上這個檔案在哪」的對照層。否決有兩個理由：其一，位元組既然要複製進 store，該對照層沒有使用者；其二，`pool` 目前位於受版控的命名空間，而檔案系統路徑是機器本地事實，兩者本來就不相容。

移除的另一個依據是可刪除性檢驗：今日移除 `pool` 會壞掉的東西是零——零筆資料、零程式路徑、零使用者流程。**但這只證明移除是安全的，不證明其承載的需求是假的**。該需求（不想為了編目複製大檔）在本變更中是被**明確拒絕**的，不是被忽略的。

### store format 提升到 8

`attachments` 元素的鍵域是封閉集合，未知種類會導致整檔 quarantine 而非保留。因此縮減鍵域是 non-additive：一份帶 `pool` 附件的記錄被新 binary 讀到會整檔 quarantine。

雖然實際受影響資料為 0 筆，**bump 的依據是鍵域的嚴格性，不是資料量**。把它當死碼移除、不 bump，會讓 refuse-if-newer 這道防線在下一次真的有資料時失效。

### 欄位放在 akashic namespace 下

放在 `akashic` 之下而非記錄頂層。頂層是書目面向、由匯入來源擁有並可被覆寫；`akashic` 命名空間依既有契約由本專案與使用者擁有，匯入絕不觸碰。副本清單是使用者的知識，不是書目來源的欄位。

## Implementation Contract

**Behavior**

1. work 記錄可在 `akashic` 命名空間下攜帶一個 digest 清單，宣告這些已儲存內容是本作品的副本。
2. 清單中的 digest 若在本機沒有對應的已儲存內容，記錄**仍然載入成功**，該狀態被回報為「內容不在本機」，與「記錄格式損壞」是兩種不同的狀況。此行為沿用既有 provenance 契約，本變更不新增語意。
3. 讀到 `pool` 種類的附件時，載入以錯誤拒絕，錯誤訊息指名合法鍵域只剩一個種類。
4. 對 format 低於 8 的 store，寫入含此清單的記錄被拒絕。
5. format 8 的 store 被僅支援到 7 的 binary 開啟時，整體拒絕開啟並要求升級。

**Interface / data shape**

清單為字串序列，每個元素是一個內容 digest，沿用既有 provenance 引用的 digest 文法與驗證函式，不另立格式。序列可為空；空與缺席等價。

**Failure modes**

- digest 字串不合文法：以具名欄位錯誤拒絕，訊息指出是哪個欄位。
- digest 合法但本機無內容：**不是錯誤**，載入成功並回報為缺席狀態。
- 出現 `pool` 鍵：以附件鍵域錯誤拒絕（既有錯誤型別，訊息內容更新）。
- 對舊 format 寫入新欄位：write gate 拒絕，訊息指出所需 format。

**Acceptance criteria**

- 帶副本清單的記錄可完成序列化與反序列化的來回，內容逐字不變。
- 不合文法的 digest 被拒絕，且錯誤訊息包含欄位名。
- 帶 `pool` 附件的 YAML 被拒絕，錯誤訊息不再提及 `pool` 為合法值。
- 對 format 7 的 store 寫入含副本清單的記錄被拒絕。
- 僅支援 format 7 的載入路徑遇到 format 8 的 store 時整體拒絕。
- 既有的 51 筆 `zotero` 附件在本變更後仍可正常載入（回歸保護）。
- 格式規格書中的附件章節、命名空間契約表、以及 format 版本沿革都已更新，且不再出現 `pool` 為合法種類的敘述。

**Scope boundaries**

*In scope*：記錄側副本清單欄位、其驗證與 write gate、`pool` 的移除、format 提升到 8、格式規格書相應章節、上述驗收所需測試。

*Out of scope*：把檔案存進內容儲存區的使用者入口（CLI／MCP）、內容索引 sidecar 的寫入路徑、既有 `zotero` 附件的遷移或日落、副本的角色分類。

## Risks / Trade-offs

- 本變更不打通「手上有 PDF → store 認得它」的完整流程 → 交付的是連結契約；擷取入口是另案。驗收條件**不宣稱**流程已打通，避免誤判完成度。
- 0 筆資料卻做 format 提升，日後可能被視為過度謹慎而被「順手降回去」 → 在格式規格書的版本沿革中寫明：依據是鍵域的嚴格性與整檔 quarantine 行為，不是資料量。
- 副本清單與欄位層級 provenance 都指向同一個內容儲存區，日後可能被誤判為重複而合併 → 在規格中寫明兩者的關係項不同，並保留本文件中拒絕合併的理由。
- 移除 `pool` 使「引用外部既有檔案而不複製」變成不可能 → 這是刻意的取捨，非疏漏；需求被明確拒絕並記錄於本文件與專案規則。

## Migration Plan

1. 提升 format 至 8。因全庫 `pool` 附件為 0 筆，**無資料遷移工作**。
2. 舊 binary 讀到 format 8 的 store 時，由既有的 refuse-if-newer 防線給出「請升級」，不會誤讀。
3. 若日後遇到外部手寫的 `pool` 附件，載入以錯誤拒絕；本變更不提供自動轉換，因為路徑無法可靠地轉成 digest（需要讀取該檔案，而該檔案可能不存在）。

回滾策略：本變更未刪除任何檔案，回滾為還原列舉成員、鍵域驗證、format 常數與規格書章節。因無資料遷移，回滾不需資料修復。

## Open Questions

- 副本清單是否需要區分角色（全文、補充材料、預印本）？目前不加：內容索引 sidecar 已逐份記載媒體型別與備註，足以辨別。若日後需要，加欄位是 additive、不需再次提升 format。
- 既有 51 筆 `zotero` 附件的日落時程與遷移方式，待另案決定。
