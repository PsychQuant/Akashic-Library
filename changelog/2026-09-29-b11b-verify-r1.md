# 2026-09-29 b11b（#607、#610、#609）R1 驗證修正：legacy 的重複也是宣稱、宣稱者只有一份定義、裁決台三個動作同一條守衛

R1 驗證（四個 Claude 席與 Codex 席）對 `zotero-legacy-match-order`（#607）、`zotero-source-single-claim`（#610）、`orphaned-additional-sources`（#609）三份 changelog 給了 5 個 MEDIUM、多個 LOW。發現是審查者的輸出，逐條在程式碼上核對過（重現用測試寫在下方）；三條的立論都成立，兩條有校正（見各項）。

## 發現與處置

### 1. 兩筆以上 legacy 同裸 key 的拒絕被「其他 library 已持有」繞過（Codex MEDIUM，#610／#607）

**核對**：成立。`ZoteroImporter` 的 legacy 分支把 `guard legacies.count == 1` 放在 `if !claimedByOtherLibrary` 裡面，別的 library 也持有同一個裸 key 時數量檢查整個不跑，條目照走「建新 entry」，報告也沒有歧義。以測試重現：兩筆 legacy＋另一筆持有 `5:KEYART01`、匯入 `1:KEYART01`，修之前新建了 `cheng2025bidentifiability`、`ambiguousSourceClaims` 為空。

**改了什麼**：legacy 分支先問「有幾筆舊檔宣稱這個裸 key」（兩筆以上→報、略過、不新建），只有唯一一筆時才問「其他 library 是否持有」。`ZoteroImporter.swift`。

### 2. 宣稱者的定義不是一份（logic／requirements／regression／DA 四席 MEDIUM，#610）

**核對**：成立，DA 的校正也成立（使用者風險不是靜默資料錯——匯入每次都印出來——實際傷害是文件與提示不實、處置無路可走）。`ZoteroSourceClaims.claimants` 跳過沒記 `library_id` 的來源，而匯入端在行內另有一份 `legacies.count == 1`：宣稱者有兩份定義，legacy 那一半 `crossRecordIssues` 看不到。CLI `import-zotero` 對每個 `?:` 鍵印「處置見 akashic validate 的跨記錄警告」、`docs/store-format.md` §2.5.3、`mcp-cli-parity`、`zero-instance-guards` 第 46 列都說「只有一份」，對 legacy 一半為假。重現：兩筆沒記 `library_id` 同裸 key，`validate` 印全綠。

**改了什麼**（整合者裁定：把 legacy 桶納入同一個 helper，匯入端改用它）：
- `ZoteroSourceClaims.claimants`：沒記 `library_id` 的**主來源**進 `?:<zotero_key>` 桶；沒記 `library_id` 的附加來源仍不算（匯入端對回不了它、合併閘也不讓它進來）。舊檔與某個 library 的來源同裸 key 仍不算多筆宣稱。`key(libraryID:zoteroKey:)` 改收 `Int?`，`nil` 就是 `?:`。
- `ZoteroImporter`：拿掉行內的 `legacies.count`，legacy 桶與 composite 用同一個 `claimants`；`legacyByBareKey` 只在 `claimants` 說「恰好一筆」時才被取用。
- `crossRecordIssues`：兩種鍵都報 warning；legacy 那一桶的標籤寫成「沒記 library_id 的 Zotero 來源（裸 key「K」）」，出路兩條都寫對——同一篇就 `record-divergence`／`resolve-divergence` 合併（測試證明兩筆都沒記 `library_id` 的舊檔走得通），記錯了就在 YAML 拿掉那個來源或補上它真正的 `library_id`。
- 文字對齊實作：`docs/store-format.md` §2.5.3、`mcp-cli-parity` 的 `akashic_import_zotero` 列、`zero-instance-guards` 第 46 列（改寫、不加新列；量測段改成可貼上執行的腳本，grep 改成同時涵蓋兩種標籤）。CLI 的提示現在是真的，文字不必改。

### 3. 同一筆 entry 被 load 讀兩次時重複計數，且導向錯誤處置（regression／DA LOW，#610）

**核對**：成立。`load()` 在兩份並存（#631）時把同一個 id 讀到兩次，`claimants` 的 `seen` 只在單一 entry 之內去重，validate 印「被 2 筆 entry 宣稱（x, x）」並建議把一筆 entry 和它自己合併；legacy 表依出現次數 append，同一筆 legacy 的兩份複本被算成兩筆、被匯入端報成歧義。

**改了什麼**：`claimants` 以 entry id 去重（兩個桶都是）；警告的名單改用 id → entry 的查找表（第一次讀到的那份），不再用 `entries.filter` 撈全部——否則一筆讀到兩次的 entry 加一筆真的攣生，名單會是三個 citekey。兩筆**不同**記錄共用同一個 id 時只看先讀到的那筆（那個形狀有自己的診斷，`unlocatableCitekeys`）。

### 4. 合成鍵的兩個產生者（logic LOW，#607／#610）

**核對**：成立。索引表與孤兒偵測仍在行內內插 `"\(lid):\(key)"`，`ZoteroSourceClaims.key` 只服務 `claimants` 與查找鍵。**改了什麼**：`ZoteroImporter` 裡所有產生來源鍵的位置（兩張索引表、`importedComposite`、主來源與附加來源的孤兒偵測，共五處行內內插）改走 `ZoteroSourceClaims.key`。這一項不在整合者的清單內，順手收——它與第 2 項是同一件事（同一份描述）。

### 5. 裁決台的垃圾桶與脫鉤沒有「無法唯一定位」的拒絕（security MEDIUM，#609）

**核對**：成立，DA 的校正也成立（那個缺口在本 diff 之前就存在，`resolve` 自 #35 就沒有；垃圾桶走系統 Trash 可救回，`.detach` 的 `writeEntry` 對兩份並存會被 #631 擋；實際風險是 LOW）。但 #609 把 `.orphaned` 的母體擴大、且同檔新增的兄弟函式有守衛，三個 App 寫入動作的定位守衛不一致在這個 diff 裡可見。

**改了什麼**：`OrphanModel.resolve` 在讀盤後、形狀檢查之前加同一條 `unlocatableCitekeys` 拒絕（重用 `AdjudicationError.unlocatableCitekey`）。

### 6. 「拿掉已刪除的附加來源」要拿掉使用者看到並確認的那一組（logic LOW，#609）

**核對**：成立。`removeAll { orphanedAt != nil }` 拿掉動作當下全部已刪除的來源；清單顯示與按下按鈕之間若一次匯入又標了另一個，那個沒被看過的也被拿掉，只在事後的報告裡才說。

**改了什麼**：`removeOrphanedAdditionalSources(citekey:reason:seen:)` 多一個必填的 `seen`（`Entry.orphanedAdditionalSourceKeys`，按下按鈕那一刻清單上的那一組來源鍵）；動作當下磁碟上的那一組與它不同（多了、少了都算）就拒絕、零寫入，新錯誤 `orphanedSourcesChanged` 兩組都列出。對話框的訊息列出將拿掉的來源。

### 7. 形狀重驗在慢速 git 閘之前、寫入卻用閘之前的快照（security LOW，#609）

**核對**：成立，窗口小。這一項不在整合者的清單內，但它與第 6 項在同一個函式、同一段流程，順手收。**改了什麼**：git 閘通過後再讀一次那筆記錄，與快照不一致就拒絕（新錯誤 `changedDuringCheck`），不整檔覆寫。測試接縫 `OrphanModel.afterRecoverabilityGate`（internal，只給測試模擬閘的時間窗）。

### 8. 失敗時對話框關閉、已打的理由遺失；空理由時破壞性按鈕沒停用（logic LOW，#609）

**核對**：成立。**改了什麼**：抽成值型別 `RemovalReasonDraft`（`AkashicAppKit`，可在沒有 SwiftUI 的測試裡驗）：同一筆重開保留理由、換另一筆清空、成功後清掉；`isSubmittable` 為假時「拿掉」按鈕 `.disabled`。`OrphanView` 綁它。**沒做**：三個 `.alert` 疊在同一個 view、結果提示與關掉輸入提示在同一個 transaction 的 SwiftUI 脆弱性——沒有 UI 自動化測試可以驗，硬改的風險大於收益，記在下面的邊界。

### 9. `ambiguousSourceClaims` 的 CLI 輸出與 MCP payload 沒有測試（requirements LOW，#610）

**改了什麼**：`ZoteroReportCLITests`（新，AkashicCLITests，真 binary，最小 zotero.sqlite）與 `ImportZoteroReportSurfaceTests`（新，AkashicKitTests，`AkashicService.importZotero`）。釘住：CLI 標題行與逐行 `⚠ 1:KEYART01：a, b`、legacy 桶 `⚠ ?:KEYART01`，以及標題行指向的 validate 警告真的存在；MCP 鍵只在非空時出現、legacy 桶、鍵消毒相撞（120 字元前綴，#669）留第一個且不 trap。

### 10. doctor 的兩個新輸出沒有測試（requirements LOW，#609）

**改了什麼**：MCP `akashic_doctor` payload 的 `orphaned`／`orphanedAdditionalSources`（`ZoteroLinkStateTests`，含空清單）；CLI `doctor` 的兩行（`ZoteroReportCLITests`，真 binary，四個形狀）；`DoctorSinglePathTests` 的必讀清單加兩個新欄位、禁止清單加「自己從主來源推導 orphan」。

### 11. MCP 工具描述沒提 `ambiguousSourceClaims`；index rebuild 失敗的分支丟掉整份新報告（DA LOW，#610）

**核對**：成立，並查到後者的程式註解（「R10：rebuild 擲錯不得吞掉整份 import report」）自己就與行為不符——錯誤訊息只帶四個計數。**改了什麼**：`akashic_import_zotero` 的描述點名 `ambiguousSourceClaims`（只在非空時出現）並說 index rebuild 失敗時錯誤訊息帶完整報告，tools/list 回應 43,560 bytes（預算 49,000，`testToolsListResponseStaysWithinByteBudget` 綠）。報告 payload 抽成 `importReportPayload`，成功與失敗兩條路徑共用，失敗時把整份放進錯誤訊息——契約仍是 `throws`（isError），不改成回成功。

### 12. 過期的文件（regression INFO）

`AppState.orphanedEntries` 的 doc comment 仍說判準是 `provenance?.orphanedAt != nil`；README 的「Orphans 三選」。**改了什麼**：兩處改寫。

## 不修的（只記錄）

- **附加來源沒記 `library_id` 時再匯入仍重造 twin**（DA LOW）：`secondaryByComposite`、`claimedLibrariesByBareKey`、`claimants` 都略過它，YAML decode 接受這種形狀、`Entry.validate()` 沒有對應檢查；程式註解把它寫成「由合併閘保證的不變式」，但合併閘只擋 `resolve-divergence`，手改或舊檔不受約束。零實例（live store 沒有沒記 `library_id` 的附加來源），另開 issue。
- **過期的 orphan 標記在不明宣稱時也被略過**（DA LOW）：被多筆宣稱的來源，本趟連 orphan 標記的清除也不做，Zotero 端復原後兩筆的 `orphanedAt` 都還在，App 的 Orphans 頁會把它們列為「Zotero 端已刪除」，歧義只出現在跨記錄警告。損害有界（垃圾桶可救回、動作當下重讀盤）；動作會被本次的定位守衛擋下的只有兩份並存那一種。另開 issue。
- **「與 Zotero 脫鉤」對新形狀做無理由、無 git 閘的移除**（DA LOW）：`OrphanModel.resolve` 的守衛在 #609 改成 `zoteroLinkState == .orphaned`，於是「沒有主來源、附加來源全部已刪除」也能走脫鉤，整批拿掉已刪除的附加來源，不要求理由、不檢查 git；同一個裁決台新增的移除動作兩者都要。這是 #605 R1 的使用者裁決（脫鉤不帶閘），本次**只在 `two-kinds-of-edits` 那一列明講「#609 把這個缺口延伸到新形狀」，不改行為**，待使用者決定要不要補閘。
- **index 的 `orphaned` 欄語意改了、沒有 schema bump**（logic／regression／DA INFO）：目前沒有任何讀者（`Sources`、`Tests`、plugin、docs 都 grep 過），沒有實際後果。
- **警告迴圈的效能**（security LOW）：對每個被多筆宣稱的來源掃全部 entries 的 `filter` 已因第 3 項改成查找表而消失（O(N) 建表＋每個來源 O(宣稱者數)）；**警告則數仍沒有上限**、沒有 `perRecordCapSummaryPrefix` 那種概括句——現實威脅面小（store 是使用者自己的 git repo），不動。
- **`ambiguousSourceClaims` 沒有筆數或位元組上限**（security INFO）：與相鄰的 `authorsPreserved`、`quarantineConflicts` 同慣例，不是回歸；`mcp-cli-parity` 的 `akashic_import_zotero` 列明寫這個差異與重開條件。
- **#609 沒有 zero-instance 列**（requirements／regression）：建議的列寫在最終報告裡，由整合者加。
- **匯入時同一趟內兩個 library 的同裸 key 條目，新建與 legacy 認領依 `items` 順序**（logic INFO）：「其他 library 已持有」由載入快照算、不隨本趟更新，是 #607 之前就有的行為，不在範圍內。
- **App 的 recoverability 前置檢查與 `AkashicService.assertRecordsRecoverable` 只共用內層函式、理由上限 4,096 是字面**（regression LOW）：兩個 target 互相不能 import，收斂要把外層 wrapper 與常數搬進 StoreIO，動到 `AkashicService`；另開 issue。

## 誠實邊界

- **SwiftUI 層沒有自動化測試**：`OrphanView` 綁 `RemovalReasonDraft`、「拿掉」按鈕 `.disabled`、對話框訊息列出來源，這些只有嚴格建置與 kit 層對 `RemovalReasonDraft`／`removeOrphanedAdditionalSources` 的測試，沒有人在畫面上點過。三個 `.alert` 疊在同一個 view 的脆弱性沒動。
- **`seen` 是必填、比對是集合相等**：一個做法是「縮到交集」（只拿掉使用者看過而且現在仍已刪除的），本次選拒絕——縮減會讓使用者以為拿掉了他確認的那一組。使用者可以翻。
- **legacy 桶的宣稱者只看主來源**：沒記 `library_id` 的附加來源不進任何桶（第 2 項的第三條），它們的重複既不被匯入端擋、也不被警告。
- **兩筆不同記錄共用同一個 id 時**，`claimants` 只看先讀到的那筆；那個形狀由 `unlocatableCitekeys` 診斷，不靠這裡。
- **index rebuild 失敗時錯誤訊息變長**（整份報告的 JSON）；sink 端仍會截，極端大的報告在錯誤裡被截斷，成功路徑不受影響。
