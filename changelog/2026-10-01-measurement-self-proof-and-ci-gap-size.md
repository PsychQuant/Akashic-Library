## 守衛檢查它（`zero-instance-rows-audit`，不加新的列）

只改文字，下一個人會再漏一條：#710 R1 verify 一次找到二十多條，而每一輪 verify 都是靠人逐條讀。`zero-instance-rows-audit` 本來就讀這份檔，所以加第五條失敗路徑（`selfProofIssues(in:)`，`ZeroInstanceRowsAudit.swift`）：

## 已知缺口清單記缺口大小（#711 第 2 項）

使用者（經主 session）的決定，保守且可逆：**清單記每一條缺口被接受那一刻的大小；缺口變大時守衛轉紅，要求重新確認。縮小維持綠。**

### 為什麼

清單原本只記「哪個守衛、哪個樣式、哪張 issue 追蹤」。issue 接受的是「那一刻的那些檔」沒有 CI 跑這支守衛；範圍長了新檔，那些新檔沒有人看過，而 rc 仍是 0——接受從一個具體的缺口悄悄變成任意大小的缺口。

### 做了什麼

- **缺口大小**＝守衛已經印的那個數：宣告範圍那一行的 `CI 未覆蓋 N 個`（`uncovered.count`），**不是**前面的「不在受保護集合 M 個」。
- **清單改成四欄**：`<守衛> <樣式> #<issue> <缺口大小>`，TAB 分隔；第四欄是正整數、不以 0 開頭、至多 7 位（`\A[1-9][0-9]{0,6}\z`）。0 不是缺口（大小為 0 就是沒有缺口，該拿掉那一條）。**只收四欄**：三欄的舊格式是格式不對（`no-compat-fallback`：不留兩種讀法）。
- **變大**：現在的 `CI 未覆蓋` 超過記錄值 → `fails`（rc=1），scope 行的標記是 `✗`，訊息寫「已知缺口變大」、記了多少、現在多少、多出幾個，並要求重新確認——確認新檔也可以不跑這支守衛之後，把第四欄改成現在的數、回 issue 記一筆；或補 CI 的 `paths:` 讓缺口消失並拿掉那一條。
- **相等**：`⊘`，rc=0，行尾多一句「（N 個）」。
- **縮小**：`⊘`，rc=0，行尾建議把第四欄改成現在的數（`縮小了，建議把第四欄改成 M`）。**不擋**：縮小是好事，不改的代價是之後再長回來時，到記錄值為止都不會出聲。
- scope 行對有列管的條目多印「｜清單記 N 個」，讓人看得到兩個數字。
- 檔頭（`.githooks/acknowledged-ci-gaps.txt`）寫明格式、量法與處置；`TriggerCoverage.swift` 的 doc comment 同步。

## 誠實邊界

- **缺口大小只比「CI 未覆蓋的檔數」**，不比檔名。有人刪一個舊檔、同時加一個新檔，數字不變、守衛不出聲。這是計數的固有限制；要擋它得記檔名清單，那是另一個量級的決定（清單會跟著檔案增減改動），這一輪沒做。
- **縮小不擋**。使用者的決定是「縮小維持綠」；`⊘` 行只建議改小。
- **issue 號與缺口大小都只驗形狀**，不查 issue 存不存在、第四欄記的數是不是真的被接受過——那一半仍是人在 issue 裡留的記錄。
- **量測指令的閘只驗「在不在」**，不驗片段是否獨有（見上）。第 70 列、第 71 列區塊那種「正對照」的寫法是約定：守衛認字面 `正對照`，不驗那一行的期望值真的不是 0。
- **其他規則檔的量測沒有掃**：守衛只掃 `zero-instance-guards.md`。`identity-is-judged-not-matched.md` 那條是正對照（期望 37），`plugin/CHANGELOG.md` 與 README 裡的同型寫法是歷史紀錄，沒有改。
