## 1. 旗標讀不到時，「位址上已經有同一份」那一支繞過拒絕（finding 0，MEDIUM）

**成立。** 前置閘只在能力旗標回 `false` 時拒絕；回 `nil`（旗標無效或讀不到）時交給實際的放置呼叫。而位址上已有大小相同的普通檔時，`writeBlob` 直接回
「早已在」，根本不呼叫 `renamex_np`／`link`——旗標讀不到又真的做不到的磁碟區上，那一支回成功；index 缺那一列時還補一列。b26 F6 的「每一次存檔都拒絕」在那裡不成立。
Codex 給的交叉情境（先以真的系統呼叫存一份，再以「旗標讀不到、兩個呼叫都不支援」存同一份）在修正前回成功，修正後拒絕。

**修法：實際放一次**（`SourcePlacement.swift` 的 `assertDirectoryCanPlace`，`writeBlob` 在排除驗證之後、任何分支之前呼叫）。對這個分片目錄：

- 能力旗標說做得到 → 放行；說做不到 → 同一句具名拒絕（分片目錄被換成指向別的磁碟區的 symlink 時也擋得下：`getattrlist` 不帶 `FSOPT_NOFOLLOW` 會跟隨它）。
- **讀不到（`nil`）→ 實際放一次**：以 `O_EXCL` 在同一個目錄建一個空的探測檔，經同一條放置路（`placeTemporaryBlob`：`RENAME_EXCL`，不支援時 `link(2)`）放到另一個暫存名上，
  之後兩個名字都刪掉。兩個呼叫都回「不支援」就是同一句拒絕；呼叫端什麼都不寫——不放 blob、不補 index。這一步自己建的目錄在拒絕時以 `rmdir` 收回（只刪空的），
  所以拒絕是真的零寫入（先前旗標讀不到時分片目錄會留著）。

**為什麼選探測、不選「寫誠實邊界＋跳過 index」**：探測是安全的，理由逐條——(1) 兩個探測名都是 `temporaryBlobName` 的形狀（帶這一次的 UUID），各自過排除驗證（#145：問的是實際要建的路徑），
被 `SIGKILL` 留下時 doctor 報它們是殘留的暫存檔；(2) 都登記給訊號清理（來源名經 `InFlightSourceFiles.create`，目的名在放置之前以 `register` 登記），`SIGINT`／`SIGTERM`／`SIGHUP` 會刪掉；
(3) 檔是空的，不是第三方內容；(4) 只在旗標讀不到時跑——APFS、HFS+ 讀得到旗標，不多一次系統呼叫以外的成本。另一條路（只寫邊界、旗標讀不到時跳過 index）要另外決定「已在的內容回成功還是失敗」，
而「實際呼叫決定」本來就是 b26 F6 對 `nil` 的承諾；探測讓那句承諾在每一條路上都成立。探測順帶讓新內容在**複製之前**就被拒絕：先前要把整份（至多 256 MiB）寫進暫存檔、`F_FULLFSYNC` 之後才發現，
`copy-zotero-attachments` 的每一筆都付一次（finding 20 的成本）。

**誠實邊界**：預演（`preflightStoreSource`）不探測——乾跑也走它，而乾跑不寫任何東西；旗標讀不到時 `copy-zotero-attachments` 的乾跑說可以、實跑逐筆拒絕（每筆在複製之前、零寫入，記進 `writeFailed`）。
探測之後同一個目錄才換成不支援的磁碟區時，真的放置那一步仍會拒絕，暫存檔由 `defer` 刪掉。SMB、NFS、FUSE 沒有實測。

**測試**（`SourcePlacementTests`）：`testExistingContentIsAlsoRefusedWhenTheVolumeReportsNothingAndCannotPlace`（Codex 的交叉情境：先 `.system` 存、再 `fatLike(volumeReports: nil)`——拒絕、
index 不變；拿掉 index 之後再存——拒絕、不補一列、`RENAME_EXCL` 被呼叫過一次）；`testWhenTheVolumeReportsNothingTheRefusalComesFromTheCallsAndLeavesNothing` 加兩個斷言（同步一次都沒被呼叫＝拒絕在複製之前；
`sources/` 底下零殘留＝分片目錄也收回）；`testTheProbeLeavesNothingBehindWhenThePlacementWorks`（旗標讀不到而其實做得到：探測一次、放上位址一次，兩個探測名都是暫存檔的形狀、都刪掉；已在的內容回「早已在」）。
**負控**：拿掉 `writeBlob` 的 `assertDirectoryCanPlace` → 三支紅、8 則失敗（交叉情境回成功、index 補一列、內容先被同步、分片目錄留著）。

## 2. 同步的「不支援」補 `ENOTTY`、`ENODEV`、`ENOSYS`（finding 1 MEDIUM、5 LOW、14 LOW）

**成立，前提有一半是 verify 量到的**：regression 席在掛載的 cd9660 映像上量到 `fcntl(F_FULLFSYNC)` 回 `ENOTTY`（25）、`fsync` 成功；logic 席在 devfs 上量到 `ENODEV`（19）。
DA 席指出本機可建立的四種檔案系統（APFS、HFS+、exFAT、FAT32）上 `F_FULLFSYNC` 都回 0，「某個**可寫**、能通過磁碟區閘的檔案系統回 `ENOTTY`」沒有人證實——所以這是未重現的設計風險，
後果是具名的拒絕、不是資料損壞。處置照主 session 的裁決：`LibraryStore.syncUnsupported` 是封閉的六個 errno——`ENOTSUP`、`EOPNOTSUPP`、`EINVAL`、`ENOTTY`、`ENODEV`、`ENOSYS`，
只有它們退到 `fsync`；`EIO`、`ENOSPC`、`EDQUOT`、`EROFS` 等仍是真的錯誤、不退（b26 F6 的裁決「不吞真的 I/O 錯誤」不變）。`fsync` 也回其中一個時仍是盡力而為（回 0）。
同步失敗的訊息改成說出 errno 與它的說明（`同步到裝置失敗（errno 25，Inappropriate ioctl for device）`），與放置的錯誤共用 `errnoText`。

**測試**：`testFsyncIsOnlyTheFallbackForAnUnsupportedFullFsync` 擴到六個「不支援」，另加四個真錯誤不退、不去試 `fsync`；`testASyncFailureRefusesAndLeavesNothing` 要求訊息含 `strerror` 的說明。
**負控**：從 `syncUnsupported` 拿掉 `ENOTTY` → 4 則失敗。

## 4. `akashic_store_source` 的說明寫「exclusionVerified=false 時拒絕」，與行為相反（finding 3、8，LOW）

**成立。** `exclusionVerified` 只回報、不重複判斷（`AkashicService.storeSource` 的 D3）：store 不在 git 工作樹內時排除驗證跳過、回 `false`、位元組照存；真正拒絕的是 store 在 git 內而 `sources/` 沒被忽略。

測試 `SourceAddressServiceTests.testTheStoreSourceDescriptionSaysWhatExclusionVerifiedFalseMeans`：在不是 git 工作樹的 store 上存一份（`false`、`bytesWritten:true`），並要求真 binary 的說明不說「false 時拒絕」、說「照存」。

## 5. 殘留暫存檔的時間不可信時：CLI 不自相矛盾，MCP 的 `possiblyInProgress` 往不刪的方向（finding 10、15，LOW）

**成立。** 修改時間在未來超過容忍時 `ageSeconds` 是 `nil`、`isStale()` 是 `true`（b26 F6：要人看一眼）。CLI 的說明依 `isStale()` 選，於是先說「不能用它判斷還在不在動」、
緊接著斷言「中斷的存檔留下的——…可以刪掉」；MCP 的 `possiblyInProgress` 是 `!isStale()`，成了 `false`——R2 verify 第 28 則為了「別讓 LLM 照 stray 去刪」才加的旗標，疑問被讀成「可以刪」。

**修法**：`StrayTemporaryFile.possiblyInProgress()`——一小時內還在動，**或時間不可信**（`ageSeconds` 是 nil：讀不到或在未來）。它與 `isStale` 不是互補：時間不可信時兩者都是 true，
`isStale` 管「要不要人看一眼」（`hasFindings` 與 App 計數不變），`possiblyInProgress` 管「可不可以刪」。MCP 用它；CLI 對時間不可信的檔改說「判不出是中斷的存檔留下的、還是正在進行的存檔——
確認沒有 store-source／copy-zotero-attachments 在跑之後才可以刪」。`akashic_doctor` 的說明寫 `ageSeconds（null＝判不出）`、「一小時內還在動或判不出的不要刪」。
測試：`testAModificationTimeInTheFutureIsNotTrustedAndCountsAsStale` 加四個斷言、真 binary 的 `testDoctorDoesNotTrustAFutureModificationTime` 要求不出現「中斷的存檔留下的——」、
`SourceAddressServiceTests.testDoctorReportsOccupantProblemsAndTheAgeOfStrayTemporaryFiles` 加未來時間的那一段（`ageSeconds` 是 null、`possiblyInProgress` 是 true）。
**負控**：MCP 改回 `!isStale()` → 紅。
