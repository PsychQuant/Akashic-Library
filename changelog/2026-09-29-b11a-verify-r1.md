# 2026-09-29 B11a 驗證 R1 的修正：venue 合併的名字併入、venue references 寫入面與合併的耦合（#565、#567、#587）

B11a 整合後的 6 席 ensemble 驗證（Codex、security、requirements、regression、logic、DA）找到 41 則發現；#567 沒有需要修的東西，其餘落在 #565 的名字併入（順序相依、二次方、位元組相等）與 #587 的通用 references 面（死角與合併耦合）。逐項對應如下。

## #565：venue 合併的名字併入

**1. 三方合併的 variant 分類與提醒不再取決於被併者的處理順序**（Codex、regression、logic、DA 四席同指；真 binary 重現）

`venueNameAbsorption` 只在「這個名字第一次被搬進來」的被併者身上讀 variant 標記。倖存者沒有 `Shared Alias`、兩個被併者各帶一份完全相同的段而只有一個標 variant：標記在鍵較前的被併者身上時合併結果 `variant: [Shared Alias]`，在較後的身上時 `variant: []`；後一種順序還印「倖存者已有這個名字，合併不替它改分類」——那個名字是先併入的被併者帶進來的，倖存者從來沒有。

規則改成只看名字（canonical 鍵）在哪裡：

- 倖存者**原本沒有**的名字：任一被併者把它列在 variant 就標 variant（`variantClaims`）。理由：未標是「不作任何宣稱」（venue-entity spec），不構成對 variant 的反對，所以說法不同時取「有宣稱的」。
- 倖存者**原本就有**的名字：不改分類；被併者對它說的 variant 只提醒（`uncarriedVariants`），全部這樣說的被併者都點名、排序固定。「倖存者已有」只對原本的倖存者判斷，不對先併入的被併者判斷。
- authorized 降級的提醒依最終結果產生：新增 `Demotion.Outcome.becomesVariant(claimedBy:)`——d1 把 `Shared X` 當 authorized、d2 把它列為 variant、倖存者沒有它時，最終是 variant，提醒說出來、並點名 d2，不再預告「成為未標」。`authorizedDemotedByMerging` 改收整份 absorption。
- 乾跑與實跑共用同一份計算（沿用 `venueNameAbsorption`／`mergedVenueKeeper` 的共用點）。

**2. 名字併入回到線性**（Codex、security、regression 三席）

首版對每個候選 `segments.filter { canonical(...) == key }`，對累積的全部段重掃並重算 canonical。現在每段的 canonical 鍵只算一次，建 `canonical 鍵 → 段` 的索引，每個候選只查自己的鍵；「逐位元組完全相同」用 `[String: Set<[[UInt8]]>]` 查。同名組的逐段並存比對另有 `sameNameScanLimit`（101）上限——組內 k 段的 k(k−1)/2 對超過 5,000 即 k ≥ 101（100 段是 4,950 對，仍在上限內），而 `Venue.validate()` 對超過那個大小的同名組一律拒絕，掃得更多只是為一個必拒的結果花 CPU。

實測（debug build，in-memory，倖存者與被併者各 5,000 個相異名字，`venueNameAbsorption` 加 `mergedVenueKeeper` 各一次）：**0.08–0.11 秒**。同一個測試在負控 5（把二次方的掃描放回去）**118.7 秒**。

**3. 「完全相同」比 UTF-8 位元組**（Codex）

`$0.segment.source == s.source && $0.segment.note == s.note` 是 Swift `String ==`，canonical equivalence——NFC 的 `Café` 與 NFD 的 `Cafe\u{0301}` 相等，被併者那一段被當成完全相同而略過，note／source 的位元組隨檔案消失。現在 `nameSegmentByteKey` 對時間欄位、source、note 各取 UTF-8 位元組（optional 用 tag 分開 nil 與空字串）；名字本身仍以 `NameIdentity.canonical` 判身分、不進這把鍵——所以被併者尾隨空白的髒寫法與倖存者乾淨的同名段仍是「完全相同」、照舊整段不搬（`testDoomedDirtNameThatWouldBeFilteredOutDoesNotBlockTheMerge`）。只差 NFC／NFD 的 note 現在是「不能並存」、具名拒絕。

**4. 拒絕訊息**（security、requirements、regression）

- 不能並存的清單：至多列 20 組（`Entry.perRecordWarningCap`），其餘一句「另有 N 組…（共 M 組；每次至多列 20 組）」；衝突依被併者分組一次（不再每個被併者重掃全部衝突）。
- 出路依衝突的另一方分開寫：另一方是先併入的被併者時，說是兩個被併者互相衝突、改其中一筆的 YAML（把那段寫進倖存者只會讓它與先併入的那段重疊，分兩次合併也解不掉）；另一方是倖存者時，說要連倖存者自己的那一段一起換掉（無日期段與有日期段是同名近重複，只把被併者的寫進倖存者會被寫入閘擋下）。

**5. 過時的測試註解**（requirements）：`testDoomedDirtNameThatWouldBeFilteredOutDoesNotBlockTheMerge` 的 doc comment 寫「以 canonical 對倖存者 names 濾除」，改成 #565 起的規則，並註明這支測試只釘住「名字身分是 canonical、完全相同的段整段不搬」那一半。

## #587：通用 references 寫入面與合併的耦合

**6. 通用面只收 `field: issn` 與 `field: names`**（regression 席以真 service 重現；requirements 席同指）

venue 的 reference 沒有移除面，所以每多收一格就多一個「寫得進去、之後只能手改 YAML 才出得來」的死角。`authorized`：寫進去之後 `authorize` 換對外形被拒（「移出後它們成孤兒」，訊息叫人刪掉那些 reference，而沒有面刪得掉）；`note`：沒有工具寫入面。`parseVenueReference` 對兩者具名拒收，並說明為什麼、出路（要記「這個名字是對外形」的來源，記在 `field: names`）；其餘欄位也具名拒收（只收 issn 與 names）。同步：`akashic-verify-venue` 的 SKILL（只用 issn／names 兩格，補了通用面的邊界與合併的注意事項）、`mcp-cli-parity`、`two-kinds-of-edits`、`zero-instance-guards` 第 43／45 列、`docs/store-format.md` §3.5、MCP 描述與 CLI help。

**7. 合併搬移 `field: issn`／`names` 的 reference**（regression、requirements、logic 三席）

`akashic-verify-venue` 對每個寫進去的號附一筆來源，「查證兩筆是不是同一本刊」又是合併的前置動作；`fieldsLostByMerging` 對非 verdict 的 reference 比位元組，兩次取得的日期／url 必然不同——每個查證過的被併者都合併不了，而拒絕訊息說「沒有工具面能搬」對這兩格已經是假話。

- `venueReferenceCarry(v, into:, mergedNames:)`：被併者的非 verdict reference 分成「倖存者已有位元組相同的一筆」（不動）、「`issn`／`names`，且它指的號或名字在合併後的倖存者上存在」（搬）、其餘（失去）。`fieldsLostByMerging`（拒絕）與 `mergedVenueKeeper`（實際搬）共用這一份，dry-run 與實跑對搬了什麼給同一個答案。
- 逐位元組搬、以 `byteExactKey` 去重（含倖存者原有的與先併入的被併者搬來的）。kind 不看：retrieval 與 judgement 型的這兩格都搬。
- 報告新增 `ResolveReport.referencesCarried`（進 `==`；dry-run 也預告；CLI 印「reference 已隨合併遷移到倖存者」）。
- 拒絕訊息逐格準確：「沒有工具面能搬」只用在真的沒有的（`paginated` 的判定、手改的 `authorized`／`note`）；`issn`／`names` 的 reference 走到拒絕只可能是它指的值不在合併後的倖存者上，訊息說「搬過去會成孤兒」。

**8. 合併不再默默丟掉 ISSN 角色**（logic 席，DA 席以真 binary 重現，範圍比原報告更廣）

`fieldsLostByMerging` 只以 `normalized` 比 ISSN、從不看 `qualifier`：倖存者無角色而被併者 `(print)` → 角色消失；倖存者 `(print)` 而被併者同一個號 `(electronic)` → 矛盾，倖存者靜默贏。兩種都列進遺失、具名拒絕，出路各寫明：

- 倖存者無角色、被併者有標準角色：先在倖存者 `update-venue --add-issn "號 (角色)"` 補上（add_issn 填缺席的格），再合併。被併者的角色認不出（遷移留下的 `Online`）：add-issn 收不下，說手改 YAML。
- 兩邊角色不同：`--remove-issn` 再 `--add-issn`，並說明移除會連帶刪掉倖存者上指向那個號的 reference；或從被併者的 YAML 刪掉它的角色。
- 倖存者有角色而被併者沒有：不算失去。

同號角色的比較是 `qualifierRaw` 的 UTF-8 位元組。loss 行的顯示上限從 300 提到 400 字元，出路才不會被截掉。

**順手（security 席 LOW 的一半）**：`updateVenue` 的 references 去重把 `ref.byteExactKey` 提到迴圈外、以 `Set` 查；先前在 closure 裡對每個既有元素重算，單筆最多 3×64 KB 的位元組複製。

## 不修的（記錄理由）

- **linking 與 print／electronic 同號**：ISSN-L 依標準必然等於某一個媒介 ISSN，而模型一個號只有一個角色欄。這是模型限制；本輪不動模型。`add_issn` 對已記為 print 的號再送 `(linking)` 仍整批拒絕，`akashic-verify-venue` 的 SKILL 已寫 linking 只給獨立的號。
- **遷移留下的 `Online` 角色被當成矛盾**：`ISSNMedium(loose:)` 只認三個小寫值，認不出同義。validate 叫人改成標準寫法、寫入面又拒絕改寫既有角色，出路是 `remove_issn` 再 `add_issn`（會連帶刪掉那個號的 reference）或手改 YAML。live store 認不出的角色 0 筆。合併時對這種角色的拒絕訊息已說「手改 YAML」。
- **url 原樣入庫**（含帳密、token、非 http scheme；`retrieved`／`status` 不驗值域）：`ProvenanceReference` 平面 init 與 `update_person`、`enrich` 是同一個既有契約；收緊要在 core 一處做並動到三個面，不在本輪。
- **digest 不核對 `sources/`**：寫入時不擋，`validate` 以 warning 報「本機缺承重存檔」（`zero-instance-guards` 第 15 列）；DA 席以真 binary 確認不是靜默。
- **讀取面不顯示新 references**：`akashic_venue`／`venue --json` 不回一般 references（person 側同）。能寫不能讀的缺口，另案。
- **`add_issn` 清單沒有筆數上限**：與 references 一次 200 筆的上限不對稱；`parseISSNItems` 的去重對相異的號仍是 O(n²)。輸入來自呼叫端而非 store，本輪只把 references 去重的重算提到迴圈外。
- **`0003 066X (print)` 被拒**：空白分隔又帶括號角色的寫法，整串的 `ISSN(_:)` 因為多了括號而不成立，`singleQualified` 又把空白切成兩個 token；沒有角色的 `0003 066X` 與無連字號的 `1935990x (electronic)` 照收。拒絕是具名、整批零寫入；已在 `parseISSNItems` 的 doc comment 註明。
- **#567 的 format 14 寫入閘**：INFO 級發現。閘是 #554 R20 預告過的範圍，format 13 且已帶 variant 的 store 在 bump 之前對那些 venue 的任何寫入都被拒，live store 是 format 18、零實例。合併時 variant 來自被併者、訊息卻寫成倖存者的 variant 無效（歸責到倖存者）——只在 format < 14 的 store 上出現，本輪不動。
- **只差 source／note 的同名段沒有修復面**：合併具名拒絕，出路是手改 YAML（`update-venue` 沒有編輯 names 段 source／note／時間欄位的參數）。live store 帶這些欄位的段 0 筆；出現需求時另案裁決要不要補面或降為提醒。

## 誠實邊界

- `sameNameScanLimit` 讓超過 101 段的同名組不再逐段比並存：那種組進得了 `incoming` 但過不了寫入閘（同名段過多一律拒絕），所以合併仍然失敗，只是訊息不再逐段點名衝突的是哪一段。
- 倖存者原本就有的名字，被併者對它的 variant 標記只提醒、不帶過去（#565 的原裁決不變）；這一輪改變的是「原本沒有的名字」在多個被併者之間的取捨（任一標了就標），這是對 D1 的延伸，使用者可翻。
- `venueReferenceCarry` 的 `names` 判斷用 `String ==`（與 `validateReferenceAttachment` 同一把）。倖存者以髒寫法（NFD、尾隨空白）持有同名時，搬過去的 reference 的 value 是被併者的位元組、指向的名字是倖存者的位元組——載入驗證放行，#582 的重複 reference 掃描若日後遇到兩筆同指一個名字的 reference 會報。
- 搬 reference 時 kind 不看。若日後要區分（只搬 retrieval），要在 `venueReferenceCarry` 一處改。
- 合併時被搬走的 reference 只在報告與 git 歷史留下來源（`referencesCarried`）；那些 reference 進了倖存者之後仍沒有移除面。

## 需要另開的 follow-up issue（由整合者開）

1. **venue 的 reference 移除面**：`update-venue --remove-reference`（或以 field＋value＋位元組鍵定位）。理由必填、只進報告、要求 venue 檔已 commit（移除面一族的既有裁決）。沒有它，通用面每多收一格都是死角；有了它，`authorized`／`note` 兩格才有可能重新評估。
2. **venue 與 person 兩個 references 面的契約對齊**：`update_person` 的 `status` 預設 200、不認得的鍵靜默忽略、沒有上限；venue 面 `status` 必填、鍵名嚴格、有上限；CLI 上 person 走 `--fields '{"references":[…]}'`、venue 走 `--references`。需要裁決往哪一邊對齊（#542 R2 對 `enrich` 裁掉過 status 預設 200）。
3. （建議）**venue names 段的 source／note／時間欄位沒有編輯面**：合併對只差這些欄位的同名段具名拒絕，出路只有手改 YAML；補面或把「只差 source／note」降為提醒，由使用者裁決。
