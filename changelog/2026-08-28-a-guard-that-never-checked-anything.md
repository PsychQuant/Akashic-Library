# 一個從來沒有真的檢查過任何一列的守衛

2026-08-28，#365。要把三項裁決補進 `zero-instance-guards` 的裁決表時，意外揭露
`zero-instance-rows-audit` **一直在讀錯欄位**。

## 抽取式要求 markdown 不要求的東西

```swift
// 舊
NSRegularExpression(pattern: #"^\| (\d+) \| (.*?) \| (.*?) \|"#)
```

它要求分隔符**前面有空格**（` |`）。而 markdown 不要求，本表既有的每一列都寫成：

```
| 1 | **零實例、成本一行、前件精確**（…種類數 = 0）| ✅ **寫** | 成本是一行前件；… |
                                                ↑ 這裡沒有空格
```

**後果不是「讀不到」，是每一欄往後挪一格**：`verdict` 讀到的是**理由欄**。於是
`verdict.contains("✅")` 對每一列都是 false，每一列都 `continue`——
**守衛從來沒有真的檢查過任何一列的實作是否在場**，而它十一列全綠。

## 它怎麼騙過負控的

負控 harness 有一個 case「新增一列裁決『寫』而編號在 Sources 裡不存在」，而它**通過**了。

原因：那個 mutation 插入的假列是我寫的，**格式恰好合抽取式的要求**（有 ` | `）。
所以守衛對**那一列**讀對了欄位、報了錯、negative control 綠燈。

**守衛只檢查過負控注入的假列，從沒檢查過表裡真的列。** 那正是本檔第 5、6 兩列講的
形狀（守衛對自己的覆蓋率說謊／從沒紅過的檢查與不存在的檢查長得一樣）——發生在守衛
**自己**身上。

## 三種分隔符狀態，三種行為

實測（`| n | a | b | c |` 的四個分隔符）：

| 狀態 | 守衛的行為 |
|---|---|
| 兩處缺空格 | **整列不匹配** → 少數一列，靜默 |
| 只有中間有 | 正確 |
| **只有行尾有** | 匹配，但**裁決欄讀成理由欄** ← 靜默誤判 |

第三種最危險：理由裡碰巧出現一個 `✅`，一個裁決「不寫」的列就會被要求實作在場；
反過來一個「寫」的列會被靜默跳過。

## 修法是改抽取式，不是改表

先前的直覺是「把表格格式統一成 ` | `」——**方向反了**。markdown 的語意是分隔符兩側
的空白無關緊要，而表是人寫的。改成整行切欄、兩側 trim。

同時加兩道兜底：

- **列號連續**——不需要知道表該有幾列（那個數字會長），只需要知道編號不該跳號
- **裁決欄必須含 ✅／⚠／❌ 之一**——抓「往後挪一格」那一種

## 一個 regression，由新檢查造成

列號檢查讓負控的那個 case 紅了：它插在第 4 列前並用編號 `5`，序列變成 1,2,3,5,4,…
——跳號檢查先觸發，蓋掉了那個 case 期望的訊息。

改成插在**表尾**且編號接續（錨點取表格後面那句散文，它不會隨列數成長）。

## 順帶：#365 的兩列

`corresponding author` 與 `role` 進表，皆 **❌ 不寫**——本表**第一次**出現「不寫」的裁決，
而該檔自己預測過這一天：

> 零實例且**成本高**的守衛。真出現時要加一列，而那一列的理由**很可能是「不寫」**。

**那個預測對了一半**：兩列的裁決確實都是「不寫」，但它預測的理由（成本高）只涵蓋第 11 列。
第 10 列的理由是**形狀取決於一個還不存在的用途**——成本高只是背景。

`pseudonym` **不進表**：它的裁決不是「不做」，是「做在別的地方」（`PersonNames` 的
`variant` 分區已經是它的位置）。
